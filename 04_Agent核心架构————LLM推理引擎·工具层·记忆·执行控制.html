04. Agent核心组件——LLM+工具+记忆+执行控制

⭐⭐ 中级 四大组件 LLM推理引擎 工具层 记忆系统 执行控制 数据流

一、题目描述

ReAct 是引擎，但 Agent 是整车。不理解四大组件如何协作，就无法构建真正能干活的 Agent。——本文作者

背景：Agent 不只是带工具的 LLM

很多初学者对Agent的理解停留在"LLM + 几个工具"这个层面。这种理解的问题在于忽略了两个关键维度：状态管理（Agent在多轮交互中如何记住和利用历史信息）和执行控制（Agent如何决定下一步做什么、何时停止、出错怎么办）。一个没有记忆的Agent就像金鱼——每次对话都从零开始；一个没有执行控制的Agent就像没有刹车的跑车——跑得快但随时可能撞墙。

FutureAGI 在2026年发布的《LLM Agent Architectures》报告中，将现代Agent分解为六个核心层级：Language Model Core（语言模型核心）、Memory System（记忆系统）、Tool & Plugin Layer（工具与插件层）、Planner & Reasoning Layer（规划与推理层）、Orchestration Runtime（编排运行时）、Observability & Evaluation（可观测性与评估）。这六个层级中，前四个是Agent的"业务核心"，后两个是"运维支撑"。本题聚焦于前四个——它们直接决定了Agent的能力上限。

而在这四个核心层级中，又可以进一步归纳为更本质的"四大组件"模型：LLM（大脑）、工具（双手）、记忆（上下文）、执行控制（神经系统）。这个四组件模型虽然简化了六层架构（将规划推理融入LLM、将编排融入执行控制），但更利于理解和实践。下面我们就用这个模型来拆解Agent。

从架构全景图中可以看到，四大组件并非简单的串行管道——它们之间存在复杂的双向交互。LLM是中央枢纽，既向工具层发送调用请求、接收执行结果，也向记忆系统写入中间状态、检索历史信息，同时还被执行控制层所调度和约束。理解这些交互的数据流，是设计Agent架构的核心能力。

题目要求

本题要求你从架构视角理解Agent的四大核心组件，并能独立设计一个完整的Agent系统。具体要求分为四个层次：

层次一：组件认知 清晰理解LLM、工具、记忆、执行控制四大组件各自的职责边界、核心能力和常见误区。能向非技术人员解释"Agent到底由什么组成"。
层次二：数据流分析 掌握组件之间的数据传递机制——用户输入如何被LLM解析、工具结果如何注入上下文、记忆如何在多轮对话中累积和淘汰。
层次三：架构设计 给定业务场景，能设计合理的组件配置方案——选什么模型、配什么工具、用什么记忆策略、设什么控制参数。并能为设计决策提供量化依据。
层次四：代码实现 使用LangGraph 1.x的create_agent API，结合国内可用模型（deepseek-v4.1-flash/deepseek-v4.1-flash），实现一个包含四大组件的可运行Agent。

二、详细思路分析

要设计一个完整的Agent系统，必须深入理解每个组件的内部机制、设计原则以及组件间的协作模式。我们将逐一拆解四大组件，然后分析它们如何通过数据流串联成一个有机整体。在进入具体组件之前，先通过一张时间线了解Agent各组件技术的演进历程——这有助于理解为什么现代Agent采用这样的架构。

2.1 LLM——Agent的大脑与推理引擎

LLM是Agent中唯一具备"智能"的组件——其他三个组件（工具、记忆、执行控制）本质上是确定性的软件系统，它们的价值完全依赖于LLM如何调度和使用它们。这就是为什么我们把LLM称为"大脑"：没有大脑的Agent就像一台没人开的机器，工具再先进也只是在闲置。

但"LLM是大脑"这个类比还不够精确。更准确的说法是：LLM是Agent的推理引擎（Reasoning Engine）。它不做执行（执行是工具的职责），不做存储（存储是记忆的职责），不做流程控制（流程控制是执行控制层的职责）。LLM的职责边界非常清晰——接收上下文输入，理解意图，进行推理，做出决策（调用什么工具、传什么参数），综合工具返回的结果，生成最终输出。

在Agent架构中，LLM承担了五项核心推理任务，这些任务构成了Agent"智能"的全部来源：

第一，意图理解与任务分解。用户说"帮我查一下最近的AI新闻然后总结成周报格式"，LLM需要理解这是一个多步骤任务，并将其分解为"搜索新闻→筛选最近一周→提取要点→按周报模板组织"等子任务。这个分解能力直接决定了Agent处理复杂任务的上限。deepseek-v4.1-flash.1和deepseek-v4.1-flash-V3在这一项上的表现已经接近甚至在中文场景下超过了deepseek-v4.1-flash，尤其在理解中文语境的隐含意图方面——比如用户说"上次说的那个方案"，deepseek-v4.1-flash.1对中文上下文的衔接理解更为自然。

第二，工具选择与参数构造。当Agent拥有多个工具时，LLM需要根据当前推理结果选择最合适的工具，并构造正确的调用参数。这看似简单，实则是Agent最常见的失败点——工具描述写得不够清晰、参数Schema设计不合理，都会导致LLM选错工具或传错参数。会专门深入这个问题。

第三，结果综合与推理链构建。工具返回的是结构化或半结构化数据（JSON、文本、表格），LLM需要将这些原始数据整合进推理链，形成连贯的逻辑推导。比如搜索返回了三篇新闻，LLM不能简单拼接，而要判断哪些信息相关、哪些可忽略、如何组织成用户能理解的回答。

第四，错误识别与策略调整。当工具调用失败或返回意外结果时，LLM需要识别问题并调整策略。搜索API返回空结果？换一个关键词重试。数据库查询超时？降级为缓存数据。这种"发现错误→改变方向"的能力是Agent区别于固定工作流的核心价值。

第五，终止判断。LLM需要判断"当前信息是否足够回答用户问题"。判断过早会导致答案不完整，判断过晚会浪费Token和增加延迟。这个看似简单的判断实际上涉及复杂的元认知（metacognition）能力——模型需要评估自己"知道什么"和"不知道什么"。

理解了LLM的五大职责后，模型选型就有了清晰的评估维度。不是简单地看"谁跑分高"，而是要针对Agent场景的特定需求做选择。以下是Agent场景下模型选型的关键考量：

模型选型只是第一步——选完模型还需要正确地配置参数。在Agent场景下，有三个参数需要特别关注：

temperature（温度参数）：控制LLM输出的随机性。在Agent场景中，推理和工具选择步骤应使用低温度（0.1-0.4）以确保决策的确定性，而最终答案生成步骤可以使用稍高的温度（0.6-0.8）以增加回答的自然度。很多Agent框架支持"分段温度"配置——在ReAct循环中，Thought步骤用低温度，Final Answer步骤用高温度。

max_tokens（最大生成长度）：设置LLM单次输出的Token上限。Agent场景下的关键考量是——如果设置太小，LLM的推理链可能被截断，导致Thought不完整、工具参数缺失；设置太大，一旦LLM"跑偏"会浪费大量Token。实践建议：推理步骤设512-1024 Token，最终答案设2048-4096 Token。

tool_choice（工具选择策略）：部分模型API支持配置工具选择行为——"auto"让LLM自主决定是否调用工具，"required"强制必须调用工具，"none"禁止调用工具。在ReAct Agent中通常使用"auto"；在需要强制工具调用的场景（如"必须先搜索再回答"）可以使用"required"。

最后讨论模型分层策略。在生产Agent中，并非所有推理步骤都需要最强模型。一个常见的成本优化策略是"模型分层"：复杂推理步骤（如任务分解、策略选择）使用deepseek-v4.1-flash.1等旗舰模型，简单步骤（如结果摘要、格式化输出）使用更轻量的模型（如deepseek-v4.1-flash-Flash或DeepSeek的蒸馏模型）。IBM的研究表明，这种分层策略可以在不损失答案质量的前提下降低40-60%的Token成本。会深入这个话题。

2.2 工具层——Agent的双手与能力扩展

如果说LLM是Agent的大脑，工具就是Agent的双手——它将Agent的能力从"只能说"扩展到"能做事"。没有工具的Agent就像一个博学但手无缚鸡之力的学者：它可以告诉你"巴黎现在14°C，降雨概率70%"的获取方法，但无法亲自去查——因为它的知识冻结在训练数据里。

工具层的本质是为LLM提供与外部世界交互的能力。这种交互可以分为三个维度：获取信息（搜索、数据库查询、API读取）、执行操作（发邮件、写文件、提交表单）、计算处理（代码执行、数学运算、数据转换）。这三个维度覆盖了Agent绝大多数的工具使用场景。

设计工具层时，最重要的原则是"工具是LLM的API，不是人的API"。这意味着工具的接口设计必须为LLM优化——具体来说，工具名称必须是自解释的（search_web而非sw），参数描述必须包含类型和含义说明，返回结果必须是LLM能理解的结构化文本。一个常见的错误是直接将人类使用的REST API暴露给LLM——200个字段的下拉框、未文档化的速率限制、脆弱的中间件，这些对LLM来说就是灾难。Composio的2025报告将这种情况称为"Brittle Connector"（脆弱连接器），是Agent生产化的三大陷阱之一。

2024年11月，DeepSeek发布了MCP（Model Context Protocol）协议，被业界称为"AI的USB-C"。MCP的核心价值在于标准化：它将工具定义、调用协议、传输层全部规范化和解耦，使得任何MCP兼容的客户端（如Claude、Cursor、Windsurf）都能直接连接任何MCP Server，无需为每个工具写定制集成代码。截至2026年，MCP生态已有9400+个公开Server，覆盖搜索、数据库、文件系统、代码执行等几乎所有常见工具类型。第10-11题会深入MCP的细节。

ℹ️ 国内生态提示

MCP是开放标准，国内模型如deepseek-v4.1-flash.1和deepseek-v4.1-flash-V3均可通过LangChain工具适配层接入MCP生态。此外，阿里云百炼平台、扣子（Coze）等国内平台也提供了类似的工具市场和标准化接入方式。

工具数量是另一个需要关注的维度。直觉上"工具越多能力越强"，但实际并非如此。研究表明，当工具数量超过15-20个时，LLM的工具选择准确率会显著下降——因为LLM需要从越来越长的工具列表中找到最匹配的那个，这增加了误选的概率。解决方案有三种：工具分组（按类别组织，先选组再选工具）、工具Reranking（用轻量模型先对工具做相关性排序）、多Agent分担（不同Agent各管几个工具）。会深入讨论"何时应该从单Agent升级为多Agent"。

2.3 记忆系统——Agent的上下文管理

记忆系统是四大组件中最容易被忽视、却最直接影响用户体验的组件。一个没有记忆的Agent就像金鱼——每次对话都从零开始，你刚才告诉它"我是后端开发者"，下一轮它就忘了。AWS re:Invent 2025的主题演讲中有一句话精辟地概括了这个问题："无状态LLM远远不够。是时候构建能学习、记忆、进化的应用了。"

MarkTechPost在2025年11月的深度对比文章中，将Agent记忆系统分为三大族类、六种系统模式。这个分类框架是迄今为止最全面的Agent记忆系统分类，值得深入理解：

这张分类图看起来选择很多，但在实际Agent开发中，最常用的记忆架构是"双层架构"——短期记忆用滑动窗口管理当前对话上下文，长期记忆用向量数据库存储历史信息。这种架构覆盖了80%以上的应用场景，也是各种Agent框架（LangGraph、CrewAI、Dify）的默认记忆实现。

短期记忆的核心挑战是"上下文窗口溢出"。即使现代模型的上下文窗口已经达到128K甚至更长，在多轮ReAct循环中，每一步的Thought、Action、Observation都会累积。一个10步的ReAct循环，加上工具返回的长文本，轻松就能消耗掉数万Token。解决方案包括：滑动窗口（保留最近N轮）、摘要压缩（用LLM总结历史对话）、重要性淘汰（用注意力分数决定保留哪些信息）。这些策略将在深入展开。

长期记忆的核心挑战是"检索精度"。Composio的2025报告指出了一个反直觉的现象：有时候更少的上下文反而产生更好的结果。把所有Confluence文档、Slack历史、Salesforce数据全倒进向量库，然后粗暴地Top-K检索——Karpathy将这种情况类比为"把整个硬盘倒进RAM"。正确做法是"上下文精度优先于上下文数量"——精心设计的分块策略、多路召回+Reranking、基于元数据的过滤，这些才是高质量长期记忆的关键。

MemGPT引入的"虚拟内存"类比是最形象的记忆架构解释。在操作系统中，RAM容量有限，当数据超过RAM容量时，操作系统会将不常用的数据"换出"（page out）到硬盘，需要时再"换入"（page in）。MemGPT将同样的思路应用于LLM上下文：活跃上下文（RAM）是当前在LLM输入中的Token，归档存储（硬盘）是更大的外部向量库。关键创新在于——LLM自己决定何时换页，通过专门的工具函数（如archive_message和retrieve_memory）来主动管理自己的上下文窗口。这种设计带来了新的挑战：换页策略（paging policy）的优劣直接决定了Agent的表现——如果Agent错误地将后续需要的信息归档了，就需要额外的检索步骤才能恢复。

2025年NeurIPS会议发表的A-Mem论文代表了记忆系统的最新前沿。它借鉴了人类知识管理中的Zettelkasten（卡片盒笔记法）——每条新记忆不是一个孤立的向量，而是一张包含上下文描述、关键词、标签的结构化"笔记"。新记忆写入时，会自动建立与已有记忆的链接，甚至触发相关历史记忆的上下文更新。这意味着记忆不再是被动存储，而是一个自组织、可进化的知识网络。Richmond Alake在LinkedIn上将2026年称为"AI Agent Memory年"，记忆工程（Memory Engineering）正在成为一门独立的技能学科。

2.4 执行控制——Agent的神经系统

执行控制层（Execution Control）是四大组件中抽象程度最高的一个，但也是最关键的——它决定了Agent"如何使用其他三个组件"。如果说LLM是大脑、工具是双手、记忆是上下文，那么执行控制就是神经系统——它协调大脑何时思考、双手何时动作、记忆何时读取和写入。

第三题深入讲解了ReAct循环——它是最核心的执行控制模式。但ReAct不是唯一的选择。现代Agent的执行控制层主要有三种模式：

ReAct（边走边看） 每步都通过LLM推理决定下一步。灵活、自适应、容错强。但Token消耗高、延迟大（串行循环）。适合信息检索、动态探索、创意研究等路径不可预测的任务。
Plan-and-Execute（谋定后动） 先用Planner LLM生成完整步骤计划，再用Executor逐步执行。Token效率高（Planner只调一次大模型），计划可人工审核。但抗变性差。适合企业自动化、固定流程等路径可预测的任务。
混合模式（自适应控制） 先Plan生成大纲，再ReAct执行每一步。当执行中发现计划不适用时，触发重新规划。这是2025-2026年的主流趋势——结合两者的优点，根据任务复杂度自动切换控制模式。

无论选择哪种模式，执行控制层都需要处理四个关键的流程控制问题：

循环终止。Agent什么时候该停？这是最基本也最容易被忽略的问题。没有终止条件的Agent就是一个烧钱机器——Token消耗没有上限，直到触发API限制或耗尽预算。三种终止条件必须同时配置：最大迭代次数（硬限制，通常10-25步）、目标完成检测（LLM判断"信息足够了"）、Token预算耗尽（总消耗超过阈值）。三者是"或"关系——任何一个满足就停止。

错误处理。工具调用失败是常态而非例外——API超时、数据库连接断开、返回格式不符合预期。执行控制层必须将错误视为一类特殊的Observation：不崩溃，而是将错误信息格式化为"工具X返回错误：Y"的Observation，反馈给LLM让其调整策略。这和第三题提到的"错误即Observation"原则一致。

资源预算。除了Token预算，还需要管理工具调用配额（每种工具每天最多调用多少次）、并发限制（同时执行的工具调用数量上限）、时间预算（单次Agent运行的最大时长）。这些约束共同构成了Agent的"资源护栏"。

状态持久化。Agent运行的中间状态（当前的Thought链、已调用的工具及结果、记忆的临时修改）需要持久化存储——这不仅是为了调试，更是为了支持"断点续传"。LangGraph的Checkpointer机制就是为此设计的：它将Agent的完整状态序列化存储，使得Agent可以在任意节点恢复执行。会深入这个话题。

2.5 数据流——组件如何协作

理解了每个组件的内部机制后，接下来分析组件之间的数据流——这是将四大组件串联起来的"血液循环系统"。数据流分析是架构设计的核心技能：只有搞清楚数据从哪里来、到哪里去、经过什么变换，才能真正理解系统的工作原理。

从数据流图中可以提炼出几个关键洞察：

第一，LLM不是被动地"等待数据"。它主动地决定从记忆中检索什么、用哪个工具获取什么信息。这种"主动信息获取"（active information seeking）是Agent区别于普通RAG系统的核心特征——RAG是被动的"检索后生成"，Agent是主动的"推理→行动→观察→再推理"。

第二，工具调用结果（Observation）必须经过格式化才能注入LLM上下文。工具返回的数据格式各异——JSON、XML、HTML、纯文本——LLM需要的是结构化但自然的文本描述。执行控制层负责将工具原始返回转换为"Observation: 搜索'API限流'返回了3条结果：1. 令牌桶算法... 2. 滑动窗口..."这样的可读文本。这个"格式化"步骤看似简单，却直接影响LLM的理解效率——格式不好的Observation会导致LLM误解或忽略关键信息。

第三，记忆的写入和检索构成闭环。Agent每完成一次任务，应该将对话摘要、学到的事实、执行的经验写入长期记忆——这些信息会在未来类似的任务中被检索出来，形成正向循环。如果只检索不写入，Agent永远无法"进步"；如果只写入不检索，记忆库会膨胀到不可用。会深入跨会话记忆持久化的设计。

2.6 Agent架构常见陷阱

理解了正确的架构设计后，了解常见的反模式同样重要——有时候"知道什么不能做"比"知道什么能做"更有价值。Composio在2025年的报告中总结了Agent生产化的三大致命陷阱，这些陷阱在架构设计阶段就应该规避：

陷阱一："Dumb RAG"——把向量数据库当记忆。这是最常见的架构错误。开发者把所有企业文档、聊天历史、业务数据一股脑倒进向量库，然后Top-K检索就直接喂给LLM。问题是：向量检索是语义相似度匹配，不是智能检索——它会返回"语义相近但上下文错误"的结果。比如检索"用户A的订单"，可能返回"用户B的类似订单"，因为语义太接近了。Karpathy的类比很精准："上下文窗口是LLM的RAM，把整个硬盘倒进RAM不会让程序跑得更快。"正确做法是分层记忆+元数据过滤+Reranking——第19-21题会深入这些技术。

陷阱二："Brittle Connector"——直接暴露原始API给LLM。企业内部的REST/SOAP API通常缺少文档、有隐含假设、包含大量非必要字段。直接将这些API包装成工具暴露给LLM，就像"给新员工服务器机房钥匙但没有文档"——LLM不知道哪些参数重要、哪些可以忽略、速率限制是什么。解决方案是使用工具适配层（如MCP Server）对原始API进行Schema标准化和文档化。

陷阱三："Polling Tax"——用轮询代替事件驱动。某些Agent设计为不断检查"任务完成了吗？现在呢？现在呢？"——这种轮询模式会浪费95%的API调用配额，永远无法做到实时响应。正确架构应该是事件驱动的——工具执行完成后主动推送通知（callback/webhook），Agent收到通知后再继续推理。

Sam Witteveen在演讲中总结了Agent进入生产的五大问题：可靠性（输出不一致）、过度循环（陷入死循环）、工具设计不当（导致LLM误用）、自我检查缺失（Agent无法验证自身输出）、缺乏可解释性（无法调试Agent决策）。这些问题都可以追溯到架构设计阶段的缺陷——LLM选型不当、工具Schema设计糟糕、记忆策略错误、执行控制缺少约束。这也是为什么深入理解四大组件如此重要——它们是所有Agent问题的根源和解决方案的落脚点。

三、参考答案

本节提供一个使用LangGraph 1.x create_agent API构建的完整Agent实现。代码使用deepseek-v4.1-flash.1作为推理引擎（通过智谱API），包含三大工具、短期记忆管理和错误处理。代码分为四个部分，对应四大组件的配置。

步骤一：配置LLM推理引擎

第一步是选择并配置LLM。这里使用deepseek-v4.1-flash（智谱AI），它在国内可直接访问，支持结构化Function Calling，128K上下文窗口足以处理多轮ReAct循环的上下文累积。如果你更偏好deepseek-v4.1-flash，只需替换base_url和model参数即可。

代码中有两个值得注意的设计决策。一是temperature=0.3——Agent的推理步骤需要确定性，低温度能减少LLM"跑偏"的概率。二是定义了两个模型实例——model用于核心推理（deepseek-v4.1-flash），fast_model用于辅助任务（deepseek-v4.1-flash）。这种"模型分层"策略可以显著降低Token成本：简单任务不需要旗舰模型的推理能力，用轻量模型就够了。

步骤二：定义工具层

工具是Agent与外部世界交互的接口。每个工具用@tool装饰器定义，函数的docstring就是工具描述——LLM会阅读这个描述来决定是否使用该工具。因此，工具描述的质量直接决定了工具选择的准确率。

工具定义中有几个关键实践：第一，docstring使用英文（因为大部分模型的Function Calling训练数据以英文为主，英文描述的匹配率更高），但参数和返回值可以是中文。第二，每个工具的docstring明确说明了"何时使用这个工具"——这比描述"工具做什么"更重要，因为LLM已经知道搜索工具是搜索的，它需要知道的是"什么情况下该选择这个搜索工具而不是另一个"。第三，calculate工具有输入校验——只允许数学字符，防止注入攻击。

步骤三：组装Agent（含记忆和执行控制）

create_agent是LangGraph 1.x的标准Agent创建API（替代了已废弃的create_react_agent）。它在内部构建了一个StateGraph，包含agent节点（LLM推理）和tools节点（工具执行），通过条件边实现ReAct循环。

步骤四：增加长期记忆（可选增强）

上面的Agent只有短期记忆（当前对话的messages列表）。对于需要跨会话记忆的场景，可以增加长期记忆层。这里演示一个基于文件系统的简易实现——生产环境应替换为向量数据库（如Milvus）。

四大组件协作流程总结
1
用户输入 → 记忆检索：执行控制层接收到用户输入，先从记忆系统检索相关的历史上下文（短期窗口+长期记忆），拼装为增强的System Prompt。
2
LLM推理 → 工具选择：增强上下文+用户输入送入LLM推理引擎。LLM理解意图、分解任务、选择工具、构造参数，输出Thought+Action。
3
工具执行 → Observation：执行控制层调度工具调用，将工具返回的原始数据格式化为Observation文本，注入LLM上下文。
4
循环/终止判断：LLM根据Observation决定继续推理（回到步骤2）还是输出最终答案。执行控制层检查终止条件（迭代次数、Token预算、目标完成度）。
5
输出 → 记忆写入：最终答案返回给用户，同时执行控制层触发记忆系统将本次对话摘要写入长期记忆。

四、举一反三

理解了Agent四大组件的基础架构后，以下三个变体题帮助你将理解深化为实践能力。每个变体聚焦一个组件的深入挑战，做完后你将对"如何根据业务需求定制Agent架构"有清晰的设计直觉。

变体一：记忆系统替换——从文件到向量库

学习目标：将参考答案中的文件系统长期记忆替换为真正的向量数据库（Milvus），训练记忆系统架构思维。在实际项目中，文件系统的关键词检索只能处理几十条记忆——当记忆条数达到上千、上万条时，向量相似度检索是不可替代的选择。这个变体培养的核心能力是理解不同记忆后端的技术特征，并根据数据规模和查询模式做出正确选型。

与原题的差异：原题用文件JSON+关键词匹配模拟长期记忆，仅适用于演示。变体一要求接入Milvus向量数据库，实现真正的语义检索：对话摘要通过Embedding模型（推荐BGE-M3或GLM-Embed）转化为向量，存入Milvus，检索时用向量相似度（Cosine）而非关键词匹配。你需要处理分块策略（Chunk Size）、Embedding维度匹配、索引类型选择（IVF_FLAT vs HNSW）等问题。

核心挑战：

  1. 对话摘要应该按什么粒度分块？整条摘要作为一个向量，还是拆分为多个关键事实分别向量化？不同选择对检索精度有何影响？
  2. Milvus的IVF_FLAT和HNSW索引各有优劣——检索速度vs精度，如何根据Agent的延迟要求做选择？
  3. 当用户问"上次说的那个方案"这种指代性查询时，向量检索如何处理？（提示：需要先用LLM将指代消解为具体描述）
  4. 记忆衰减：30天前的旧记忆应该和新记忆一样容易被检索到吗？如何在向量相似度中加入时间衰减因子？

考察的核心能力：向量数据库选型与配置、Embedding模型选择、分块策略设计、记忆衰减实现。这个变体直接关联第19-20题（向量数据库选型和检索实战）。

变体二：多模型成本优化——Agent的"经济舱"策略

学习目标：在Agent运行过程中动态切换不同价格的模型，训练成本工程思维。原题虽然定义了model和fast_model两个实例，但没有实现动态切换逻辑。这个变体要求你实现一个"智能路由器"——根据当前推理步骤的复杂度自动选择模型。核心能力是在不损失答案质量的前提下，系统性地降低Agent的运行成本。

与原题的差异：原题的模型选择是静态的——所有ReAct步骤都用同一个模型。变体二要求实现动态分层：第一步的意图理解和任务分解用deepseek-v4.1-flash（复杂推理），中间的工具调用参数构造用deepseek-v4.1-flash（性价比），最终答案的格式化输 deepseek-v4.1-flash（简单任务）。你需要在LangGraph的自定义节点中实现模型切换逻辑，而不是简单地用create_agent的默认行为。

核心挑战：

  1. 如何判断当前步骤的"复杂度"？简单步骤用便宜模型，复杂步骤用贵模型——但"复杂度"如何量化？（提示：可以基于输入Token数、工具数量、推理深度等维度评分）
  2. 不同模型的输出格式可能有细微差异（如Function Calling的JSON结构），如何保证模型切换不会破坏工具调用的兼容性？
  3. 预算监控：实时追踪Token消耗，当总成本超过预算的80%时自动降级到全用便宜模型——这个逻辑如何实现？
  4. 如何评估模型分层对答案质量的影响？设计什么A/B测试来验证"省钱但不降质"？

考察的核心能力：模型选型与成本估算、动态路由实现、Token计量与预算控制、A/B测试设计。这个变体直接关联（成本控制——Token管理与缓存策略）。

变体三：自定义工具开发——从Schema到安全沙箱

学习目标：设计并实现一个生产级的自定义工具（如"执行用户提供的Python代码"），训练工具Schema设计与安全防护思维。原题的三个工具（搜索、计算、知识库）都是安全无副作用的读取操作。变体三要求实现一个有副作用的工具——代码执行——这涉及到输入校验、沙箱隔离、超时控制、资源限制等生产级问题。核心能力是在"工具强大"和"工具安全"之间找到正确的平衡点。

与原题的差异：原题的calculate工具只能做简单算术。变体三要求实现一个execute_python工具，接受任意的Python代码字符串并在隔离环境中执行。这大大扩展了Agent的能力（可以处理数据、生成图表、操作文件），但也带来了安全风险（代码注入、资源耗尽、数据泄露）。你需要在工具设计中同时考虑功能完整性（代码能正常运行）、安全性（不能执行危险操作）、可控性（超时、内存限制）。

核心挑战：

  1. 沙箱设计：如何隔离代码执行环境？Docker容器、subprocess+seccomp、还是Python AST白名单？各自的优缺点是什么？
  2. 工具Schema设计：code参数的JSON Schema如何描述？如何告诉LLM"只接受数据处理代码，不接受网络请求代码"？这种约束是写在Schema里还是运行时检查？
  3. 错误处理：代码执行失败时，返回给LLM的错误信息应该包含多少细节？太详细可能泄露系统信息，太简略LLM无法自我纠错。
  4. 权限分级：不同信任级别的用户应该有不同的代码执行权限。如何在工具层实现RBAC（Role-Based Access Control）？

考察的核心能力：工具Schema设计、沙箱隔离架构、安全策略实现、错误处理设计。这个变体直接关联第15-16题（自定义工具开发和工具安全）。

🔑 举一反三要点
  • 变体一（记忆升级）：从文件到Milvus，核心是从"关键词匹配"升级为"语义检索"，关键决策是分块策略和Embedding模型
  • 变体二（成本优化）：动态模型路由，核心是将"用最贵的模型"变为"用最合适的模型"，关键挑战是复杂度判断和兼容性保证
  • 变体三（安全工具）：代码执行沙箱，核心是"强大与安全的平衡"，关键设计是隔离层和权限分级
  • 三个变体分别深入四大组件中的一个——记忆、LLM、工具——做完后你将对Agent架构有全栈式的深入理解
