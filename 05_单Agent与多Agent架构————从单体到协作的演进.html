05. 单Agent与多Agent架构——从单体到协作的演进

⭐⭐⭐ 中级 单Agent天花板 多Agent编排 通信开销 分解时机 MAST失败分类

一、题目描述

背景故事:FinAssist 的架构危机

你是一家金融科技创业公司 FinAssist 的技术负责人。一年前,你们推出了一个 AI 财务助手--起初很简单,只有 3 个工具:股票查询、新闻搜索、持仓查看。那时候 Agent 响应迅速、选工具精准、用户好评如潮。

但成功的代价是需求的膨胀。产品经理每月都会塞进来新功能:风险评估、税务计算、汇率换换、合规检查、情感分析、财报解读、策略回测、智能提醒、账单解析、信用卡推荐......到现在,你的单个 Agent 已经挂载了 22 个工具。

问题随之而来:

  • 工具选择错误率飙升:用户问"帮我算一下卖出 AAPL 的税",Agent 却调用了"汇率换算"工具。测试数据显示,工具超过 15 个后,选择准确率从 94% 下降到 71%
  • 响应延迟翻倍:每次推理都要在 22 个工具描述中做选择,系统提示词膨胀到 6000+ tokens,仅工具定义就吃掉了上下文窗口的 15%
  • 维护噩梦:新增一个工具,全量回归测试要跑 80+ 个场景,因为新工具可能与现有任何一个工具产生语义冲突
  • 团队协作困难:股票组、风控组、合规组三个团队同时往同一个 system prompt 里加指令,互相覆盖、互相干扰

CTO 在周会上甩出一张架构图:"我觉得该拆了,搞成多个 Agent。但我听说多 Agent 系统的失败率很高......你怎么看?"

这正是 Agent 架构设计中最经典的抉择时刻--单 Agent 还是多 Agent?如果选多 Agent,选什么模式?如何避免常见的失败陷阱?

题目要求

作为技术负责人,你需要完成以下任务:

  3. 原型实现:使用 LangGraph 1.x 实现 Supervisor 模式的多 Agent 原型
  4. 风险评估:基于 MAST 失败分类法,识别 3 个最可能出现的失败模式并设计防御方案

这个任务模拟的是一个真实场景:你作为技术负责人,需要向 CTO 和产品团队证明架构决策的合理性。仅有代码是不够的--你还需要一份清晰的架构设计文档,说明为什么选择多 Agent(而非单 Agent 优化)、为什么选 Supervisor 模式(而非 Swarm 或 Pipeline)、预期收益和风险各是什么。这正是面试中"系统设计"题的核心考察点:不光看你能不能写出代码,更看你能不能讲清楚 why。

二、思路分析

这道题考察的不是"会不会写多 Agent 代码",而是架构判断力--在什么情况下从单 Agent 升级为多 Agent?选什么模式?如何避免翻车?这是 Agent 架构师最核心的能力之一。

2.1 从"一个顶所有"到"术业有专攻"--单Agent天花板效应

要理解为什么单 Agent 会遇到天花板,我们首先需要看清 LLM 在每次推理时实际发生了什么。当你给 Agent 挂载了 22 个工具时,每一次用户提问,LLM 都要执行以下认知操作:

读取所有工具描述 22 个工具 × 平均 80 tokens 描述 = ~1760 tokens 的工具定义。这些 tokens 在每次推理时都会被发送给模型,无论用户问的是"今天天气"还是"帮我做风险对冲"。
语义匹配与排序 LLM 需要在 22 个工具的描述中找到与当前请求最匹配的那一个。这本质上是一个"注意力分配"问题--Transformer 的注意力机制需要在大量工具描述之间分配注意力权重。
解析参数 Schema 每个工具的 JSON Schema 参数定义(参数名、类型、描述、是否必填)也在消耗上下文空间和注意力。
抑制干扰工具 最关键的一步--LLM 需要主动"忽略"那些看起来相关但实际上不该调用的工具。工具越多,相似度越高,抑制难度越大。

这就是为什么工具数量超过某个阈值后,工具选择准确率会急剧下降。LangChain 和多个研究团队的实验数据一致指向一个经验值:约 15 个工具是单 Agent 的实际工作极限。

但这并不意味着"15"是一个物理常数。它受到多个因素的影响:

工具描述质量 描述越清晰、区分度越高,天花板越高。好描述可以把天花板推到 18-20 个。差描述可能 10 个就开始混乱。
工具语义距离 22 个完全不同领域的工具比 22 个相似领域的工具更容易区分。"股票查询"和"K线分析"的混淆概率远高于"股票查询"和"账单解析"。
模型能力 更强的模型(如 deepseek-v4.1-flash)注意力分配能力更强,可以处理更多工具。但即使是最强的模型,超过 20 个工具后也会出现明显退化。
工具分组与Reranking 通过先对工具分组、再在组内做精排的二级选择策略,可以有效突破天花板。这正是从单 Agent 走向多 Agent 的渐进路径。

所以"15 个工具天花板"更像是一个架构预警信号,而非硬性限制。当你发现 Agent 的工具选择准确率持续下降、维护成本持续上升、团队协作开始互相干扰时--不管工具数量是 12 还是 22--都是时候认真考虑架构拆分了。

除了工具选择准确率,单 Agent 天花板还体现在另外两个容易被忽视的维度上。第一个是系统提示词战争:当多个领域的指令共享一个 system prompt 时,它们会互相竞争注意力权重。比如风控组要求"所有建议必须附带风险提示",而行情组要求"回答简洁直接"--这两条指令在语义上就是矛盾的,LLM 只能选择一个优先遵循。第二个是Few-shot 示例膨胀:好的工具使用示例可以大幅提升准确率,但 22 个工具的示例本身就是数千 token 的额外开销。在多 Agent 架构中,每个子 Agent 只需要加载自己领域的示例,示例质量和数量都可以提升而不必担心膨胀。

⚠️ 常见误判:"只要模型够强,工具多少都不是问题"

这是面试和架构评审中最常见的错误观点。事实上,即使是最强的模型(如 deepseek-v4.1-flash 的 128K 上下文窗口),注意力分散的问题依然存在。论文《Lost in the Middle》(Liu et al., 2023)已经证明,LLM 对位于上下文中部的信息利用率显著低于首尾位置。22 个工具的定义占据了大量上下文空间,即使模型"看到"了所有工具描述,也未必能有效利用中间位置的工具。这也是为什么减少每个 Agent 的工具数量比单纯增强模型能力更有效--注意力集中比窗口大小更重要。

2.2 多Agent架构四大模式--LangChain 分类法

LangChain 在 2025 年的多 Agent 架构指南中,将多 Agent 模式归纳为四种基础模式。这不是唯一的分类方法(微软 Azure 架构中心有不同的命名),但它是目前业界接受度最高的分类框架。

这四种模式各有适用场景,理解它们的差异是做出正确架构选择的基础:

Subagents(子代理模式)是多 Agent 系统中最常见的模式。一个 Supervisor Agent 维护完整的对话上下文,将具体任务通过工具调用的方式委派给无状态的子 Agent。每个子 Agent 有自己独立的工具集和系统提示词,完成工作后将结果返回给 Supervisor。这个模式的优势在于强上下文隔离--每个子 Agent 只看到与它专业相关的信息,不会被其他领域的噪音干扰。但代价是每次委派都增加一次 LLM 调用(Supervisor 调用一次,子 Agent 调用一次),因此延迟和 Token 消耗都会增加。

Skills(技能模式)是一个有趣的"伪多 Agent"方案。技术上它只使用一个 Agent,但这个 Agent 可以按需加载不同的"技能包"--每个技能包含专门的提示词、知识库和工具集合。当用户问编程问题时加载编程技能,问分析问题时切换到分析技能。这种模式的通信开销为零(因为只有一个 Agent),但随着技能累积,对话历史可能膨胀。它最适合"一个大脑、多种才能"的场景。

Handoffs(交接模式)更像是一个接力赛。当前活跃的 Agent 根据对话上下文判断"这个问题不该我处理",然后通过 handoff 工具把控制权交给更合适的 Agent。与 Subagents 不同的是,Handoff 不是"委托后等结果",而是"完全移交控制权"。这种模式在客服流程中特别有用--先由信息收集 Agent 了解用户问题,然后交给技术支持 Agent 解决,最后交给满意度回访 Agent 收尾。

Router(路由模式)是唯一原生支持并行处理的模式。Router 首先对输入进行分类,然后将任务同时分发给多个专门的 Agent 并行处理,最后将所有结果综合为最终答案。当你需要同时查询多个独立领域的信息时(比如"对比 AAPL 和 TSLA 的技术面和基本面"),Router 可以让行情 Agent 和分析 Agent 同时工作,大幅减少响应时间。Router 的技术实现通常是在 Supervisor 中使用一个轻量级分类器(甚至可以是基于规则的关键词匹配而非 LLM),先判断输入属于哪些领域,然后并行分发任务。这种"先分类后并行"的策略在多领域问答场景中特别有效。

理解了四种模式之后,一个自然的问题是:能否混合使用多种模式?答案是肯定的,而且生产环境中混合使用才是常态。例如,一个系统可以对外使用 Router 模式做并行分发,对内每个子 Agent 使用 Skills 模式按需加载专业能力。或者一个客服系统在前期使用 Handoff 模式收集信息,到需要多维度分析时切换为 Subagents 模式并行处理。模式选择不是非此即彼的,关键是理解每种模式的优势和代价,然后根据场景需求进行组合。

2.3 五种生产级编排拓扑--从学术到工程

上面的四种模式是概念层面的分类。在生产环境中,这些概念落地为五种具体的编排拓扑结构。微软 Azure 架构中心和多个生产部署团队的经验总结如下:

编排拓扑 控制方式 核心优势 主要风险 生产采用率
Orchestrator-Worker 集中(fan-out / fan-in) 易调试、水平扩展、错误恢复 编排器单点故障 + 吞吐瓶颈 ⬤⬤⬤⬤⬤ (最高)
Pipeline 顺序阶段处理 简单可审计、流程清晰 无并行能力、串行延迟 ⬤⬤⬤⬤ (高)
Hierarchical 树状委派 清晰的职责层级 层间延迟累积、过度分解 ⬤⬤⬤ (中)
Handoff 状态驱动转换 低延迟直接通信 状态管理复杂 ⬤⬤⬤ (中)
Swarm 去中心化涌现 大规模并行探索 可观测性差、收敛困难 ⬤ (低·多见于研究)

一个关键的工程洞察:生产部署中绝大多数使用 Orchestrator-Worker 模式。Dev.to 的调研文章指出:"The pattern we see across production deployments is consistent: the overwhelming majority implement the hub-and-spoke orchestrator-worker model, not the complex swarm architectures that dominate academic papers."(生产部署的模式高度一致:绝大多数实现了 hub-and-spoke 的编排器-工作者模型,而非学术论文中主导的复杂 swarm 架构。)

这不是巧合。Orchestrator-Worker 模式有四个关键工程优势:

可调试性 所有任务流经一个编排器,日志集中在一条链路上。出了问题,你只需要看编排器的 Trace 就能定位。
错误恢复 编排器可以在某个 Worker 失败时重试、降级或切换到备用 Worker。这种集中式的错误处理比分布式协调简单一个数量级。
水平扩展 Worker 是无状态的,可以根据负载水平扩展。编排器本身可以用 LLM 也可以用规则引擎实现。
渐进迁移 从单 Agent 迁移到 Orchestrator-Worker 时,可以先把现有 Agent 作为第一个 Worker,然后逐步拆分出新 Worker。

但 Orchestrator-Worker 也有明确的瓶颈。如果编排器本身使用 LLM 做路由决策,每次路由都需要一次 LLM 调用(通常 2-5 秒)。假设有 20 个 Worker 等待分配任务,编排器的分解吞吐上限约为 6.7 tasks/s。对于高吞吐场景,需要用规则引擎替代 LLM 编排器,或者引入多级编排器(如树状结构,每个子编排器管理一组 Worker),将路由决策分散化。多级编排器是 Hierarchical 拓扑的核心思想--但层级的引入也意味着延迟累积(每增加一层编排器增加 1-3 秒延迟),需要在响应速度和系统可扩展性之间权衡。

Swarm 模式虽然在生产中采用率最低,但它在特定场景中有不可替代的优势。当你需要大规模并行探索--比如对 100 家公司同时做尽职调查--Swarm 可以让每个 Agent 独立工作、相互不依赖。关键挑战是收敛:如何把这些 Agent 的发现聚合为有意义的结论?实践中通常需要一个专门的"聚合 Agent"来收集和综合所有 Worker 的发现,或者引入投票机制(多个 Agent 对同一问题独立给出结论,取多数共识)。AWorld 框架就是这种思路的典型代表--它在 6 小时内构建的多 Agent 系统成功解决了 2025 年 IMO 6 道题中的 5 道,证明了 Swarm + 投票模式在复杂推理任务上的潜力。

Pipeline 模式虽然概念简单,但在特定垂直场景中却是最优选择。以法律合同审查为例:文档解析→条款提取→风险识别→合规检查→报告生成,每个阶段有明确的输入输出契约,前一步的输出是后一步的唯一输入。这种严格顺序、无分支、无并行的特征使得 Pipeline 模式比 Orchestrator-Worker 更合适--不需要编排器做路由决策,减少了不必要的 LLM 调用。Pipeline 的另一个优势是天然可审计:每个阶段的中间结果都可以持久化,形成完整的处理链路,满足合规要求。在生产实践中,Pipeline 模式常用于文档处理、数据清洗、内容审核等流程化任务,是"最朴素但最可靠"的多 Agent 模式。

Hierarchical 模式则适用于组织结构复杂、任务嵌套层级深的场景。一个典型的生产案例:某大型银行的智能投顾系统采用了三层结构——顶层是总控编排器(接收用户请求,判断属于“理财咨询”“贷款审批”“合规审查”中的哪个业务线);第二层是各业务线的领域编排器(如理财线编排器负责任务分解,决定需要调用行情查询、风险评估还是产品推荐);第三层是具体的工作 Agent(如行情查询 Agent、风险计量 Agent、合同生成 Agent)。这种三级结构在实践中是必要的:该银行有 15 个以上的工作 Agent,如果全部挂在单个编排器下,路由准确率会显著下降;而引入中间层后,每个领域编排器只需管理 3-5 个工作 Agent,路由准确率保持在 90% 以上。代价是延迟累积——三层串行调用总延迟约 5-9 秒,对于非实时场景(如投资报告生成)可以接受,但对实时聊天场景则偏慢。微软 Azure 架构中心建议:当 Agent 数量超过 10 个时,应考虑引入层级化分组,避免单个编排器成为瓶颈。不过层级也不宜过深——实践经验表明,超过 3 层的层级结构会因延迟累积和上下文传递损耗而导致用户体验严重下降。

2.4 何时分解--六大信号与决策框架

知道了有哪些多 Agent 模式,下一个问题是:什么时候该从单 Agent 升级到多 Agent?过早拆分是"premature multi-agentization"(过早多 Agent 化),增加复杂性却没有收益;过晚拆分则让系统在瓶颈中挣扎。

综合 LangChain 指南、微软 Azure 架构建议和生产团队的经验,我们提炼出六大分解信号:

除了决策树中的四个核心问题,还有两个经常被忽略但同样重要的信号:

信号5:安全与合规边界。如果你的 Agent 同时处理需要不同权限级别的操作(比如查询公开行情 vs 执行交易指令),将它们拆分为不同安全级别的 Agent 可以实现更精确的权限控制。微软的多 Agent 决策指南明确指出:如果用例跨越安全和合规边界,应该直接从多 Agent 系统开始。

信号6:独立扩展需求。当某些功能模块的调用量远高于其他模块时(如"股票查询"日均 1200 次而"合规检查"只有 50 次),多 Agent 允许你只对高频模块增加计算资源,而不必扩展整个系统。这类似于微服务架构的核心思想--将不同负载特征的功能拆分为独立服务,按需伸缩。在 FinAssist 的案例中,行情 Agent 可以部署 5 个副本应对高峰流量,而合规 Agent 只需要 1 个副本--这在单 Agent 架构中是做不到的。

综合六个信号,我们可以总结出一个简单的二分决策规则:

  • 0-1 个信号:保持单 Agent,通过优化工具描述、引入分组/Reranking 策略来解决当前问题。这是最低风险的选项。
  • 2-3 个信号:建议拆分,首选 Orchestrator-Worker 模式。可以先从 Skills 分组开始验证拆分效果,再逐步迁移到 Subagents。
  • 4+ 个信号:必须拆分,且应考虑混合模式(如 Router + Subagents)。拆分越早越好,技术债务会随时间指数增长。
  • 跨越安全/合规边界:无论信号数量多少,直接使用多 Agent。安全边界的隔离需求优先于架构简化诉求。

💡 黄金法则

当你在纠结"该不该拆"时,先用 Skills 模式(技能分组)作为中间步骤--它不需要引入多 Agent 的复杂性,但可以验证"按领域拆分"是否真的能提升工具选择准确率。如果 Skills 模式验证有效,再升级为 Subagents 模式实现真正的隔离。这是一个低风险的渐进迁移路径。

2.5 通信开销--多Agent的隐性税

多 Agent 系统的通信开销是一把隐形利刃--它不会在架构图中显示出来,却能在生产环境中持续蚕食你的利润率和用户体验。理解通信开销的量级和构成,是做出合理的多 Agent 架构决策的前提。很多团队在上线后才发现实际成本是预期的 2-3 倍,根本原因就是低估了通信开销。

多 Agent 不是免费午餐。每增加一个 Agent 节点,就增加一条通信链路,而每条通信链路都意味着额外的 Token 消耗和延迟。理解通信开销的量级,是做出合理架构决策的前提。

我们来看单 Agent 和多 Agent 在处理同一个请求时的 Token 消耗对比。单 Agent 方案中,用户输入约 50 token,系统提示词约 200 token,22 个工具定义约 1760 token,LLM 推理输出约 100 token,总计约 2110 token,只需 1 次 LLM 调用。而多 Agent(Supervisor)方案中:用户输入约 50 token,Supervisor 提示词加子 Agent 描述约 450 token,路由决策约 30 token,委派给子 Agent 后子 Agent 提示词约 150 token 加 5 个工具定义约 400 token,推理加工具调用约 200 token,结果回传加 Supervisor 综合约 150 token,总计约 1430 token--Token 总量反而更低!但代价是需要 2 次 LLM 调用,延迟翻倍(×1.8-2.2)。

这个对比揭示了一个反直觉的事实:多 Agent 的 Token 总量不一定比单 Agent 高。因为每个子 Agent 只加载自己领域的工具定义(5 个工具 ~400 tokens vs 22 个工具 ~1760 tokens),实际上节省了大量"无关工具的描述 Token"。但多 Agent 的实际成本更高,因为:

  1. LLM 调用次数翻倍:Supervisor 路由一次,子 Agent 执行一次,如果是多轮对话 Supervisor 还需要综合结果--一个请求可能触发 2-3 次 LLM 调用
  2. 延迟累积:每次 LLM 调用 1-3 秒,两次串行调用就是 2-6 秒。对于延迟敏感场景这是不可接受的
  3. 上下文传递损耗:Supervisor 需要把用户请求"翻译"成子 Agent 能理解的格式,子 Agent 的结果又需要"翻译"成用户能理解的回答。每次翻译都可能丢失信息

通信开销还有一个容易被忽视的维度:上下文窗口竞争。在 Supervisor 模式中,Supervisor 需要维护完整的对话历史,同时还要加载所有子 Agent 的描述。随着对话轮数增加,对话历史不断膨胀,可能挤占子 Agent 描述的空间。当上下文窗口逼近上限时,Supervisor 可能被迫截断早期的对话历史,导致上下文丢失。这恰恰会触发 MAST 分类中的"上下文丢失"失败模式。生产环境中的最佳实践是:为 Supervisor 设置对话历史压缩策略(如每 10 轮对话做一次摘要),并为每个子 Agent 设置独立的上文窗口(子 Agent 只看到与当前任务相关的上下文,而非全部历史),从而避免上下文窗口竞争问题。

另一个降低通信开销的有效策略是缓存子 Agent 的工具调用结果。在金融场景中,许多查询具有时效性但变化不频繁(如财报数据每季度才更新一次)。通过在 Supervisor 层引入短期缓存(如 Redis),对相同参数的工具调用直接返回缓存结果,可以避免重复的子 Agent 调用。实测数据显示,合理的缓存策略可以减少 30-45% 的子 Agent 调用次数,显著降低延迟和 Token 成本。但缓存必须设置合理的过期时间--行情价格等实时数据的缓存不应超过 30 秒,而财报数据的缓存可以持续到下一季度发布。

2.6 MAST失败分类法--多Agent翻车大全

如果你决定走多 Agent 路线,你必须了解多 Agent 系统的失败模式。NeurIPS 2025 的 Spotlight 论文 MAST(Multi-Agent System Failure Taxonomy)是首个经验驱动的多 Agent 失败分类法,分析了 7 个主流 MAS 框架上的 1600+ 条执行轨迹,标注一致性 Cohen's Kappa = 0.88(很高)。

核心发现令人警醒:多 Agent 系统的生产失败率在 41%-86.7% 之间,取决于框架和任务复杂度。

MAST 的数据告诉我们,超过一半的失败(53%)发生在 Agent 之间的交互环节,而不是单个 Agent 的能力不足。这意味着即使你用了最强的 LLM,如果 Agent 之间的通信协议设计不当,系统依然会失败。这个发现对架构设计有深远影响:提升多 Agent 系统的可靠性,投入产出比最高的方向不是"买更强的模型",而是"设计更好的 Agent 间通信协议和验证机制"。

一个经典的失败案例:ChatDev Wordle 实验。研究者让多个 Agent 协作开发一个 Wordle 猜词游戏。由于任务描述中"游戏规则"的表述存在歧义,不同的 Agent 对规则有不同的理解--负责逻辑的 Agent 实现了标准 Wordle 规则,而负责 UI 的 Agent 实现了变体规则。最终集成时游戏行为完全错乱。这就是典型的规约歧义导致的失败。

MAST 的发现中有一个反直觉的结论值得特别注意:失败率与 Agent 数量并非线性关系。增加 Agent 从 1 个到 3 个,失败率上升幅度可控(从 ~30% 到 ~45%);但从 3 个增加到 5 个时,失败率跳跃式上升(到 ~65%),因为 Agent 间的两两交互路径从 3 条暴增到 10 条。这意味着控制 Agent 数量是多 Agent 系统可靠性的最有效杠杆--能用 3 个 Agent 解决的问题,绝对不要用 5 个,这是多 Agent 架构设计的黄金法则。

针对每一种失败模式,我们可以制定具体的防御策略。以下四层防御体系覆盖了 MAST 的三大支柱:

  1. 规约层(防支柱1):为每个 Agent 编写精确的角色定义(Role)、任务边界(Scope)和输出格式(Format),使用 JSON Schema 约束通信格式,消除自然语言歧义。实践提示:在 YAML 配置文件中定义 Agent 规范,而不是用自然语言在 prompt 中描述。
  2. 通信层(防支柱2):引入消息确认机制(接收方必须回执"已收到并理解"),关键决策需要二次确认,设置通信超时和重试策略。特别是对于 Supervisor 模式,Supervisor 应该对子 Agent 的返回结果做基本的合理性检查(如字段完整性、数值范围)。
  3. 验证层(防支柱3):添加独立的质检 Agent 或规则引擎,对最终输出进行事实核查、数值合理性检查和格式验证。验证层应该是独立于生产链路的--它不参与结果生成,只参与结果审查。
  4. 可观测层(跨支柱):实现分布式 Tracing,记录每个 Agent 的输入、输出和决策过程,使问题可定位、可回溯。LangFuse 等开源工具提供了 Agent 调用链追踪能力。

ICLR 2025 的后续研究进一步细化为 18 种失败模式,归为四大类:规约歧义与错位、组织崩溃、Agent 间冲突与协调缺口、弱验证与质量控制。这些研究的核心启示是:多 Agent 系统的可靠性瓶颈不在单个 Agent 的智商,而在于 Agent 之间的"组织管理"。

📊 数据解读:这些数字在你的日常场景中意味着什么?

90.2% 提升幅度(Anthropic):这不是说多 Agent 比单 Agent 好 90%——它的意思是在研究类开放性问题中,多 Agent 的产出质量评分比单 Agent 高出约一倍。如果你的场景是 FAQ 客服,这个差距可能缩小到 5-10%;如果是多维度调研,差距可能更大。

42.68% vs 2.92%(Cornell):这个近 15 倍的差距来自极其复杂的规划任务基准。关键信号是:当任务需要 5 步以上的规划时,多 Agent 开始显著领先。低于 3 步的任务,单 Agent 通常已经够用。

实用判断法则:用“步骤数 × 领域数”估算复杂度。乘积 < 5,单 Agent 足够;乘积 5-15,考虑 Skills 分组;乘积 > 15,多 Agent 是更优选择。这不是精确公式,但能帮你快速建立直觉。

另一个值得关注的趋势是多 Agent 辩论(Jury)模式的兴起。受 Marvin Minsky《Society of Mind》理论启发,这种模式让多个 Agent 对同一问题独立给出答案,然后通过投票或辩论选出最佳结论。研究表明,即使是 3 个中等能力 Agent 的投票,其准确率也能超过单个高能力 Agent。这是一种用"广度"替代"深度"的策略--通过多样化的视角来弥补单个 Agent 的盲点。代价是 Token 消耗是单 Agent 的 N 倍(N = Agent 数量),因此适用于对准确率要求极高而对成本不敏感的场景(如医疗诊断、法律判断)。

2.8 框架选型指南--LangGraph vs CrewAI vs AutoGen

确定了架构模式后,下一个实际问题是选什么框架来实现。2025-2026 年主流的多 Agent 框架各有特色,选型不应只看功能列表,还要考虑团队技术栈、维护成本和学习曲线。

LangGraph 是目前生产环境采用率最高的多 Agent 框架。它的核心抽象是 StateGraph--一种有向图数据结构,节点代表 Agent 或处理逻辑,边代表数据流和控制流。LangGraph 1.x 的 create_agent API 让创建单个 Agent 变得简洁,而将多个 Agent 组合为图结构则提供了完整的控制力。它还内置了 Checkpointer(状态持久化)、Human-in-the-loop(人工介入)等生产级功能。缺点是学习曲线较陡,开发者需要理解图编程模型。

CrewAI 走的是"角色化抽象"路线。你不需要画图,而是定义角色(Agent)、任务(Task)和团队(Crew)。CrewAI 1.x 引入了 Flows 引擎,提供了更强大的编排能力,支持条件分支、错误处理和结构化输出。CrewAI 的代码量通常比 LangGraph 少 30-40%,适合快速原型开发和角色明确的场景。缺点是对底层数据流的控制不如 LangGraph 精细。

AutoGen(微软)是最灵活的框架,支持 Agent 间的自由对话和 human-in-the-loop。它在研究领域使用最广,因为可以快速实验各种协作模式。但生产部署的工具链(监控、部署、版本管理)不如前两个成熟。微软还推出了 Semantic Kernel,更适合 Azure 生态的企业应用。

对于 FinAssist 的场景,我们推荐 LangGraph,原因是:(1) 需要自定义验证层(可在图中插入验证节点);(2) 交易场景需要状态持久化和恢复(LangGraph 的 Checkpointer 原生支持);(3)合规要求意味着需要完整的审计追踪(图结构天然可追溯)。如果你只是想快速验证想法,可以先花半天用 CrewAI 做个原型,确认架构方向后再用 LangGraph 实现生产版本。这种"CrewAI 原型 → LangGraph 生产"的渐进策略在实践中被广泛采用。

框架选型的最终建议是:不要在第一天就选定一个框架并绑死。用 CrewAI 或扣子/百炼花半天做原型,验证架构方向;用 LangGraph 实现生产版本,享受精细控制力和生态丰富性;在 Agent 和外部工具之间始终插入一层 MCP 标准化接口,为未来框架迁移预留空间。这种"原型快验 + 生产精建 + 接口标准"的三层策略,是多 Agent 项目从 Demo 走向生产的最佳实践,也是在面试中展示架构成熟度的加分项。

三、参考答案

3.1 架构设计方案

基于上述分析,我们为 FinAssist 设计如下多 Agent 架构:

  • 编排模式:Orchestrator-Worker(Supervisor 模式)
  • Agent 划分:按业务领域分为 5 个专业 Agent
  • 通信协议:结构化 JSON 消息(防歧义)
  • 验证层:独立的结果验证 Agent + 超时降级机制
  • 模型选择:Supervisor 用 deepseek-v4.1-flash(需要更强推理),子 Agent 用 deepseek-v4.1-flash(够用且更经济)

这个架构方案体现了三个关键设计理念。首先是领域驱动划分:Agent 的边界不是随意画的,而是沿着业务领域的自然边界切分--行情、风控、交易、资讯、客服各自有独立的知识库、工具集和评估标准。其次是模型分层策略:不同 Agent 使用不同能力等级的模型,这是成本控制的核心手段。Supervisor 需要做意图理解和路由决策,这是高复杂度任务,用更强的模型;子 Agent 的任务更聚焦(5 个工具 vs 22 个),中等模型就能胜任。实践数据显示,这种分层策略可以降低 40-60% 的 Token 成本,同时保持甚至提升整体性能。最后是独立验证层:这是针对 MAST 支柱 3(任务验证失败占 21%)的直接防御措施。验证层不参与结果生成,只负责审查--格式是否完整、数值是否合理、结论是否有数据支撑。验证层的实现可以采用规则引擎和 LLM 相结合的方式:规则引擎负责格式检查和数值范围验证(快且确定性强),LLM 负责语义合理性检查(如"建议卖出所有持仓"这类异常建议)。这种双层验证机制能在不显著增加延迟的前提下拦截大部分错误输出。

基于 MAST 失败分类法的分析,我们需要为系统添加防御措施。以下是验证层和错误处理的实现:

3.4 CrewAI 对照实现(简化版)

作为对比,下面展示用 CrewAI 1.x 实现相同架构的代码。CrewAI 的哲学是"团队角色化"--每个 Agent 有明确的角色(Role)、目标(Goal)和背景故事(Backstory),更像在组建一个虚拟团队。

LangGraph vs CrewAI 对照

两个框架的核心差异在于抽象层次:

  • LangGraph更底层,你直接操作图节点和边,对数据流有完全控制。适合需要精细控制编排逻辑的场景
  • CrewAI更高层,你定义角色和任务,框架自动编排。适合快速原型和角色明确的团队协作场景
  • 对于 FinAssist 这种需要自定义验证层的场景,LangGraph 更合适--你可以精确地在编排流程中插入验证节点
  • 如果只是快速验证想法,CrewAI 的代码量大约少 40%。CrewAI 的 YAML 配置方式也更接近"声明式",便于非工程师参与设计
  • 两个框架并非互斥:可以用 CrewAI 做原型验证,确认架构方向后再用 LangGraph 重写生产版本。这种渐进策略在硅谷创业公司中非常普遍

3.5 关键设计决策回顾

本题架构设计要点

  1. 为什么选 Supervisor 模式而非 Swarm?因为 FinAssist 需要可审计的交易记录和明确的责任链。Supervisor 模式的集中控制特性使得每笔分析都可以追溯。
  2. 为什么 Supervisor 用 deepseek-v4.1-flash 而子 Agent 用 deepseek-v4.1-flash?模型分层策略--Supervisor 需要更强的意图理解和路由能力,而子 Agent 的任务更聚焦,中等模型就够用。这样可以降低 40-60% 的 Token 成本。
  3. 为什么添加独立验证层?MAST 数据显示 21% 的失败与验证缺失有关。一个轻量级的验证模块(即使只是字段检查和数值范围检查)就能拦截大量低级错误。
  4. 为什么用结构化 JSON 通信?MAST 支柱1(规约问题)占失败的 26%。结构化通信格式可以大幅减少 Agent 间的理解歧义。

四、举一反三

掌握了单 Agent vs 多 Agent 的架构选择框架后,以下三个变体题帮助你将这套思维模型应用到不同场景中。每个变体题聚焦不同的能力维度。这三个变体分别对应 Swarm、Handoff 和 Pipeline 三种编排拓扑,加上本题的 Supervisor 模式,你就完整覆盖了所有主流的多 Agent 架构模式。

变体题 A:研究聚合系统--Swarm 模式设计

学习目标:训练对去中心化协作模式的设计能力。与本题的 Supervisor(集中式)模式形成对照,理解何时该用集中控制、何时该让 Agent 自主涌现。

场景:你的公司需要构建一个竞争情报分析系统。每天早上,系统需要自动收集 20+ 家竞争对手的最新动态(产品发布、融资新闻、人事变动、专利申请、社交媒体舆情),并生成一份综合简报。

与原题的差异:

  • 任务从"交互式问答"变为"批量数据收集+综合"--更适合并行处理
  • 不需要实时响应(可以离线处理)--延迟不再是约束
  • 每个信息源的收集方式差异很大--Agent 需要更高的自主性
  • 信息量可能非常大--上下文管理更关键

考察的核心能力:并行调度设计 / 终止条件设计(Swarm 模式中最容易出问题的就是 Agent 无限循环--MAST 分类中的"循环依赖"失败模式)/ 结果聚合策略。提示:设计时必须定义明确的最大迭代次数、质量阈值和超时收敛机制,否则 Agent 可能陷入无限循环。

输入输出示例:

  • 输入:竞争对手列表 ["company_a", "company_b", ...],简报主题 "AI芯片行业"
  • 输出:结构化情报简报(JSON 格式,包含每家公司的动态摘要 + 行业趋势分析 + 关键预警)

变体题 B:多阶段客服--Handoff 模式实现

学习目标:训练对状态驱动转换的设计能力。Handoff 模式是多 Agent 系统中最难掌握的模式之一,因为它需要在保持对话连贯性的同时切换控制权。

场景:一家电商公司需要升级客服系统。当前流程是:用户先描述问题 → 信息收集 → 技术诊断 → 解决方案 → 满意度调查。每个阶段需要不同的专业能力和工具集。

与原题的差异:

  • Agent 之间是串行交接而非并行--前一个 Agent 的输出是后一个 Agent 的输入
  • 需要维护跨 Agent 的对话状态--用户不需要对每个新 Agent 重新描述问题
  • 有明确的终止条件(满意度达标或升级人工)--可以学习终止条件设计
  • Agent 切换时机需要自主判断--这是 Handoff 模式的核心挑战

考察的核心能力:状态传递设计 / Agent 切换条件定义 / 上下文连续性保障 / 对话历史压缩策略。提示:关键是设计一个 ConversationState 数据结构,包含用户画像、问题描述、已收集信息、处理进度等字段,每个 Agent 读取和更新这个共享状态而非维护独立的对话历史。

输入输出示例:

  • 输入:用户消息 "我昨天买的手机壳颜色不对,而且尺寸也偏小"
  • 输出:多阶段处理后的完整客服记录(信息收集Agent→退换货Agent→满意度Agent的交接日志 + 最终处理结果)

变体题 C:文档处理流水线--Pipeline 模式与工具数量优化

学习目标:训练对顺序编排和工具边界设计的能力。Pipeline 是最简单的多 Agent 模式,但"简单"不意味着"容易做对"--正确的阶段划分和工具分配需要深入思考。

场景:一家律所需要自动化处理合同审查流程。流程为:文档解析 → 条款提取 → 风险识别 → 合规检查 → 修改建议 → 报告生成。整个流程涉及 30+ 种工具(OCR、NLP、知识库查询、规则引擎等)。

与原题的差异:

  • 流程是严格顺序的--不需要并行或路由
  • 每个阶段的输入输出类型固定--可以严格定义数据契约
  • 工具数量更多(30+)--需要更精细的阶段划分
  • 对可审计性要求极高--每个决策都需要可追溯

考察的核心能力:Pipeline 阶段划分原则 / 阶段间数据契约设计 / 工具按阶段分配策略 / 可审计性实现。提示:阶段划分的核心原则是"每个阶段只做一件事",阶段间的数据契约用 Pydantic 模型定义。可审计性可以通过为每个阶段的输出附加元数据(时间戳、Agent名称、置信度)来实现,最终拼接为完整的审计日志。

输入输出示例:

  • 输入:PDF合同文件路径 "contracts/vendor_agreement_v3.pdf"
  • 输出:结构化审查报告(包含每个阶段的处理结果 + 风险等级 + 修改建议 + 完整审计日志)

💡 变体题练习建议

三个变体题分别对应并行模式(Swarm)、串行模式(Handoff)和流水线模式(Pipeline)--加上本题的 Supervisor 模式,你就完整覆盖了所有主流的多 Agent 编排拓扑。建议至少完成一个变体题的完整实现,包括架构设计文档和可运行的原型代码。完成全部三个变体后,你将具备在任何场景下选择和设计多 Agent 架构的系统性能力--这正是 Agent 架构师最核心的竞争力。

🔑 核心知识点回顾

  • 15工具天花板:单 Agent 工具超过 ~15 个后,选择准确率显著下降。但这不是硬限制--工具描述质量、语义距离和模型能力都会影响实际拐点
  • 四种基础模式:Subagents(集中编排)、Skills(渐进披露)、Handoffs(状态交接)、Router(并行调度)--LangChain 分类法
  • 五种生产拓扑:Orchestrator-Worker(最常用)、Pipeline、Hierarchical、Handoff、Swarm(多见于研究)
  • 六大分解信号:工具数量、领域多样性、并行需求、安全边界、团队结构、独立扩展--≥2 个信号即建议拆分
  • 通信开销:多 Agent 的 Token 总量不一定更高,但 LLM 调用次数翻倍,延迟 ×1.8-2.2,编排器吞吐上限 ~6.7 tasks/s
  • MAST 失败分类:3 大支柱 14 种模式--规约问题(26%)、Agent 间错位(53%)、任务验证(21%)。生产失败率 41-86.7%
  • 基准数据:多 Agent 在复杂任务上比单 Agent 高 90.2%(Anthropic),复杂规划任务 42.68% vs 2.92%(Cornell)
  • 渐进迁移路径:单 Agent → Skills 分组 → Subagents 隔离--低风险的分步升级策略
