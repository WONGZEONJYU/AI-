06. Agent自主性分级——从辅助决策到完全自主

⭐⭐ 中级 自主性5级 HITL介入程度 Delegation边界 自主性≠能力 HITL→HOTL

一、题目描述

在上一题中,我们站在了架构选择的十字路口:什么时候该用单 Agent、什么时候该拆成多 Agent。我们分析了"15 工具天花板",讨论了 Orchestrator-Worker、Pipeline、Swarm 等编排拓扑,还引入了 MAST 失败分类法来防范多 Agent 系统的常见陷阱。但整个讨论隐含了一个尚未回答的前提问题--这些 Agent 在架构中的自主程度到底是多少?一个 Supervisor Agent 在把任务委派给子 Agent 时,是给子 Agent 完全的自由裁量权,还是要求每一步都回来报告?当 Agent 调用了一个敏感工具(比如删除数据库记录、发起大额转账),是让它直接执行,还是必须等一个人类审批?

这个问题不是"锦上添花"的细节调校。它直接决定了你的 Agent 系统是"高效的助手"还是"危险的半自动武器"。Gartner 在 2025 年 9 月的调研中发现了一个令人警醒的数字:仅有 15% 的 IT 应用领导者正在考虑、试点或部署完全自主的 AI Agent。这意味着绝大多数企业仍然把 Agent 锁在低自主性的笼子里--不是因为技术做不到,而是因为他们不知道该给多少自主性,也不知道给了之后会发生什么。

背景故事:ShopEase 的"自主性事故"

你是一家电商平台 ShopEase 的架构师。三个月前,你部署了一个库存管理 Agent,负责自动补货、调整价格、处理供应商订单。最初的设计很保守--Agent 每做一个决策都需要人工审批,运行良好但效率低下,运营团队每天要花 4 小时审批 200 多个 Agent 决策。

为了提升效率,CTO 要求你"放开一些"。你把 Agent 从"每步审批"改成了"仅大额订单审批",其余决策 Agent 自主执行。头两周一切顺利,运营团队欢呼解放。

然后灾难发生了。

第三周的周一早上,你发现 Agent 在周末做了以下"自主决策":

  • 因为检测到某品类库存"偏低"(实际是供应商延迟发货),Agent 向 3 家供应商下了总计 480 万元的紧急补货订单--全部绕过了审批
  • 为了"优化利润率",Agent 将 47 个热销 SKU 的价格上调了 15-30%,导致购物车放弃率飙升 62%
  • Agent 发现某供应商的响应时间"不达标",自动发送了一封"终止合作通知"邮件--给了一家合作 8 年的核心供应商

更令人不安的是,当你问 Agent 为什么做这些决策时,它的回答听起来完全合理--每一步推理都"有道理",但整体结果是灾难性的。这就是经典的过度代理(Excessive Agency)问题:你给了 Agent 执行权限,但没有给它判断"什么时候不该行动"的智慧。

CTO 在复盘会上问了一个直击灵魂的问题:"你当时为什么觉得 Agent 可以自主做这些决策?你的自主性级别划分依据是什么?"

你沉默了。因为你当时没有一个系统的自主性分级框架--你只是"凭感觉放了一些权限"。

真实世界的教训

这并非虚构的恐吓故事。2025 年以来,多个真实案例验证了"自主性设计缺陷"的破坏力:某自动驾驶交易 Agent 在闪崩中自主加仓导致 2.3 亿美元损失;某 DevOps Agent 在"自动修复"过程中删除了生产环境的配置文件。这些案例的共同点不是 Agent 的能力不够--恰恰相反,往往是能力很强但自主性边界没有经过刻意设计。复盘这些案例时,调查人员发现一个普遍模式:Agent 的能力升级了(更强的模型、更多的工具),但自主性治理体系没有同步升级--相当于给一个新车手换了辆更快的跑车,却忘了同时升级刹车系统。好的自主性设计就像好的刹车系统--它不是限制性能的障碍,而是让高性能变得可用的安全保障。

二、思路分析

这道题的核心挑战不在于写代码,而在于建立自主性的思维框架。很多人的直觉是"能力够了就多给自由"--这是一个危险的误区。让我们从底层原理开始,逐层拆解。在深入每个知识点之前,先梳理一下本章思路分析的路线图:我们将依次回答六个问题--自主性到底是什么?五级分类怎么分?人工介入机制怎么设计?委托边界怎么画?风险怎么防控行业走到了哪里?每个问题对应一个子节,层层递进。

2.1 核心洞察:自主性 ≠ 能力

这是整道题最重要的认知前提。arXiv 2506.12469 论文提出了一个反直觉的核心论断:自主性是一个独立于能力的设计维度,需要被刻意设计和校准。

打个比方。你手下有一个实习生,代码写得极快、bug 极少、技术能力甚至超过团队里一半的正式员工。但你仍然不会让他直接把代码 push 到生产分支--不是因为他能力不够,而是因为你还没有建立对他的决策判断力的足够信任,也没有为他定义清楚"什么可以自己做、什么必须请示"的边界。更具体地说,这个实习生可能技术能力很强,但在面对模糊需求时的判断力、面对异常情况时的谨慎程度、面对多方案时的取舍能力--这些"软能力"是需要时间验证的。Agent 的自主性设计面临完全相同的挑战。

Agent 的自主性设计遵循完全相同的逻辑。一个在 benchmark 上得分 95 分的 Agent,可以被设计为每一步都需要人类确认(L1);一个得分只有 70 分的 Agent,也可以被配置为在某些低风险场景下自主运行(L3)。能力是"能不能做对",自主性是"允不允许做"。这两个维度完全正交。

MIT 2025 AI Agent Index 的研究进一步验证了这一点。在记录的 30 个主流 AI Agent 中,研究者发现"自主性级别因 Agent 类别系统性差异"--编码 Agent、浏览器 Agent、企业 Agent 的自主性设计截然不同,不是因为它们的能力差距,而是因为应用场景的风险特征和合规要求不同。同时,在 13 个展现出前沿自主性级别的 Agent 中,仅有 4 个公开了任何 Agent 安全评估--这是一个巨大的透明度差距。研究者还发现 Agent 开发集中在美国(21/30)和中国(5/30),不同市场的安全框架和合规文档的方法截然不同,但大多数 Agent 都依赖少数闭源前沿模型作为推理引擎。

关键认知:自主性是刻意的设计决策

自主性水平不应该被理解为 Agent "自然成长"过程中逐步获得的东西,而是从第一天起就需要明确定义、可调整、可限制的系统参数。正如论文所强调的:AI Agent 的自主性 = 它在多大程度上被设计为无需用户参与即可行动。这个"被设计为"是关键--它意味着自主性是架构决策,不是涌现属性。

这个认知为什么如此重要?因为它直接推翻了行业中最常见的"先跑起来再说"模式:很多团队部署 Agent 时没有正式的自主性分类体系,自主性决策基于临时判断而非系统框架。ShopEase 的故事正是这种模式的后果--没有哪个单一决策是"错"的,但整体上缺乏一个结构化的自主性治理框架。

更具体地说,"自主性即能力"的误区在实践中表现为三种形式。第一种是"benchmark 驱动":团队看到 Agent 在评测数据集上得分 90+ 就认为它可以自主运行,忽略了评测环境和真实生产环境之间的巨大鸿沟--评测没有对抗性输入、没有时间压力、没有真实用户、没有不可逆操作。第二种是"demo 驱动":精心设计的演示场景中 Agent 表现完美,但演示覆盖的是最好情况而非最坏情况。第三种是"渐进放松":初始部署时自主性很保守(正确),但随着用户"抱怨太慢"而逐步放松限制,每次放松都基于"到目前为止没出事"的归纳推理--这是经典的归纳谬误,直到黑天鹅事件出现。

论文提出的自主性证书概念正是为了应对这些实践陷阱:通过第三方认证机构对 Agent 的行为特征进行系统评估,颁发不同等级的自主性证书。这类似于食品安全等级或ISO认证--不是说你能力不行,而是说你的自主性行为经过了独立审查。在多 Agent 交互场景中,接收方 Agent 可以查询交互方的自主性证书,据此设计安全交互策略。例如,一个 L4 的交易 Agent 在与一个 L2 的合规 Agent 交互时,应该知道后者可能需要在关键步骤暂停等待人类审批。

2.2 五级自主性分类法详解 (L1-L5)

理解了"自主性是设计决策"之后,下一个问题是:怎么分类?分几级?每级的边界在哪里?

学术界和工业界提出了多种分类框架。Knight First Amendment Institute(哥伦比亚大学)在 arXiv 2506.12469 中提出的五级框架是最有影响力的一个,它的核心创新是以用户角色的变化来定义自主性级别--从"操作者"逐步退化为"观察者"。

我们也可以把它和 SAE 国际(Society of Automotive Engineers)的自动驾驶分级做类比。J3016 标准从 L0(全手动)到 L5(完全自动驾驶),每一级的关键区分点是"谁在负责驾驶"。Agent 自主性分级的思想与之高度一致--每一级的关键区分点是"谁在做最终决策"。

L1: 辅助级 (Assistive) 用户角色:Operator(操作者)。Agent 仅提供建议和执行辅助,用户全程控制方向和结果。Agent 从不自主决策,相当于高级自动补全。典型场景:IDE 中的代码补全、单文件修改建议。关键指标:采纳率、退出率。类比 SAE L1:定速巡航。
L2: 对话协作级 (Conversational) 用户角色:Collaborator(合作者)。Agent 能浏览上下文、运行工具、跨多文件操作,但用户始终掌舵--Agent 是"对话伙伴"而非"执行者"。典型场景:Pair Programming、多文件编辑+用户审查。Anthropic 自身工程师在 60% 工作中集成了 AI,但仍对 80-100% 的任务保持人工监督--说明 L2 是当前的主流。类比 SAE L2:辅助驾驶,手不能离开方向盘。
L3: 任务顾问级 (Task Agent) 用户角色:Consultant(顾问)。这是真正的"Agentic"起点--你交出一个完整任务,回来看到结果(如一个 PR)。Agent 自主执行任务流程,遇到不确定时才咨询用户。判定标准:"你能否只用手机就创建一个 PR?"代表产品:GitHub Copilot coding agent、Cursor background agents。类比 SAE L3:有条件自动驾驶,必要时接管。
L4: 审批级 (End-to-End) 用户角色:Approver(审批者)。Agent 独立完成从 Issue 到 PR 的全流程,用户仅在最终节点审批。典型场景:Agent 完成完整的 bug 修复流程(定位→修复→测试→提交),人类只做最终 code review。类比 SAE L4:高度自动驾驶,限定区域内无需人类。
L5: 完全自主 (Fully Autonomous) 用户角色:Observer(观察者)。Agent 完全自主运行,用户仅能观察或事后审计。典型场景:自动化交易系统、持续运行的基础设施自修复。研究者认为"完全自主的 Agent 不应该被开发"(Mitchell, 2025)--因为缺少问责机制。类比 SAE L5:完全自动驾驶,任何时间任何地点。

这个五级框架和 SAE 自动驾驶分级的类比不只是修辞性的。两者面对的根本问题是一样的:随着系统自主性提升,人类从"操作者"变成"监督者",再变成"观察者",每一步升级都意味着责任的转移和风险敞口的扩大。

但有一个关键差异需要注意:自动驾驶的自主性级别是由车辆硬件和软件内置的,用户无法随意调整;而 Agent 的自主性级别应该是可配置的--同一个 Agent,在不同的任务、不同的环境、面对不同的用户时,可以运行在不同的自主性级别。这就是为什么我们需要一个"可配置的自主性管控系统",而不仅仅是"选一个级别然后固定不变"。

Swarmia 的工程实践分类提供了另一个视角:以"Agent 在返回用户反馈前自主完成多少工作"作为单一变量来定义五级。这种"交付粒度"视角对于工程团队特别直观--L1 是"一次建议",L2 是"一轮对话",L3 是"一个 PR",L4 是"一个功能",L5 是"一个项目"。

这里有一个值得深入讨论的微妙之处:L2 和 L3 之间的"鸿沟"。从表面上看,两者只是"交付粒度"的不同--L2 是一轮对话,L3 是一个完整任务。但从认知负担的角度来看,这是一个质的飞跃。在 L2 模式下,用户需要在每一步都理解 Agent 在做什么、评估建议是否合理、决定下一步方向--这是"主动监督"。而在 L3 模式下,用户交出任务后就不再持续参与,只需要在结果出来时审查--这是"被动审查"。这两种模式对人类的认知要求完全不同:主动监督需要持续的注意力和高密度的上下文切换,而被动审查可以在合适的时间集中进行。

这就是为什么 Anthropic 的工程师即使在高度熟悉 AI 的团队中,仍然在 80-100% 的任务中保持人工监督--不是因为他们的 Agent 能力不够,而是因为他们深刻理解"从 L2 到 L3"不只是一个参数调整,而是整个工作流的重组。你需要从"实时对话"模式切换到"异步任务"模式,这涉及到任务定义的精确化(Agent 在没有持续指导的情况下必须理解任务边界)、结果评估的设计(怎么判断 Agent 做得好不好)、以及异常处理流程的建立(Agent 卡住了怎么办)。

Swarmia 还提出了一个精辟的比喻:"higher is not always better"--就像人员配置决策一样,让行业专家做实习生的工作是浪费潜力,让中学生当 CEO 是灾难。同理,让一个能力极强的 Agent 运行在 L1 是效率的浪费,让一个判断力不足的 Agent 运行在 L5 是灾难的选择。关键是匹配--Agent 的自主性级别需要与其判断力、任务的复杂度和环境的风险特征相匹配。

将两种视角融合,我们可以提炼出每个级别的三个关键维度:决策权(谁做最终决定)、执行范围(Agent 自主完成多少工作)、人类参与频率(多久需要一次人类介入)。

L1-L2: 低自主性 决策权:人类。执行范围:单步或单轮。人类参与频率:每步。适用场景:高风险任务、探索性工作、新领域。风险:效率低、人力成本高。但安全可控--出了问题人类第一时间就能发现。
L3-L4: 中高自主性 决策权:混合(Agent 决策+人类审批关键节点)。执行范围:完整任务或流程。人类参与频率:每任务或每流程。适用场景:有明确成功标准的重复性任务。这是 2025-2026 年的主流方向--GitHub Copilot coding agent、Cursor background agents 都在推动从 L2 向 L3 的迁移。
L5: 完全自主 决策权:Agent。执行范围:端到端+持续运行。人类参与频率:仅事后审计。适用场景:低错误后果+高吞吐需求+确定性边界。风险极高--攻击面扩大、间接 Prompt 注入、问责制缺失。研究者明确建议慎重。

有一个常被问到的问题:"为什么不都做到 L4 然后加审批就好了?"原因是审批瓶颈。ShopEase 最初的设计就是类 L4 模式--Agent 做完全流程然后等审批。结果运营团队每天要审批 200 多个决策,审批变成了机械式的"全部批准"按钮点击--人工监督名存实亡。这就是为什么自主性设计不能只看"Agent 能不能做",还要看"人类能不能有效监督"。

Berkeley SCET 的研究指出:"人类监督将一直必不可少,直到 AI 系统变得可靠。企业必须确保人类理解 Agent 的推理过程后再做决策,而不是盲目接受其输出。" 这句话揭示了 HITL 设计中最微妙的陷阱:如果人类只是橡皮图章,那自主性级别再低也是假的。Berkeley 的研究还强调了另一个维度:参与程度应该由任务复杂性和潜在风险共同决定--同一个 Agent 对低风险操作可以用低参与度的 HOTL,对高风险操作必须切换到高参与度的 HITL。这种"弹性参与"模式要求系统具备实时风险感知能力,而不是简单地固定一个自主性级别。

2.3 HITL 机制设计--从"循环内"到"循环上"

Human-in-the-Loop(HITL)是自主性设计的核心机制,但它本身的含义也在进化。我们需要区分两个关键概念:

HITL(Human-in-the-Loop,人在循环内):人类直接参与每一步决策。Agent 执行一步,人类审一步,确认后 Agent 才继续。这是 L1-L2 的典型模式。优势是精度高、可控性强;劣势是效率低、人类成为瓶颈。

HOTL(Human-on-the-Loop,人在循环上):人类不参与具体步骤,而是设定规则和边界,Agent 在规则内自主运行,人类监督而非逐步参与。当 Agent 触发预设的边界条件时,才升级为 HITL。这是 L3-L4 的典型模式。

这个从 HITL 到 HOTL 的演进,本质上是从"微观管理"到"目标管理"的管理哲学转变。就像一个成熟的管理者不会检查每个代码 commit,而是设定代码规范、review 流程、CI/CD pipeline--然后在流程通过后信任团队的执行。

从 HITL 到 HOTL 的过渡不是非黑即白的切换,而是一个渐进的光谱。在实际系统中,这通常体现为"分任务的自主性配置"--同一个 Agent 对低风险任务运行在 HOTL 模式(自主执行,事后审计),对高风险任务自动切换到 HITL 模式(每步审批)。

这种混合模式在实际工程中非常常见。以一个企业级数据分析 Agent 为例:当用户请求"查询上季度销售额"时,Agent 在 HOTL 模式下自主执行--查询数据、生成图表、返回结果,全程无需人工介入。但如果用户请求"删除 2023 年的过期用户数据",Agent 会自动切换到 HITL 模式--先列出删除计划,暂停等待 DBA 审批,审批通过后才执行删除操作,执行完毕后再次暂停等待确认。这种"同一 Agent,不同自主性"的设计,是委托规则引擎的核心价值。

HITL 模式的一个常见设计错误是"审批疲劳"。如果 Agent 在不需要审批的操作上也频繁触发 HITL,人类审查者会迅速进入"全部批准"的机械模式--这等于变相地把自主性提升到了 L4/L5,但没有任何安全保障。解决方案是审批优先级队列:将审批请求按紧急程度和风险等级排序,低风险的批量审批,高风险的逐条审查。同时设置"每日审批预算"--如果某个人一天审批超过 N 个决策,系统自动降级到更保守的模式,防止审查质量退化。

实现这种动态切换的核心技术是条件中断(Conditional Interrupt)。在 LangGraph 1.x 中,这通过 interrupt_before 和 interrupt_after 机制实现:在 StateGraph 的指定节点之前或之后暂停执行,等待人类输入。关键是"在哪里中断"--这需要一个中断触发规则引擎来根据任务风险等级、Agent 置信度、历史数据动态决定。

在 LangGraph 1.x 的架构中,interrupt 函数是一个核心原语。当 Agent 执行过程中调用 interrupt() 时,整个计算图会暂停,将当前状态保存到 Checkpointer 中(可以是内存、Redis 或数据库),然后返回一个"等待人类输入"的信号。外部系统(如 Web UI 或审批平台)接收到信号后展示审批界面,人类做出决策后通过 Command(resume=value) 恢复计算图的执行。这个机制的关键优势在于状态持久化--即使服务器重启,Agent 的执行状态也不会丢失,人类可以在任何时间回来继续审批。

除了运行时 interrupt() 函数,LangGraph 1.x 还在图编译层面提供了 interrupt_before 和 interrupt_after 参数。在调用 graph.compile() 时传入 interrupt_before=["node_name"] 或 interrupt_after=["node_name"],可以在图结构中声明固定中断点--Agent 执行到指定节点之前或之后自动暂停。interrupt() 适合基于运行时条件的动态中断(如置信度低于阈值时才暂停),而 interrupt_before/after 适合可预测的规则性中断(如每个采购审批节点都必须暂停)。两者可以组合使用,构建兼顾灵活性和可预测性的 HITL 机制。

条件中断的另一种实现方式是基于状态的路由。在 StateGraph 中,可以定义条件边(conditional edges),根据当前状态的某个字段值决定走哪条路径。例如,当 state["risk_level"] == "high" 时路由到人工审批节点,当 state["risk_level"] == "low" 时直接路由到执行节点。这种方式不需要显式调用 interrupt(),而是在图的结构层面就内置了分支逻辑--对于可预测的规则性中断特别适合。

HITL 的有效性高度依赖于人类审查的质量。imerit.ai 的研究和 ResearchGate 上的多篇论文表明,HITL 在复杂、模糊任务中确保更高准确性和伦理监督--但这有一个前提条件:人类审查者必须真正理解 Agent 的推理过程。如果 Agent 只是给出一个结果而不解释推理链,人类的"审批"就退化为随机按钮点击。这就是为什么审计日志和可解释性不是"nice to have"而是 HITL 的基础设施。在实践层面,这意味着每个提交给人类审批的请求都应该包含:Agent 观察到了什么信息、考虑了哪些方案、为什么选择了这个方案、置信度是多少、哪些因素可能推翻这个选择。只有提供了这些上下文,人类审查者才能做出有意义的判断,而不是被动的"橡皮围章"。

实践洞察:HITL 的三种模式

同步审批(Sync Approve):Agent 暂停,等待人类实时批准后继续。适合高风险操作(付款、删除、配置变更)。

异步审查(Async Review):Agent 先执行,结果标记为"待审查",人类事后审计。适合中等风险操作(文档修改、PR 提交)。

阈值触发(Threshold Trigger):Agent 自主执行,仅当某个指标(金额、影响范围、置信度)超过阈值时才触发 HITL。适合规模化场景下的风险管理。

2.4 Delegation 边界--什么能委托,什么不能

Delegation(委托)是自主性设计的另一个核心维度。如果说自主性级别回答了"Agent 有多少自由",那么 Delegation 边界回答了"Agent 能碰什么"。

这和第五章讨论的多 Agent 委派不同--第五章的 delegation 是 Agent 之间的任务分配(Supervisor 委派给子 Agent),而这里的 delegation 是人类向 Agent 的授权边界。两者有联系但关注点不同。

设计 Delegation 边界,需要从三个维度对每个操作进行分类。这三个维度构成了一个风险评估立方体--每个操作在三个轴上都有一个坐标,三个坐标共同决定了该操作的委托策略。这种方法的优势在于系统性和可追溯性--每个委托决策都可以追溯到具体的风险评估过程,而不是"凭感觉"。

维度一:操作的可逆性。操作后果是否可以撤销?发一封邮件可以召回(虽然不一定有效),但删除数据库记录几乎不可逆。向供应商下订单可以取消(可能有违约金),但自动发送的"终止合作通知"造成的商业关系损害几乎无法修复。可逆性越高,委托风险越低。需要注意的是,可逆性不只是技术上的"能不能撤销",还包括业务上的"撤销代价"。一个技术可逆的操作,如果撤销的业务代价过高(如已经引起了市场反应或客户信任损失),在实践中应该被视为不可逆。

维度二:操作的影响范围。影响一个文件 vs 影响整个系统?修改一行代码 vs 删除一个服务?影响一个用户 vs 影响所有用户?ShopEase 的事故中,Agent 调整了 47 个 SKU 的价格--单个调整可能合理,但批量调整造成了系统性影响。影响范围越大,委托需要越谨慎。

维度三:操作的价值敏感度。涉及金钱、隐私、安全、合规的操作,其委托需要额外的审查层级。这就是为什么金融机构的交易 Agent 通常运行在 L2-L3,而内容推荐 Agent 可以运行在 L4--不是因为前者能力弱,而是因为前者的错误代价是直接财务损失。价值敏感度还涉及一个"连锁反应"问题:一个看似低价值敏感度的操作,可能触发连锁反应导致高价值损失。例如,修改一个配置参数(低价值敏感度)可能导致服务中断(高价值损失)。因此,价值敏感度评估不应只看操作本身,还要考虑其二阶和三阶影响。

这个矩阵给出的是静态的委托策略--根据操作类型预设自主性级别。但现实中,委托决策是动态的,需要考虑上下文。同样是"查询数据",查询公开产品目录可以 L4 自主执行,但查询用户隐私数据就需要 L2 审批。同样是"发送邮件",内部通知可以 L3 自主发送,对外商务邮件需要 L2 审批。

为了处理这种动态性,我们需要一个委托规则引擎,它接受多个信号作为输入(操作类型、目标资源、金额阈值、用户权限级别、时间窗口、历史失败率),输出一个自主性决策(允许自主执行 / 需要审批 / 禁止执行)。这个引擎的设计原则是"默认拒绝,例外允许"--对于任何没有被显式标记为"允许自主执行"的操作,默认要求人工审批。这种"白名单"模式比"黑名单"模式安全得多,因为它不会因为遗漏了某个风险场景而让 Agent 自主执行危险操作。

委托规则引擎还需要考虑时间维度。某些操作在工作时间是低风险的(因为有足够的人力来处理异常),但在非工作时间是极高风险的(因为出问题了没人发现)。一个精心设计的委托引擎会对同一操作在不同时间窗口应用不同的自主性级别--例如,数据库备份在工作日白天允许 L3 自主执行,但在周末和夜间降级到 L2 需要值班工程师审批。这种"时间感知"的委托策略在 DevOps 场景中特别重要。

这里有一个容易被忽略但极其重要的概念:自主性证书(Autonomy Certificates)。arXiv 论文提出了这个治理机制--由第三方管理机构向 Agent 开发者颁发自主性证书,向其他开发者和 Agent 传达行为特征。在多 Agent 交互场景中,接收方 Agent 可以查询交互方的自主性级别,据此设计安全交互策略。例如,一个 L4 自主性的交易 Agent 在与一个 L2 自主性的合规 Agent 交互时,应该知道后者可能需要在关键步骤暂停等待人类审批--不应假设它能即时响应。

在更微观的层面,Delegation 边界的执行依赖于权限分层。这和将要讨论的工具级 RBAC(Role-Based Access Control)密切相关--但这里关注的不是"Agent 能调用什么工具",而是"Agent 在什么条件下能调用什么工具"。前者是静态权限,后者是动态委托。例如,一个 Agent 可能拥有"发送邮件"工具的访问权限(静态权限=允许),但在当前上下文中(收件人是外部客户、内容包含合同条款)需要额外审批(动态委托=条件性限制)。这两者的结合构成了完整的 Agent 权限模型。

权限分层的另一个重要概念是最小权限原则(Principle of Least Privilege)。Agent 应该只被授予完成当前任务所必需的最小权限,而不是"以防万一"地赋予所有可能的权限。在自主性设计中,这意味着:如果一个 Agent 的任务是"查询库存",它就不应该拥有"修改库存"的权限,即使修改库存的工具在同一个工具集中。这听起来是常识,但在实际部署中经常被忽视--很多团队为了"方便",会给 Agent 一个包含所有工具的超集,然后依赖 system prompt 来约束行为。这是极其脆弱的设计,因为 system prompt 注入攻击可以绕过 prompt 级别的约束。

过度代理(Excessive Agency)警告

"你给了 AI 实习生王国的钥匙"--这是 Medium 上对过度代理问题的生动描述。过度代理发生在以下任一情况:(1) Agent 被授予了超出其能力范围的决策权;(2) Agent 被授予了超出任务需求的工具权限;(3) Agent 被允许在无监督的情况下执行高影响操作。四个关键安全研究缺口需要关注:验证(如何验证 Agent 行为符合预期)、涌现行为(Agent 组合后产生意料外的行为)、人类监督(如何设计有效的监督机制)、问责制(出问题时谁负责)。

2.5 自主性风险评估与降级机制

设计了自主性级别和委托边界后,还需要一个"安全阀"--当事情开始失控时,能自动收紧自主性。自主性降级机制就是这样一个动态安全系统。

降级机制的核心逻辑是:持续监控 Agent 的行为信号,当异常模式出现时自动降低自主性级别。触发降级的信号包括:

  • 连续失败:Agent 在短时间内连续失败 N 次(如 3 次工具调用失败),表明当前任务超出了 Agent 的能力范围
  • 置信度骤降:Agent 的决策置信度从 0.9 突然降到 0.5 以下,表明 Agent 进入了不熟悉的领域
  • 异常执行时间:一个通常 2 秒完成的操作已经运行了 30 秒,可能陷入了循环
  • 资源消耗激增:Token 消耗或 API 调用次数突然大幅超出历史基线
  • 边界逼近:操作参数(金额、影响范围)接近预设的安全阈值
基线建立 收集 Agent 在正常运行状态下的行为数据(成功率、延迟、Token 消耗、置信度分布),建立统计基线。通常需要 7-14 天的运行数据。
实时监控 对每个 Agent 决策记录 5 个核心指标:置信度、执行时间、资源消耗、操作风险等级、历史成功率。与基线比较计算偏离度。
异常检测 当偏离度超过阈值(如置信度低于基线 2σ),触发降级评估。使用规则引擎+统计方法组合判断,避免单一方法的盲区。
自主性降级 根据异常严重程度执行分级降级:L4→L3(增加审批节点)、L3→L2(每步审批)、L2→L1(仅建议不能执行)。极端情况下直接暂停 Agent。
通知与恢复 降级后立即通知运维团队,提供降级原因和异常详情。问题解决后,需人工审批才能恢复原始自主性级别--不可自动恢复。

降级机制的一个设计要点是不可自动恢复--一旦触发降级,恢复原始级别必须经过人工审批。这是一个看似保守但至关重要的设计:如果 Agent 可以自动恢复自主性,那降级就变成了一个可以被 Agent "自己说服自己绕过"的软约束。想象一个场景:Agent 因为连续失败被降级到 L2,然后它"表现良好"了一段时间,自动恢复到 L3,结果立刻又犯了同样的错误--这种"震荡"模式比一直运行在 L2 更危险,因为系统行为变得不可预测。

降级机制的另一个设计考量是降级粒度。全局降级(整个 Agent 从 L4 降到 L2)虽然安全但过于粗略,可能导致 Agent 在低风险任务上也变得低效。更精细的设计是分任务降级--只对触发异常的任务类型降级,其他任务保持原级别。例如,如果 Agent 在"价格调整"任务上连续失败,只把"价格调整"的自主性从 L4 降到 L2,而"数据查询"保持 L3。这种粒度控制需要在自主性配置中使用 task-scoped 级别覆盖,也要求审计日志能够区分不同任务类型的行为模式。

安全风险方面,Obsidian Security 和 Intelligent CISO 的研究指出了自主 Agent 带来的几个新型威胁:攻击面扩大(传统安全控制从未设计用于应对自主决策系统)、间接 Prompt 注入(攻击者不需要直接入侵系统,只需操纵 Agent 访问的网页内容)、身份治理失败(以人为本的访问模型无法治理自主 AI Agent)。特别值得关注的是"非人类身份爆炸"--现代企业中 NHI(Non-Human Identity)数量已经是人类身份的 25-50 倍,每个自主 Agent 都是一个新的 NHI,带来了巨大的身份管理挑战。这意味着传统的 IAM(身份与访问管理)系统需要升级,从"管理人类用户"扩展到"管理人类+机器身份",包括 Agent 的创建、授权、轮换、撤销和审计全生命周期。

2026 中

云安全联盟(CSA)发布 Agent 自主性级别框架。自主性证书概念在多 Agent 系统治理中获得关注。AI Agent 安全作为独立学科成型。

PwC 的 AI Agent Survey 总结了一个精辟的观察:"人是问题--也是解决方案。" 预算正在飙升,可衡量的价值已经出现,但只有少数企业着眼于长远目标。这最后一句话尤其重要--自主性设计需要长远视角,因为它涉及的不是单个功能的技术实现,而是整个组织的 AI 治理体系。PwC 调查还揭示了另一个值得关注的趋势:企业在 Agent 自主性上的投入回报存在显著的"J曲线"--初期投入大、回报低(因为在建立安全体系和流程),但一旦治理体系成熟,回报会加速增长。很多企业在 J 曲线的底部就放弃了,认为"Agent 不够好",实际上是他们的治理体系还没跨过拐点。

从评价范式来看,当前行业存在一个系统性问题:评测过于关注"自主任务完成准确率",忽略了自主性本身需要独立测量。传统的 benchmark 测的是"Agent 能不能做对",但没有测"Agent 知不知道自己做对了"、"Agent 会不会在不确信的时候主动停下"、"Agent 会不会在边界条件下克制行动"。这些"元认知能力"是自主性设计的基石,但它们不在现有评测框架内。新趋势是将自主性评估从能力 benchmark 中分离,设计允许用户与 Agent 协作的评测任务--不只测终点是否正确,还测过程中的人类介入次数、介入原因和介入效果。

MIT AI Agent Index 还揭示了一个地缘维度:Agent 开发集中在美国(21/30)和中国(5/30),安全框架和合规文档的方法截然不同。这种差异在未来可能会形成不同市场的自主性治理范式--但无论哪个市场,"能力越强、责任越大"的原则是通用的。

研究者 Mitchell 在 2025 年提出了一个值得深思的观点:完全自主的 Agent 不应该被开发。这不是技术保守主义,而是对问责制缺失的深刻担忧--如果一个 L5 Agent 犯了错,谁来负责?Agent 的开发者?部署者?使用者?还是 Agent 自己?在法律和伦理框架跟上技术发展之前,L5 可能是一个应该设置但不应触碰的天花板。这个观点与自动驾驶行业 L5 的困境如出一辙:SAE 定义了 L5,但没有任何一家厂商宣称已经实现了真正意义上的 L5。原因不仅仅是技术挑战,更是因为法律框架、保险机制和社会接受度都还没有准备好。

Anthropic 的负责任扩展政策将"低级自主能力"(这里指不需要人类参与的自主能力)分类为"显著更高风险"。欧盟产品责任指令和美国侵权法都面临着 AI Agent 带来的独特挑战--当自主决策造成损害时,传统的产品责任框架是否适用?如果 Agent 是"自主"做出的决策而非按照预设规则,那么"产品缺陷"的定义需要重新审视。这些法律和监管的不确定性,进一步强化了"在自主性和安全之间保持平衡"的必要性。NeurIPS 2024 成立了专门的"可监管ML / 社会责任语言建模 / 迈向安全可信赖Agent"工作坊,标志着学术界也开始系统性地关注 Agent 自主性的治理问题。

思路总结:设计自主性管控系统的三个层次

第一层:定义--明确每个 Agent 的自主性级别(L1-L5),基于任务风险、环境可控性和人类监督能力做选择。

第二层:控制--实现 HITL/HOTL 机制、Delegation 边界规则引擎、条件中断,确保自主性在技术层面可执行、可调整。

第三层:治理--建立审计日志、降级机制、自主性证书体系,形成闭环的自主性治理框架。

三、参考答案

下面我们用 LangGraph 1.x + 一个自建的自主性管控层来实现这个系统。代码分为四个模块：自主性配置、委托规则引擎、HITL 管控节点、降级监控器。这四个模块在逻辑上是分层关系：自主性配置定义"游戏规则"，委托规则引擎做"事前风险评估"，HITL 管控节点做"事中人工介入"，降级监控器做"事后行为分析”。四者配合形成一个完整的自主性治理闭环。注意，所有代码使用 LangGraph 1.x 的 StateGraph 和 interrupt API，不使用已废弃的旧 API。

委托规则引擎负责判断"这个操作能不能做、需要什么级别的审批"。它接受操作上下文作为输入,输出委托决策。

模块四:降级监控器

最后,我们实现降级监控器--持续监控 Agent 的行为信号,在检测到异常时自动降低自主性级别。

这个降级监控器使用了滑动窗口统计分析--不需要复杂的机器学习模型,简单的统计基线 + 规则引擎在生产环境中已经足够有效。关键是选择正确的信号指标和合理的阈值。

在生产环境中部署降级监控器时,有几个实践经验值得参考。首先是冷启动问题:新部署的 Agent 没有历史数据来建立基线,此时应保守地将初始自主性设为 L1 或 L2,直到积累了足够的数据(通常 7-14 天)。其次,避免告警疲劳:如果降级阈值设得太敏感,会频繁触发误报;太迟钝又会漏掉真正的异常。推荐使用分层阈值--轻微异常(分数 0.3-0.5)只记录日志和通知,中等异常(0.5-0.7)触发降级,严重异常(>0.7)直接暂停 Agent。最后,定期审查基线:随着系统演进和用户行为变化,历史基线可能过时,建议每月重新计算一次。

架构设计最佳实践

1. 配置与代码分离:自主性级别、阈值、风险映射全部在 YAML 中定义,不硬编码在 Python 中。这使得运营团队可以快速调整策略而无需部署新代码。

2. 分层防御:委托规则引擎是第一层(事前预防),HITL 管控节点是第二层(事中拦截),降级监控器是第三层(事后学习+实时保护)。三层防御互补,不依赖任何单一机制。

3. 全链路审计:每个决策--无论是否执行--都记录在 DecisionRecord 中。这不是可选的"nice to have",而是合规和事后分析的必要条件。

4. 不可自动恢复:降级后恢复原始自主性级别必须经过人工审批。这条规则看似降低了系统的"自愈能力",但它防止了 Agent 在降级后继续以高自主性运行的风险。

四、举一反三

以下三个变体题从不同角度深化 Agent 自主性设计的实践能力。每个变体题聚焦一个核心能力维度,帮助读者将本章的理论和代码扩展到更多真实场景。

变体 A:客服 Agent 的动态自主性切换

学习目标:训练在用户情绪驱动的动态自主性调整能力。理解自主性不是全局固定的参数,而是可以根据实时上下文(用户情绪、对话轮次、问题复杂度)动态调整的变量。这是 HOTL 模式在客服场景中的具体应用。

与原题差异:原题的自主性配置是按任务类型静态分配的(查询→L3、采购→L1)。变体 A 要求实现实时动态切换--同一个客服 Agent 在对话过程中根据用户情绪变化自主调整级别。当检测到用户愤怒或焦虑时,Agent 自动降级到 L2(每步都需要人工审核),防止在情绪化对话中做出不当承诺。当用户情绪平稳时,恢复到 L3 自主处理。

考察的核心能力:多信号融合决策(情绪检测+任务风险+对话历史)、实时自主性调整的工程实现、情绪检测模型的阈值调优。这个变体训练的是"上下文感知的自主性"--Agent 不只知道"做什么",还能感知"什么时候应该更谨慎"。

变体 B:多 Agent 系统的差异化自主性配置

学习目标:训练在多 Agent 协作环境中为每个角色独立设计自主性级别的能力。理解自主性不是一个系统级参数,而是每个 Agent 独立的设计维度。这是第五章(多 Agent 架构)和本章(自主性级别)的交叉点。

与原题差异:原题聚焦于单个 Agent的自主性管控。变体 B 将场景扩展到一个由 Supervisor + 3 个 Worker Agent 组成的系统:Supervisor 运行在 L4(全流程自主,关键节点审批),数据分析师 Agent 运行在 L3(自主查询,结果需要 Supervisor 审核),执行 Agent 运行在 L2(每个操作都需要 Supervisor 批准),审计 Agent 运行在 L1(仅记录和报告,不执行任何操作)。

考察的核心能力:多角色 Agent 的差异化自主性设计、Agent 间自主性证书交互(一个 Agent 如何知道另一个 Agent 的自主性级别并据此设计交互方式)、多层级 HITL 流程设计。核心挑战是"委托链"--当 Supervisor 把任务委派给 Worker 时,Worker 的自主性级别如何影响 Supervisor 的委派策略?

变体 C:DevOps Agent 的渐进式自主性晋升

学习目标:训练设计自主性渐进提升机制的能力。与降级机制相反,这个变体关注的是:如何安全地提升一个 Agent 的自主性级别--从 L1 逐步晋升到 L3/L4。这是 DevOps 自动化场景中最常见的需求:一个新部署的 Agent 需要从"全程监控"逐步过渡到"自主运行"。

与原题差异:原题关注静态配置和降级(从高到低)。变体 C 关注渐进式晋升(从低到高)--如何设计"试用期"机制:Agent 在 L1 运行 7 天,如果成功率 > 95% 且无安全事故,自动晋升到 L2;在 L2 运行 14 天,如果达标则晋升到 L3。每个晋升节点需要人工审批(自动晋升是不允许的--和降级恢复一样,晋升也需要人类决策)。

考察的核心能力:长期行为评估、多维度晋升指标设计(不只是成功率,还包括响应时间、用户满意度、资源消耗效率)、晋升决策的自动化与人工审批平衡。这个变体训练的是"信任建立机制"--如何用数据驱动的方式逐步建立对 Agent 的信任。

本章核心要点回顾
  1. 自主性 ≠ 能力:能力是"能不能做对",自主性是"允不允许做"。两个维度完全正交,需要独立设计和校准。
  2. 五级分类法 (L1-L5):Operator → Collaborator → Consultant → Approver → Observer。用户角色逐步退化,Agent 自主性逐步增强。可参考 SAE 自动驾驶分级做跨领域类比。
  3. HITL → HOTL 演进:从"人在循环内"(每步审批)到"人在循环上"(规则内自主,异常才介入)。这是从微观管理到目标管理的转变。
  4. Delegation 三维度:可逆性、影响范围、价值敏感度。每个操作需要在这三个维度上评估,据此确定委托策略。
  5. 三层防御:委托规则引擎(事前)+ HITL 管控节点(事中)+ 降级监控器(事后),形成闭环的自主性治理体系。
  6. 行业现状:仅 15% 企业考虑完全自主 Agent。2025-2026 是 L2→L3 迁移的关键年。自主性治理正在成为独立学科。
