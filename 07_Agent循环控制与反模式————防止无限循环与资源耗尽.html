07. Agent循环控制与反模式——防止无限循环与资源耗尽

⭐⭐⭐ 高级 最大迭代数 目标完成检测 死循环识别 Token预算管理 四层防御策略 BATS框架

一、题目描述

在上一题中，我们构建了一套完整的Agent自主性治理体系——从L1到L5的分级框架、HITL审批机制、Delegation边界评估、到降级监控器。那套体系回答了"Agent该有多少自由"的问题。但自主性治理中有一个信号特别值得警惕：降级监控器检测到"连续失败"和"置信度骤降"。这两个信号暗示着一个更深层的工程问题——Agent可能已经陷入了无法自拔的循环，它不是"做错了需要降级"，而是"根本停不下来了"。

一个不会停的Agent，就像一辆没有刹车的跑车。自主性治理给了它方向盘和油门——你可以授权它在高速公路上飞驰。但如果没有可靠的刹车系统（终止条件），这辆车最终只有一种结局：撞墙。而AI Agent的"墙"，就是你收到账单那一刻的震撼。

背景故事：$47,000的午夜账单

2025年11月的一个周二早晨，某AI初创公司的CTO Marcus打开邮箱，发现了一封来自API提供商的账单通知。金额：$47,000。他的第一反应是钓鱼邮件——整个公司上个月的API支出也不过$3,000。但登录控制台后，数据冰冷地摆在眼前：4个通过A2A协议协调的LangChain Agent，在过去11天里（264小时）不间断运行，执行了超过48,000次API调用，其中单个Agent在最后48小时内的调用量就超过了20,000次。

调查复盘发现了一个荒诞的循环链：Analyzer Agent生成市场分析报告 → Verifier Agent收到后认为"数据不够充分，需要进一步分析" → Analyzer重新生成 → Verifier再次要求"更深入的分析" → Analyzer照做……这个乒乓循环在4个Agent之间以每3-4秒一次的频率持续运转，没有任何Agent主动说"够了，任务完成了"。更讽刺的是，在第一天之后，分析报告的内容已经完全没有实质变化——两个Agent只是在反复处理相同的信息，用略微不同的措辞重新包装。

为什么没有一道防线阻止这件事？Marcus团队事后列出了"五道本应拦住的防线"以及它们各自失败的原因：

  • 最大迭代限制：团队确实设了LangGraph的recursion_limit=100，但多Agent协调的A2A协议绕过了单个图的递归计数器——每个Agent的内部循环都不到100，但跨Agent的循环没有计数
  • 预算告警：可观测性平台LangSmith确实记录了异常消耗，告警邮件在第三天就发了——但发到了运维工程师的邮箱，而该工程师恰好在休假
  • 人工巡查：团队没有安排7×24小时值守，周末和夜间无人监控
  • API限额：API提供商的月度限额是$50,000——差一点就触发了自动暂停，但差的那$3,000意味着循环又白白多转了8天
  • Agent自我判断：每个Agent都被赋予了"如果你认为任务完成了就停下来"的指令，但Verifier的system prompt中写着"确保分析足够全面"——"足够全面"是一个永远无法被二元判断的主观标准

这五道防线全部失守。不是因为技术不够先进，而是因为每一道防线都犯了同一个错误：用监控代替执行，用主观判断代替可验证条件，用单一层防御代替纵深防御。

这个案例的根因不在于某一个设计失误，而在于缺少系统性的终止条件设计。Agent的循环执行本身是特性而非Bug——正是"失败就重试、信息不足就追问"的迭代能力让Agent能处理复杂多步任务。但当迭代变得无效时，系统必须有能力识别并阻止它继续空转。

二、详细思路分析

要设计一套可靠的Agent循环终止系统，我们需要从理解"Agent循环到底是什么"开始，然后逐层构建防御体系。这道题考察的不是某一个具体的技术点，而是你对整个"Agent运行时安全"领域的系统性理解。下面我将从六个维度展开分析。

2.1 Agent循环的本质：为什么成本是O(n²)？

Agent循环（Agent Loop）是每个自主AI系统的核心执行引擎。它不是一次性请求-响应模式，而是一个迭代执行循环：LLM推理 → 选择工具 → 执行工具 → 将结果反馈给LLM → 再次推理，直到任务完成或达到停止条件。这个循环的每一次迭代，都会向对话历史（上下文窗口）中添加新内容。

关键洞察在于理解这个循环的成本结构。假设每次迭代的工具执行结果大约产生K个token的新上下文，那么第N次迭代时，LLM需要处理的输入token数为：初始提示 + N×K个累积token。这意味着总token消耗不是线性的O(N)，而是接近O(N²)——因为第N步的推理需要把之前所有步骤的历史都送进去。具体来说，N次迭代的总输入token消耗约为：初始提示×N + K×(1+2+…+N) = 初始提示×N + K×N×(N+1)/2。

来做一个具体的计算。假设初始system prompt + 用户消息 = 2,000 token，每次工具调用结果 = 1,500 token，模型输出 = 500 token。那么第1次迭代的输入token约为2,000，第5次迭代的输入token约为2,000 + 4×2,000 = 10,000，第15次迭代的输入token约为2,000 + 14×2,000 = 30,000，第25次迭代的输入token约为2,000 + 24×2,000 = 50,000。注意第25步的输入是第1步的25倍！这意味着即使每次迭代做的事情完全相同（比如反复调用同一个搜索工具），后续步骤的API成本也远高于前面的步骤。这就是为什么Waxell.ai的研究指出："第5步循环可能花费155×基线调用成本"——因为每次调用都携带着之前所有步骤的完整上下文。

这个O(n²)的成本结构是理解Agent预算管理的数学基础。它意味着：你不能简单地用"单次API调用成本 × 预期迭代次数"来估算总成本——实际成本会远超这个估算。正确的做法是按会话设定预算，并在运行时同步检查。

O(n²)成本公式

对于N次迭代的Agent会话，总输入token消耗约为：

Total = Σ(i=0 to N-1) [P + i × S] = N×P + S×N×(N-1)/2

其中 P = 初始提示token数，S = 每次迭代新增的平均token数。当N较大时，S×N²/2 项主导总成本。

理解了成本结构，接下来的问题是：Agent应该在什么条件下停止迭代？这引出了终止条件设计的核心方法论。

2.2 六类可验证停止条件：从"差不多"到"确定性"

Agent循环终止的最大陷阱之一是使用主观停止条件。所谓主观停止条件，是指那些依赖LLM自身"感觉"来判断是否完成的条件——比如"当你确信答案正确时停止"、"当输出质量足够高时停止"、"当收集了足够信息后停止"。这些条件的问题在于：LLM没有"信心"这种东西，它的"质量判断"不稳定，而"足够"这个标准缺乏可测量的定义。

可验证的停止条件完全不同。它有三个核心属性：二元性（条件要么为true要么为false，不存在"大概完成了"的灰色地带）、无需解释（Agent或独立检查代码无需主观推理即可评估）、引用具体可测状态（世界中某些东西已经改变、数字已达阈值、列表已完成）。基于这三个属性，我们可以将实际场景中的停止条件归纳为六大类：

类型 示例 适用场景 可验证性
计数型 "5次迭代后停止" 硬安全帽；步数可预测的任务 ✅ 确定性：整数比较
状态变化型 "当文件存在于目标路径时停止" / "API返回status:complete时停止" 需要外部系统确认的任务 ✅ 确定性：文件/API状态检查
列表完成型 "当输入数组每个项都处理完时停止" 批处理任务（如处理N个文档） ✅ 确定性：列表长度比较
阈值型 "当测试覆盖率超过80%时停止" / "当错误率降至1%以下时停止" 有明确量化指标的任务 ✅ 确定性：数值比较
Schema验证型 "当JSON输出通过schema验证无错误时停止" 结构化数据提取/格式化 ✅ 确定性：JSON Schema校验
目标完成型 LLM返回特定finish标记（如"TASK_COMPLETE"） 开放性任务，需配合硬帽使用 ⚠️ 半确定性：依赖LLM判断

注意最后一行"目标完成型"标记了⚠️——这是唯一一类依赖LLM自身判断的停止条件。它不是不能用，而是不能单独使用。在生产系统中，"目标完成型"必须与其他五类确定性条件配合使用，或者由一个独立的验证器（而非执行任务的LLM自身）来判断目标是否真的达成。

对比一下主观停止条件的失败模式就更清楚了："输出质量高时停止"——什么算高？谁来定义？"比上一版更好时停止"——好在哪里？字数？可读性？准确率？"当你确信答案正确时停止"——LLM没有"确信"这个状态，它只是生成下一个token。这些模糊条件会导致同一个Agent在面对相同输入时，有时在第3步停止，有时在第30步还不停止，行为完全不可预测。

2.3 四层防御策略：从硬性安全帽到运行时执行

$47K事故的最大教训不是"缺少某个终止条件"，而是缺少纵深防御。任何单一的终止机制都可能失效——最大迭代数可能被绕过（如A2A跨Agent循环），预算告警可能没人看，LLM自我判断不可靠。真正可靠的终止系统必须采用多层防御（Defense in Depth）策略，让每一层都成为下一层的后备。

以下是经过生产验证的四层防御策略：

第1层：硬性安全帽是"不可协商"的物理限制。它不关心Agent在做什么、做得怎么样，只要触发任何一个限制就立即终止。这一层包括三重硬帽：最大迭代次数（建议设为预期步数的3-5倍）、最大Token预算（以美元计，如$5/session）、最大执行时长（如300秒超时）。硬性安全帽的设计哲学是"宁可错杀，不可漏放"——它可能偶尔在Agent快要完成任务时强行终止，但这是可以接受的代价，因为另一端的代价是无限循环。

第2层：智能预警在硬性安全帽触发之前就介入。它的设计哲学是"给Agent收尾的机会"。如果一个Agent的硬性限制是30次迭代，第25次才触发硬截断就太粗暴了——Agent可能正在做有意义的最后几步，突然被截断会丢失中间成果。智能预警系统会在迭代15-20左右就开始注入"你还剩N次迭代"的提醒消息，并在最后一次时强制注入"你必须立即给出最终回复"。此外，这一层还包含重复调用检测（Debounce Hook）和进展检测（连续N步没有任何文件创建、API调用成功、状态变化则终止）。

第3层：目标完成检测是最聪明的一层。它通过确定性代码（而非LLM自身判断）来检查任务目标是否已经达成。比如：检查目标文件是否存在且非空、检查所有输入项是否已处理、检查输出是否通过了JSON Schema验证、检查测试覆盖率是否超过阈值。这一层的关键原则是"用代码做判断，而不是用LLM做判断"——因为代码的判断是确定性的，而LLM的判断每次都可能不同。

第4层：运行时执行解决的是"监控≠执行"的鸿沟。在$47K事故中，告警确实发了（第三天就发了），但没有人看到，也没有任何机制阻止Agent继续运行。真正的预算执行必须是同步拦截——在下一次API调用之前检查预算，如果超限就拦截调用，而不是在调用完成后异步通知。此外，这一层强调"暂停-审查-恢复"机制而非直接杀死会话：当预算触达时，暂停Agent，等待人工审查后决定是追加预算恢复运行还是终止任务。这使得预算执行更加灵活，适合需要保留中间成果的场景。

监控 vs 执行：$47K事故的核心教训

监控（Alerts）：在花费发生后记录和报告 → 异步通知人 → 事后追责 → 适合日常运营

执行（Enforcement）：在花费发生前拦截请求 → 同步阻止API调用 → 事前阻止 → 适合生产安全网

两者的区别就像"烟雾报警器"和"自动灭火系统"——前者告诉你着火了（你可能在睡觉听不到），后者直接把火灭了。一个可靠的Agent系统两者都需要，但执行比监控更重要，因为你不能假设总是有人在看告警。

2.4 死循环识别：三种检测技术

即使有了四层防御，我们还需要能识别"虽然没触发硬限制，但Agent已经在空转"的情况。死循环识别是第2层（智能预警）的核心技术，包含三种互补的检测方法。

第一种：重复调用检测（Duplicate Call Detection）。这是最简单也最有效的检测方式——跟踪最近N次工具调用的签名（工具名+参数），如果相同签名在滑动窗口内出现超过阈值（如2次），第3次调用被阻断。实现上，可以采用类似Strands SDK的DebounceHook：维护一个固定大小的调用历史列表，每次工具调用前检查是否与最近的调用重复。这种检测对于"Agent反复搜索同一个关键词"这类死循环非常有效。

但仅仅检测完全相同的调用还不够。有些Agent会"聪明地"稍微改变参数——比如换一个搜索关键词——但实际效果一样（搜索结果相同）。因此更完善的检测还需要结果指纹检测：对工具返回结果计算哈希值，如果最近N次不同调用的结果哈希相同，说明Agent在获取完全相同的信息但没意识到。

第二种：进展检测（Progress Detection）。重复调用检测关注"是不是在做相同的事"，进展检测关注"是不是在做有用的事"。它的原理是定义一组可观测的状态指标（如：已创建的文件数、已处理的任务项数、已收集的数据条目数），然后跟踪这些指标在最近N步迭代中的变化。如果连续K步迭代中所有状态指标都没有变化，就判定为"无进展"并触发终止。

进展检测的关键是选择合适的状态指标。对于代码生成Agent，可以是"代码行数变化"和"测试通过数变化"；对于研究Agent，可以是"已引用的信息源数量"和"报告字数"；对于数据处理Agent，可以是"已处理的记录数"和"新增的错误数"。如果这些指标连续多步不变，Agent很可能陷入了无效循环。

第三种：乒乓循环检测（Ping-Pong Detection）。这是多Agent系统特有的问题——两个Agent之间互相踢皮球，A说"需要更多分析"→B做了分析→A说"分析不够深入"→B再做→循环。检测方法是在协调层（Supervisor）维护一个跨Agent的消息历史，如果发现A→B→A→B的交替模式持续超过阈值轮次且每轮的语义内容相似度很高，就触发乒乓循环警报。

乒乓循环的防护需要在协调层实现断路器模式（Circuit Breaker）：跟踪Agent之间的消息序列，当检测到A↔B交替超过设定阈值（如5轮），强制中断循环并升级给Supervisor或人类处理。每个Agent还应有独立的迭代预算，防止一个Agent的循环耗尽整个系统的预算。

2.5 迭代预算压力与Token预算管理

迭代预算压力（Iteration Budget Pressure）是一个来自NousResearch/hermes-agent项目的精巧设计。它的理念非常简单但有效：与其在Agent达到最大迭代数时粗暴截断，不如在它接近限制时就提前注入系统消息，让LLM知道"时间快到了"，给它自我收尾的机会。

具体实现是一个两级压力系统。第一级在迭代数达到最大值的约70%时触发，向对话中注入一条系统消息："注意：你还剩N次迭代机会。如果你已经完成了主要任务，请开始整理和总结你的发现。"第二级在最后一次迭代时强制注入："你必须立即给出最终回复。不要再调用任何工具。"这种设计的巧妙之处在于它利用了LLM的指令遵循能力——大多数LLM在收到明确的"该收尾了"指令后，确实会停止工具调用并生成最终回复，而不是被强行截断后留下半成品。

迭代预算压力之所以重要，是因为它解决了一个工程难题：如何优雅地终止一个还在"努力工作"的Agent。简单截断（到第N步直接kill）的问题在于，Agent可能在第N-1步刚刚获取了关键信息，还没来得及整合到最终输出中就被终止了，导致整个会话的成果丢失。预算压力给了Agent一个"整理遗物"的机会——它会主动把已经收集的信息整合成不完美但可用的最终回复。

与迭代预算压力紧密配合的是Token预算管理。基于前面分析的O(n²)成本结构，有效的预算管理需要实现以下功能：Per-Agent预算（每个Agent有独立的预算上限，防止一个Agent耗尽全局预算）、Per-Session预算（整个多Agent会话有一个总预算上限）、运行时同步检查（每次API调用前检查剩余预算，不够则拦截）、以及预算感知提示（将剩余预算信息注入Agent的上下文，让它自行调整行为策略）。

经验法则：迭代上限设置

预期步数的3-5倍作为最大迭代数。如果你的任务通常需要5-7步完成，设max_iterations=25。这给了Agent足够的容错空间（重试失败的工具、探索不同方案），同时防止失控循环消耗过多资源。

2.6 主流框架的终止条件实现对比

不同Agent框架对终止条件的实现方式各有不同，了解这些差异对于选型和迁移非常重要。

LangGraph使用recursion_limit参数控制图的最大迭代次数，默认值为25。它的工作原理是计数图中的每一步执行（节点调用），当达到限制时抛出GraphRecursionError。设置方式是在invoke/config中传入：config={"recursion_limit": 100}。LangGraph的递归限制有几个需要注意的细节：多Agent协调中的子图各自有独立的递归计数器，跨子图的循环不会被外层计数器捕获（这正是$47K事故中A2A协议绕过限制的原因）；用户报告即使设了较大的recursion_limit，有时仍会触发默认25的限制（通常是CopilotKit等集成层的覆盖问题）；确保停止条件在递归限制内触发是开发者的责任——框架只提供"硬截断"，不提供"智能预警"。

CrewAI在1.x版本中通过Task级别的max_iter参数控制每个Agent的迭代上限。同样存在递归深度超限的问题，尤其是Agent之间互相委派任务时。CrewAI 1.x引入的Flows引擎提供了更好的编排控制，但终止条件的配置仍然需要在Task定义中显式设置。

Strands Agents SDK（AWS）提供了最细粒度的控制——通过Hooks机制实现自定义终止逻辑。BeforeToolCallEvent允许在工具执行前拦截（可用于Debounce Hook），BeforeInvocationEvent在每次Agent调用开始时触发（可用于重置状态）。Strands还内置了LimitToolCounts Hook来限制每次调用的工具使用次数，以及滑动窗口检测重复调用的DebounceHook。这是目前主流框架中对终止条件支持最完善的。

LiteLLM从API网关层面提供预算控制，不依赖具体框架。它支持max_iterations（每会话LLM调用次数硬帽）和max_budget_per_session（每会话美元预算上限），通过x-litellm-trace-id跟踪会话内调用，超限返回HTTP 400。LiteLLM的优势是它能在API调用层面拦截，而不需要修改Agent逻辑——即使Agent框架本身的终止条件有Bug，LiteLLM也能在网关层兜底。

2.7 工具终态设计：一个被低估的循环根因

很多Agent循环不是由于终止条件设计不当造成的，而是由于工具返回值设计不当造成的。考虑以下两个工具返回：

❌ 反面模式：模糊信号导致循环 return f"Found {len(matching)} flights. Note: More results may be available." Agent看到"更多结果可能可用" → 判断需要继续搜索 → 用不同参数重试 → 又看到同样消息 → 无限循环
✅ 正面模式：明确终态让Agent知道何时停止 return f"SUCCESS: Found {len(matching)} flights out of {total}. All available results returned." return f"FAILED: {hotel} fully booked. No alternatives in price range." Agent收到SUCCESS → 明确知道任务完成 → 停止迭代

工具返回值的终态设计是一个被严重低估的工程实践。每一个工具的返回值都应该包含一个明确的终态标记（SUCCESS / FAILED / PARTIAL），加上结构化的数据负载。这个设计之所以重要，是因为Agent的停止决策很大程度上依赖于工具返回值中的信号。如果工具总是返回"可能有更多"这类模糊信号，Agent的指令遵循天性会驱使它继续尝试。反之，如果工具明确说"这是所有可用结果"（SUCCESS），Agent就有信心停止迭代。

一个完整的工具终态设计应该遵循以下规范：所有工具返回一个包含status字段的结构化对象，值为"SUCCESS"（任务完全完成）、"FAILED"（任务无法完成，附带原因）、或"PARTIAL"（部分完成，附带完成度和未完成原因）。此外，返回值还应包含data字段（实际数据负载）和metadata字段（如总结果数、是否还有更多数据等辅助信息）。这种设计使得Agent可以基于status字段做出可靠的停止决策，而不需要从自然语言文本中猜测"任务是否完成了"。

2.8 多Agent协调中的乒乓循环防护

$47K事故的直接原因是Analyzer和Verifier之间的乒乓循环。这种循环在多Agent系统中极为常见——因为每个Agent都被设计为"追求最佳结果"，当两个追求最佳结果的Agent互相评审时，就会陷入"永远可以更好"的死循环。

防护乒乓循环需要从三个层面入手。第一个层面是独立预算：每个Agent都有自己的迭代预算和Token预算上限，这样即使一个Agent陷入循环，也不会无限制地消耗系统资源。在$47K事故中，如果Analyzer有独立的$2预算上限，它在花了$2之后就会被终止，而不会循环11天。

第二个层面是协调层超时：Supervisor或协调器维护一个跨Agent的循环计数器，当检测到两个Agent之间的交互轮次超过阈值时（如5轮），主动介入并做出"终止或升级"决策。这需要Supervisor追踪Agent之间的消息序列模式——如果A→B→A→B的交替模式持续超过设定阈值，就触发断路器。

第三个层面是任务定义的完备性检查：很多乒乓循环的根因是任务定义中缺少明确的"完成标准"。比如Verifier被指示"确保分析足够全面"，但"全面"没有定义。如果在任务定义时就指定了可验证的完成标准——如"分析报告包含至少3个数据源引用、覆盖了指定的5个维度"——Verifier就可以用确定性检查代替主观判断，避免无限要求"更全面"。

2.9 BATS框架：让Agent拥有预算意识

前面讨论的所有防御机制都是外部强加给Agent的——由框架代码检查迭代数、由Hooks阻断重复调用、由Supervisor切断乒乓循环。这些"被动防御"是必要的，但不充分。一个更前沿的思路是让Agent主动拥有预算意识，在运行时自行决定如何最优地使用剩余资源。

这就是2025年arxiv论文（abs/2511.17006）提出的BATS框架（Budget-Aware Tool-use Scaling）的核心思想。BATS框架包含两个核心组件：Budget Tracker（预算追踪器）是一个轻量级插件，为Agent提供持续的预算感知——在每个推理步骤中，Budget Tracker将当前剩余预算（剩余迭代次数、剩余Token、剩余美元）作为上下文注入Agent的提示；Budget-Aware Strategy（预算感知策略）则是Agent根据剩余预算动态调整行为——预算充足时"深挖"有希望的线索（多调用工具、做更细致的分析），预算紧张时"转向"直接给出基于已有信息的最优回复。

BATS论文的一个重要发现是：简单给Agent更大的工具调用预算并不能提升任务完成质量。研究者对比了"给Agent 50次工具调用预算"和"给Agent 50次预算+BATS框架"两种条件，结果发现没有BATS的Agent倾向于在前10次调用中就花掉大部分预算（因为它没有"预算紧张"的概念），而后面的40次调用往往是低质量的重复。有了BATS的Agent则会更谨慎地分配预算——在前几次调用中探索不同方向，确认有希望的方向后集中预算深挖，在预算紧张时及时转向总结。这就像一个有经验的旅行者不会在第一天就把旅费全花光，而是根据整体行程合理分配每天的预算。

BATS框架对我们的终止系统设计的启示是：除了外部的硬性限制和智能预警，还应该在Agent的上下文中注入预算信息，让Agent成为自己预算的"管理者"。具体实现上，可以在每次迭代时向Agent的上下文注入一条系统消息："当前进度：迭代{current}/{max}，已用预算${used}/${total}（{percentage}%），剩余迭代{remaining}次。"这种简单的预算感知能让Agent在接近限制时主动收窄探索范围，而不是盲目继续调用工具直到被外部机制截断。

四层防御 + BATS = 完整防御体系

四层防御策略是"外部约束"——由系统代码在Agent外部实施的硬性限制和智能检测。BATS框架是"内部意识"——让Agent在运行时拥有预算感知、主动调整策略。两者结合构成了完整的防御体系：外部约束确保即使Agent的内部意识失效（比如LLM没有遵循预算提示），系统仍然安全；内部意识确保Agent在被外部约束终止前有最大的机会完成任务。

2.10 六个新手陷阱与修复方案

在实际工程实践中，Agent循环终止设计有六个高频陷阱。如果你正在构建Agent系统，请逐条自查。

陷阱1：只设硬帽不设预警 设了max_iterations=25，Agent到第25步被强制截断，中间成果全部丢失。修复：实现迭代预算压力，在接近限制时提前警告LLM。
陷阱2：工具反馈模糊导致循环 工具返回"更多数据可能可用"类模糊信号，Agent理解为"需要继续"。修复：所有工具必须返回SUCCESS/FAILED/PARTIAL终态。
陷阱3：混淆重试与循环退出 用单步重试逻辑（retry 3次）处理整体循环退出问题。修复：重试处理单步失败，循环退出需要定义整体任务的"完成"标准。
陷阱4：忽略上下文累积成本 按单次API调用成本估算总预算（假设每次调用$0.05×30步=$1.5）。修复：理解O(n²)成本结构，按会话设预算并留足余量。
陷阱5：多Agent无独立预算 多个Agent共享一个总预算，一个Agent循环耗尽所有资源。修复：每个Agent设独立预算上限。
陷阱6：依赖LLM判断完成 让LLM自己决定"是否完成"，结果不稳定——同一输入有时第3步停、有时第30步不停。修复：用确定性代码检查可验证条件。

这六个陷阱几乎覆盖了Agent循环终止设计中最常见的失败模式。如果你在code review中发现以上任何一个模式，请立即修复——它们不是"优化项"，而是"必须修的生产Bug"。

二、详细思路分析

2.1 先问一个价值百万的问题：你真的需要Agent吗？

让我们从一个朴素但经常被遗忘的工程原则开始：

"用最简单的方案解决问题，只有当简单方案确实不够时才增加复杂度。"
—— 这不是某个Agent框架的原则，这是整个软件工程的黄金法则。

这条法则在AI时代变得尤为重要，因为AI技术的"酷炫感"会扭曲工程师的判断。当你手握一把锤子（Agent框架），所有东西看起来都像钉子（需要Agent解决的问题）。但这种心态的危险在于：每增加一层Agent抽象，你就在成本、延迟、可靠性和可维护性上付出代价，而且这些代价是指数级增长的。

DeepSeek在2024年12月发布的《Building Effective Agents》指南中，将这一原则具化为一个清晰的二分法：

Workflow（工作流）：通过预定义代码路径编排LLM和工具调用。开发者掌控控制流——先做什么、后做什么、在什么条件下走哪条路，都写在代码里。

Agent（智能体）：让模型自行从环境反馈中选择下一步工具调用。开发者只掌控目标和护栏——至于怎么走到目标，由LLM自己决定。

这两者的区别不是学术层面的咬文嚼字，而是直接影响你的系统成本、延迟、可靠性和可维护性的核心架构决策。

用一个类比来理解：

🚂 Workflow = 火车 轨道是固定的。每站停什么、走哪条线、什么时候到，全写在时刻表里。你100%确定能按时到达，但如果前面塌方了，火车不会自己绕路。
🚙 Agent = 越野车 你告诉司机目的地，至于走高速公路还是乡间小路、要不要绕开堵车，司机自己判断。灵活，但你不能100%确定到达时间，也不能保证司机不走错路。

问题在于：如果你的"货物"（业务逻辑）只是从A站到B站这条固定线路，你不需要一辆越野车。你需要的只是一列准点的火车。如果你花$340K造了一辆越野车来运送从A到B的固定线路货物，你不是在"拥抱AI"，你是在浪费工程资源。

更进一步，Anthropic在指南中给出了一个"三问法则"来快速判断你需要Workflow还是Agent：

  1. 路径确定吗？——你能提前写出"第1步做什么、第2步做什么"吗？如果能，用Workflow。
  2. 有反馈信号吗？——Agent每一步的执行结果能否被验证（如测试通过、API返回结构化数据）？如果没有可验证信号，Agent的自主决策就是盲目的。
  3. 有护栏吗？——你能为Agent提供沙盒环境、最大迭代次数、预算限制吗？如果不能，先建基础设施。

三个回答中任何一个是"否"，都倾向于使用Workflow。只有三个都是"是"，才值得考虑Agent。

一句话判断原则

"Use an agent when the path to the goal is uncertain, and a workflow when the path is known. If you can write down the steps, write them down."

翻译：路径不确定时用Agent，路径已知时用Workflow。如果你能把步骤写下来——那就写下来。

2.2 DeepSeek的6种Workflow模式：不用Agent也能用LLM

很多开发者有一个根本性的误解：不用Agent = 不用LLM。这个误解导致了大量不必要的Agent项目——开发者以为要使用LLM就必须搭建Agent系统。大错特错。Anthropic定义了6种Workflow模式，每一种都比Agent更简单、更可控，但同样充分利用了LLM的能力。让我们逐一深入：

① 单次增强LLM调用（Augmented LLM） 一次LLM调用 + 可选的检索/工具。适用于：一次性问答、文本分类、草稿生成、情感分析。最简单的模式，80%的"AI功能"到这一步就够了。
② Prompt链式（Chaining） 固定调用序列：A的输出是B的输入。适用于：大纲→写正文→检查语法→润色。每一步都可审计、可单独优化。
③ 路由分发（Routing） 分类器先选分支，再走对应处理流程。适用于：不同类型工单走不同处理逻辑。比"一个Agent处理所有类型"更可控。
④ 并行化（Parallelization） 多路同时调用LLM，汇聚结果。适用于：多维度审查（安全检查+风格检查+事实核查同时做）。比串行Agent快得多。
⑤ 编排者-工人（Orchestrator-Workers） 中心模型动态分配子任务给工人模型。适用于：多文件代码修改（每个文件不同操作）。看起来像Agent，但控制流在编排者手中。
⑥ 评估器-优化器（Evaluator-Optimizer） 生成→评分→改进的循环。适用于：有明确评分标准的迭代改进（翻译质量、代码优化）。比Reflexion Agent更可控。

这6种模式的精髓在于：它们让LLM负责内容生成，而不是控制流决策。开发者在代码中定义"第1步→第2步→第3步"的路径，LLM只负责每一步中"生成什么内容"。这种分工带来了三个巨大优势：

模式详解①：单次增强LLM调用——80%场景的终极答案

这是所有Workflow模式中最简单也最被低估的一种。它的完整架构就是：一次LLM调用 + 可选的RAG检索 + 可选的工具调用。没有循环，没有多步推理，没有Agent协调。

听起来太简单了？但事实是，绝大多数生产环境的"AI功能"——客服FAQ、内容审核、邮件分类、情感分析、摘要生成——用这一种模式就能解决，而且效果比多Agent系统更好，因为：

  • 延迟 = 1次LLM调用时间（~1-2秒）
  • 成本 = 1次Token费用（~¥0.01-0.05/次）
  • 可靠性 = 单步准确率本身（~95%+，无复合衰减）
  • 可调试性 = 只需检查1次调用的输入/输出

适用场景判断：如果你的任务可以用一句话描述（"把这段文本翻译成英文"、"判断这条评论是正面还是负面"），你需要的只是单次LLM调用。不要用链式，不要用路由，更不要用Agent。

常见误用：很多团队把这个级别的任务包装成了"Agent"——加了一个意图识别Agent、一个执行Agent、一个审查Agent。3次LLM调用解决1次就能搞定的问题，成本翻了3倍，可靠性从95%跌到86%（0.95³）。

模式详解②：Prompt链式——可分解的多步任务

当一个任务可以分解为固定的、有序的子步骤，且每个子步骤的输出是下一个步骤的输入时，Prompt链式是最优选择。与Agent的本质区别在于：步骤的顺序和数量是代码定义的，不是LLM运行时决定的。

典型例子：内容生成管道。步骤1生成大纲，步骤2根据大纲写正文，步骤3检查语法和事实准确性，步骤4润色风格。每一步都是独立的LLM调用，使用不同的Prompt（甚至不同的模型），但流程是固定的。

关键优势：每一步都可以独立测试和优化。如果最终输出有问题，你可以精确定位到哪一步出了错——这在Agent系统中几乎不可能做到，因为你不知道Agent"为什么选择了这条路径"。

何时升级到Agent：如果步骤的数量和顺序取决于中间结果——比如步骤2的输出可能告诉你"这个主题需要先查阅外部资料"——那你就需要Agent的动态决策能力了。但大多数内容生成管道不需要这种灵活性。

模式详解③：路由分发——分类器驱动的多分支

当输入数据可以分为若干已知类型，且每种类型需要不同的处理逻辑时，路由分发模式是最佳选择。第一步用一个分类器（可以是规则系统，也可以是LLM），第二步根据分类结果走对应的处理分支。

这就是小王的客服系统应该采用的架构：一个分类器将工单分为"退款/换货/物流查询/复杂投诉"四类，前三类走模板+单次LLM润色（成本¥0.03/次），后一类转人工或走更复杂的处理流程。整个系统的步骤数固定为2步，可靠性高、成本低、延迟小。

与"一个Agent处理所有类型"相比，路由分发的优势在于可预测性：每条路径都是独立优化的，不会因为某个类型的处理逻辑变更而影响其他类型。

模式详解④：并行化——用并发换延迟

当多个独立的LLM调用可以同时执行时，并行化模式可以将总延迟从串行的N×T降低到并行的T（T = 单次调用时间）。典型场景包括：

  • 多维度内容审查：同时检查安全性、合规性、语气风格、事实准确性（4路并行，延迟不变）
  • 多语言翻译：同时翻译成5种语言（5路并行，延迟 = 1次翻译时间）
  • 投票式决策：用不同Prompt运行同一问题3次，取多数票（提高准确率）

如果用Agent来实现这些场景，Agent会串行地一个一个处理——因为Agent循环天然是串行的（思考→行动→观察→思考→...）。并行化Workflow可以比Agent快N倍。

模式详解⑤：编排者-工人——受控的动态分配

这是6种模式中最"像Agent"的一种。中心模型（编排者）根据任务动态分配子任务给工人模型。但关键区别是：编排者的分配逻辑是受控的——它在一个预定义的决策空间内做选择，而不是像Agent那样可以做任意决策。

典型场景：多文件代码修改。编排者模型分析PR，决定"文件A需要修改函数签名，文件B需要更新调用方，文件C需要添加测试"——然后为每个文件分配一个工人LLM执行具体修改。控制流（编排者的分配策略）在开发者手中，只是具体内容（每个文件的修改方式）由LLM动态决定。

与Multi-Agent的区别：Multi-Agent系统中的Agent可以自主通信、协调、甚至"拒绝"执行任务——这种灵活性带来了巨大的协调开销和不可预测性。编排者-工人模式中的工人是被动的执行者，不做决策，只做分配到的工作。

模式详解⑥：评估器-优化器——受控的迭代改进

当任务有明确的评分标准时，评估器-优化器模式比Reflexion Agent更可控。流程：生成器产出内容 → 评估器打分 → 如果分数不达标，优化器根据评估反馈改进 → 再次评估 → 循环直到达标或达到最大迭代次数。

与Agent的Reflexion模式的区别：评估器-优化器的循环次数有硬性上限（通常2-3轮），评估标准是代码定义的（不是LLM自己判断的），且每一轮的改进方向是结构化的（来自评估器的结构化反馈，不是自由格式的反思）。

典型应用：翻译质量改进（用BLEU分数评估）、代码优化（用测试通过率评估）、文档可读性提升（用Flesch分数评估）。

6种模式的共同特征

注意一个关键事实：这6种模式里，控制流都在开发者手中。LLM负责的是每一步的"内容生成"，而不是"决定下一步做什么"。这就是Workflow和Agent的本质区别——谁来掌控控制流。

为什么控制流归属这么重要？因为当LLM不需要做路由决策时，你的系统获得了三个巨大优势：

  1. 可预测性：你能100%确定系统会走哪条路径，因为路径是代码定义的——你可以在代码中看到每一个if-else分支
  2. 可调试性：出了问题，你能精确定位到哪一步出了错，而不是面对一个"它自己决定这么做的"黑盒
  3. 成本可控：每一步的Token消耗是已知的，没有Agent循环带来的不确定性——你可以精确预估月度成本

这就是所谓的可靠性悬崖（Reliability Cliff）：在某个步骤数阈值之前，系统看起来运行良好；一旦超过这个阈值，成功率断崖式下跌。对于95%的单步准确率，这个悬崖大约在第5到第10步之间——5步时还有77%，到10步时就只剩60%了。

这个数学原理对"该不该用Agent"的决策有直接的指导意义：

工程推论

如果你的任务步骤数可预知且很少（1-3步），Agent的可靠性损失在可接受范围内。如果你的任务步骤数不可预知或可能很多（10步以上），你需要的不是Agent，而是一个将多步拆解为多个独立Workflow的系统设计——每个Workflow只做1-3步，可靠性保持在85%以上。

更深层的洞察来自METR（Model Evaluation & Threat Research）的研究发现：Agent以约50%可靠性完成的最大任务长度正在指数增长，能力翻倍周期从2025年的212天缩短到2026年的131天。这意味着更强的模型正在到来——但研究同时指出，"原始能力提升转化为可靠性提升的效果有限"，因为"更强的Agent尝试更多，但额外自主性意味着更不可预测的失败方式"。

换句话说：模型在变强，但可靠性悬崖这个数学规律没有变。你不能靠堆模型能力来逃避指数衰减——唯一的出路是减少步骤数，而这恰恰意味着用Workflow替代Agent。

2.4 88%失败率背后的7大反模式

让我们深入分析前三个"杀手级"反模式——它们合计占了61%的失败案例：

反模式#1：范围蔓延（Scope Creep）—— 34%

这是最常见的失败模式，也是最经典的反模式。它不是一次性犯的错误，而是一个渐进式的腐烂过程。它的典型演化路径是这样的：

初始需求很简单 "我们需要一个自动回复客户邮件的系统。" → 这本来一个分类器+模板+单次LLM调用就能搞定。预计2周开发，成本¥0.05/次。
第一个"顺便" "既然有了LLM，能不能顺便做情感分析？" → 加了一个情感分析Agent节点。开发延长到4周。
需求滚雪球 "既然能做情感分析，能不能自动判断是否需要升级到人工？" → 又加了一个决策Agent。开发延长到6周。
失控 "既然能判断升级，能不能自动查工单历史、推荐解决方案、生成回复草稿？" → 系统变成了一个臃肿的多Agent怪物。步骤数从2步膨胀到12步，可靠性从90%跌到54%，延迟从1秒涨到15秒。
崩溃 项目在花了$340K后被叫停。复盘时发现：初始需求只需要一个2周的Workflow项目就能满足。范围蔓延过程中增加的每一个"顺便"，都在系统可靠性、成本和延迟上付出了指数级的代价。

范围蔓延的根因在于一个认知偏差：增量需求的感知成本远低于实际成本。每个"顺便"看起来只是"多加一个功能"，但在多步系统中，每增加一个步骤都会让整体可靠性乘以一个小于1的系数。从2步增加到12步，即使每步准确率不变（95%），可靠性也会从90%跌到54%——不及格。

Anthropic的建议非常精准："起始范围比感觉舒适的更窄"。成功项目的共同特征是先做最小可行版本——甚至比直觉认为的还要小——然后根据生产数据逐步扩展。如果数据告诉你"需要加情感分析"，那时候再加——而不是在需求阶段就预建。

反模式#2：数据质量失败 —— 27%

这是一个经常被忽视但杀伤力巨大的反模式。Agent的输出质量有一个常被遗忘的前提假设：它依赖的数据是准确的。但现实世界中：

  • 知识库文档可能过时——研究表明，80%的企业文档在上次更新后超过6个月没人维护，其中30%包含已过时的信息
  • 数据库中的字段可能缺失或格式不一致——某金融Agent因为数据库中"账户余额"字段有时存储为字符串、有时存储为浮点数，导致每次格式转换都有5%的错误率
  • 外部API可能返回意外格式或错误——某天气查询Agent因为第三方API在一次版本更新中改变了JSON字段名，导致所有天气查询返回"未知"
  • 用户输入可能包含误导性信息——用户在客服对话中的错误描述会让Agent基于错误前提做推理

当一个Rule-Based系统遇到脏数据时，它会产生一个可预测的错误（比如返回空值或默认值，或者抛出异常被上层捕获）。但当一个Agent遇到脏数据时，它会基于错误数据做出不可预测的推理——它可能"创造性地"将错误数据与其他信息关联，生成一个看起来合理但完全错误的输出。这比不返回结果危险得多，因为错误的自信比诚实的"我不知道"更有害。

防御策略：在Agent的每一步工具调用之前，加入数据验证层——检查字段是否存在、格式是否正确、值是否在合理范围内。如果数据有问题，直接返回结构化错误，让Agent决定是重试还是降级。

反模式#3：安全阻塞 —— 14%

安全架构没有与开发同步建设。典型的失败场景是：团队花3个月搭建了一个功能完善的Agent系统，能查询数据库、调用内部API、发送邮件。项目即将上线时，安全团队介入审查："等一下，这个Agent能访问客户数据库？它有写入权限？用户可以通过自然语言让它执行任意SQL？"项目被阻塞，重新设计安全方案的成本比从头开发还高。

更糟糕的是，安全重构往往意味着在已有架构上"打补丁"——限制工具权限、加入输入过滤、增加审计日志——这些补丁会降低Agent的灵活性，可能让原本设计好的工作流变得不可用。结果是：要么放弃安全补丁上线（风险极大），要么重新设计架构（成本极高），要么放弃项目（沉没成本$340K）。三选一，没有好结果。

正确做法：安全设计从Day 1开始。在架构设计阶段就引入安全团队的审查，确保每个工具都有明确的权限边界、每个用户请求都经过身份验证、每个Agent操作都有审计日志。

失败模式的共同特征

注意一个规律：这三大失败模式——范围蔓延、数据质量、安全阻塞——都不是模型能力问题。它们是工程决策问题。换句话说，88%的失败率不是因为"AI不够强"，而是因为"架构师做了错误的技术选型"。这也解释了为什么应用结构化评估可以将失败率从88%降到15%以下——评估的正是技术选型，不是模型能力。

2.5 渐进复杂度阶梯：从API调用到Multi-Agent

理解了"为什么不该用Agent"之后，一个自然的问题是：如果确实需要增加智能，按什么顺序升级？答案是渐进复杂度阶梯——每一步都只在前一步确实不够用时才升级。

这个阶梯传达了一个核心理念：复杂度是代价，不是价值。每升一级，你都在用成本、延迟和可靠性换取灵活性。80%的业务场景在第0级和第1级就能解决。需要升级到第3级（Agent）的场景，实际上可能不到10%。

关键原则：在每一级停留足够长的时间，用生产数据验证它确实不够用了，再升级。Anthropic自己的SWE-bench团队就是这种做法——他们先尝试最简单的prompt+工具调用方案，只有在明确验证不够时才引入更复杂的Agent架构。

但成本对比还不仅于此。除了直接可量化的费用，Agent还有一系列隐性成本：

  • 调试成本：Agent的输出是非确定性的，同一个输入可能产生不同输出。当用户报告"Agent回复不正确"时，调试需要复现当时的完整上下文（包括对话历史、工具返回值、模型温度等），耗时可能是调试确定性Workflow的5-10倍
  • 监控成本：Agent系统需要比Workflow更细粒度的监控——每个工具调用的延迟、成功率、Token消耗，以及Agent的推理路径分析。这意味着更复杂的可观测性基础设施
  • 回归测试成本：每次Prompt修改或模型升级，都需要对Agent做全量回归测试，因为Agent的行为可能因为微小的Prompt变化而产生意想不到的改变
  • 团队培训成本：调试和维护Agent系统需要团队具备新的技能——Prompt工程、LLM行为分析、概率系统调试——这些技能的培养需要时间和资源

当然，这不是说Agent永远不值得用。有些场景确实需要Agent的灵活性。但你必须确保Agent带来的价值（灵活性、自动化程度）能够覆盖这些直接和间接成本。

2.7 Agent-Washing：当"Agent"只是营销标签

2025-2026年出现了一个值得警惕的现象：Agent-Washing（Agent粉饰）。厂商将简单的脚本和固定工作流贴上"Agent"标签以获取溢价。买家担心为Agent能力付钱却只得到Workflow功能。开发者担心过度工程化一个用循环和API调用就能解决的问题。

这个现象的泛滥程度远超想象。某咨询公司的调研发现，市面上标称"AI Agent"的产品中，超过60%实际上只是固定工作流——它们的执行路径在代码中是写死的，LLM只负责每一步的文本生成，完全不做路由决策。这些产品利用了"Agent"概念的热度来获取更高的定价和投资，但实际提供的价值和传统Workflow没有区别。

如何识别Agent-Washing？问三个问题：

❌ 伪Agent信号 步骤是固定的、可预知的 → 控制流写在代码里，LLM只负责每一步的内容生成。这本质上是Prompt链式Workflow，不是Agent。不管产品页面怎么宣传，它的核心逻辑只是"调用API → 处理结果 → 调用下一个API"。
✅ 真Agent信号 步骤数不可预知，每步的发现影响下一步 → LLM在运行时决定调用什么工具、什么时候停止。开发者只定义目标和工具集，不定义执行路径。真正的Agent在相同输入下可能走出完全不同的路径。

一个实用的判断标准——白板测试：

如果你能在一个白板上画出系统的完整执行流程图——每个分支、每个循环、每个条件——那么你的系统本质上就是Workflow，不管你在PPT里叫它什么。真正的Agent的流程图是一个开放循环：循环体内的每一步都由LLM动态决定，你无法预先画出完整路径。

"翻译功能 = 调API的10行代码 → 不需要Agent。开放式研究任务 = 每步发现影响下一步 → 适合Agent。"这个对比虽然简化，但捕捉了核心差异。确定性 vs 不确定性，这是Agent和Workflow的终极分界线。

2.8 "亮新事物"综合症：开发者的心理陷阱

Towards Data Science 的一位开发者写了一段非常诚实的反思：

"我刚上手CrewAI和LangGraph时，感觉自己打开了一个全新世界……突然之间，我不只是有了工具和管道——我有了团队（crews）。我搭得越多，就越频繁地碰到问题……一个Agent一直在'思考'的循环怎么调试？就在那一刻，我意识到我跳过了一个关键问题：这真的需要做成Agent吗？"

这就是"亮新事物"（Shiny New Thing）综合症的典型表现。它不是技术问题，而是心理陷阱——新技术带来的兴奋感会扭曲工程判断。当你刚学会一个新框架时，你有一种强烈的冲动去使用它，即使使用场景并不适合。

John Berryman（Arcturus Labs）在2025年9月的演讲中总结了AI工程实践的"七宗罪"：

  1. 追求完美准确率是死路——LLM是概率模型，100%准确率在数学上不可能。追求100%只会导致过度工程化（加更多检查步骤、更多Agent审查），反而降低整体可靠性
  2. 使用Agent时失去控制——把控制权交给LLM却不设护栏。Agent可能在"思考"中无限循环，每次循环都在消耗Token
  3. 不做上下文工程——以为堆prompt就能解决一切。实际上，Agent的上下文窗口是有限资源，必须精心管理
  4. 一开始就过度编排——不做简单方案，上来就搭Multi-Agent。这是最常见的新手错误
  5. RAG系统中检索和生成不分离——让Agent同时做检索和生成，导致两种功能互相干扰
  6. 复杂抽取不做拆分——让一个Agent同时抽取多种信息，而不是用多个专门的Workflow步骤
  7. 不知何时用框架、何时不用——Anthropic建议：能直接用LLM API就别用框架

Anthropic的框架使用建议尤其值得关注："我们建议尽可能直接使用LLM API，因为框架会隐藏prompt并鼓励过度工程化。" 这句话出自Agent框架的最大受益者之一（Anthropic自家的Claude是最常用的Agent模型之一），份量极重。如果连卖Agent模型的公司都说"别过度用框架"，那这个建议值得认真对待。

新手最常见的错误路径
  1. 所有问题都想用Agent解决 —— 拿着锤子找钉子
  2. 上来就搭Multi-Agent系统 —— "我要一个Supervisor管理三个Worker！" 但连单Agent都没验证过
  3. 不先尝试简单的prompt + 工具调用 —— 直接跳到最复杂的方案
  4. 忽视评估和监控基础设施 —— 没有评估管道，无法知道系统是否在改善
  5. 低估Token成本 —— 一个客户查询$47 API调用费不是笑话，是真实案例

避免这些陷阱的方法很简单——在开始任何AI项目之前，先完成下面的决策自查清单：

  1. 我是否先尝试了最简单的方案（直接LLM API调用）？
  2. 简单方案的具体不足是什么？（不能用"不够智能"这种模糊回答——必须是具体的功能缺失）
  3. 增加Agent层后，预期的灵活性收益能否覆盖成本增长（15-40倍）？
  4. 我是否有评估基础设施来衡量Agent的效果？
  5. 我是否有沙盒环境来安全测试Agent？

如果以上任何一个问题的回答是"不确定"，暂停Agent开发，先解决这个不确定性。

2.9 Rule-Based vs LLM-Based：何时规则完胜AI

在AI时代，有一个反直觉的事实：很多时候，传统的规则系统比LLM Agent更好。这不是退步，而是正确的工程选择。技术先进性不等于技术适用性——用最简单的能解决问题的工具，才是工程智慧。

让我们做一个系统性的对比：

📋 Rule-Based

  • 灵活性：低，只能处理预定义场景
  • 可预测性：高，决策路径透明
  • 计算成本：极低（CPU计算，毫秒级）
  • 开发成本：高（需穷举规则）
  • 维护成本：规则增多后指数增长
  • 可审计性：强（符合SOC2/ISO27001）
  • 错误模式：可预测的边界失败
  • 延迟：<10ms（纯规则计算）

🤖 LLM-Based Agent

  • 灵活性：高，可处理多样化输入
  • 可预测性：低，基于概率生成
  • 计算成本：高（GPU推理，秒级）
  • 开发成本：低（prompt工程）
  • 维护成本：模型更新即可
  • 可审计性：弱（黑盒决策）
  • 错误模式：不可预测的幻觉
  • 延迟：1-15s（取决于步骤数）

注意"可审计性"这一项。在金融、医疗、法律等强合规行业，每一条决策都必须能追溯到具体规则。一个LLM Agent说"基于概率，我选择了这个方案"在审计师眼中等于"无法解释的决策"。这就是为什么很多金融机构在尝试了LLM Agent后又回到了Rule-Based + LLM辅助的混合模式——Agent做初步处理，规则系统做最终决策。

更微妙的是"错误模式"的差异。Rule-Based系统的错误是可预测的——它总是在规则覆盖不到的边界case上失败，而且失败方式一致（返回默认值或抛异常）。LLM Agent的错误是不可预测的——它可能在任何地方以任何方式失败，包括生成完全虚构的内容（幻觉）。对于关键系统来说，不可预测的错误比可预测的错误危险得多。

混合策略：最佳实践

成熟的工程方案通常不是"全用规则"或"全用Agent"，而是混合策略——在系统的不同层面使用不同的技术：

  • 用规则处理确定性流程：输入校验、权限检查、固定业务逻辑、数据格式化。这些步骤的路径是确定的，用规则可以做到100%准确率和毫秒级延迟
  • 用LLM处理需要灵活性的部分：自然语言理解、内容生成、模糊匹配、意图识别。这些步骤的输入是多样化的，需要语义理解能力
  • 用规则监控Agent行为：安全边界（"Agent不能执行DROP TABLE"）、异常检测（"Agent连续5次工具调用失败，触发告警"）、兜底策略（"Agent无法处理时转人工"）

这就是为什么Anthropic建议的"三组件Agent模型"中，Tools和System Prompt是开发者在代码中定义的——这些是"规则"部分。只有Agent循环本身是"LLM灵活"的部分。好的架构不是最大化灵活性，而是在正确的地方使用灵活性。

2.11 行业回调与2026反思

2025年中开始，AI行业出现了一波值得关注的"回调"——大量"Agent泡沫"质疑文章出现，"Stop Using AI Agents for Everything"成为技术社区的热门话题。这并非AI冬天重演，而是行业从"技术兴奋期"进入"工程理性期"的标志。

LangChain State of AI Agents 2025调查显示，45.8%的小公司将"性能质量"列为首要关注——不是"功能丰富"，不是"支持更多工具"，而是"性能质量"。这说明市场已经开始从"功能竞赛"转向"可靠性竞赛"。

几个值得关注的行业趋势：

  • Co-Pilot优先：行业共识已从"完全自主Agent"转向"human-in-the-loop Co-Pilot"。先建人机协作系统，再根据数据逐步提升自主性级别
  • 评估基础设施成为头号投资优先级：团队意识到，没有评估管道就无法衡量Agent质量，无法衡量就无法改进
  • 从Multi-Agent到单Agent + Skills：减少复杂的多Agent协调，转向单Agent加载按需技能。这降低了协调复杂度和Token成本
  • MCP协议标准化：DeepSeek推动的Model Context Protocol正在成为Agent工具连接的统一标准（已有9400+个MCP Server），减少工具开发的重复工作

这些趋势的共同方向是：从"更复杂"转向"更可靠"。这也是本题想传达的核心精神——真正的Agent架构师不是能搭最复杂系统的人，而是能在复杂和简单之间做出正确选择的人。

思路分析小结

让我们回到开篇的问题："你确定你需要Agent吗？"现在你应该能从以下维度系统性地回答：

  1. 路径确定性：步骤能写下来吗？能 → Workflow。不能 → 继续评估
  2. 可靠性预算：你的步骤数会让成功率跌到可接受线以下吗？会 → 减少步骤数（用Workflow替代Agent循环）
  3. 成本可行性：$5,000+/月的Agent成本能被业务价值覆盖吗？不能 → 简化方案
  4. 基础设施就绪度：你有沙盒环境、评估管道、监控系统吗？没有 → 先补齐这些基础设施
  5. 团队能力：你能调试一个"它自己决定这么做的"系统吗？不能 → 从Workflow起步，逐步积累Agent调试经验
  6. 替代方案验证：你是否真的尝试过简单方案？还是只是假设"不够用"？如果只是假设，先试简单方案

记住Anthropic的建议：尽可能直接使用LLM API，因为框架会隐藏prompt并鼓励过度工程化。这句话的潜台词是——如果你发现自己在用框架"简化"Agent开发，先问自己：你真的需要Agent吗？

3.1 五个场景的决策分析

以下对5个场景逐一分析。注意：这些决策不是绝对的——同一个场景在不同业务约束下可能有不同选择。关键不是记住"答案"，而是掌握分析的方法和维度。

场景1：客服自动回复

决策：Workflow（路由分发模式）

分析维度：

  • 路径确定性：90%的工单处理路径完全可预知（分类→查询→模板回复），只有10%的复杂投诉可能需要灵活处理
  • 可靠性需求：客服系统面向终端用户，需要稳定SLA（响应时间<3秒），Agent的多步循环无法保证
  • 成本约束：日均处理量大（假设10,000次/天），单次成本差异会被放大（¥0.03/次 vs ¥4.7/次 = 日均差异¥46,700）

方案：用分类器做路由分发。标准问题走模板+单次LLM润色（2步Workflow），复杂投诉转人工或走更长的Workflow。10%复杂投诉可以未来考虑用Agent处理。

ROI：Workflow月成本约$300，Agent系统月成本约$5,500。月节省$5,200。且可靠性从~55%（多步Agent）提升到~92%（2步Workflow），延迟从8秒降到1.5秒。

场景2：代码审查助手

决策：混合方案（编排者-工人Workflow + 受限Agent）

分析维度：

  • 路径确定性：部分步骤可预知（运行测试、检查风格规范），部分需要语义理解（理解PR上下文）
  • 反馈信号：有丰富的可验证信号——测试通过率、Linting结果、覆盖率变化
  • 沙盒环境：天然存在（CI/CD pipeline）

方案：确定性任务（测试、规范检查）用Workflow，语义理解部分（PR上下文分析、改进建议）用受限Agent（最大迭代3轮）。Agent的工具集明确：读取代码、运行测试、查看diff。

ROI：参考QA Agent正面案例（7.4x ROI），类似场景适用。月成本$4,200，月节省$31,000。

场景3：多语言翻译管道

决策：Workflow（并行化模式）

分析维度：

  • 路径确定性：5种语言的翻译完全独立，路径100%确定（输入→翻译→输出），没有动态决策需求
  • 延迟优势：并行执行5路翻译，总延迟 = 1次翻译时间。串行Agent需要5×延迟
  • 质量改进：如果需要质量检查，加一个评估器-优化器循环即可，不需要完整的Agent

方案：并行化Workflow，5路同时翻译。每路可以独立选择最优模型（如英文用deepseek-v4.1-flash，日文用专用翻译模型）。

ROI：并行Workflow月成本约$200，多Agent协调系统月成本约$4,000+。月节省$3,800。且延迟从15s+降到2s。

场景4：投资研报生成

决策：Agent（带护栏）

分析维度：

  • 路径确定性：研报生成是开放式任务——从哪些数据源获取信息、如何综合分析、报告结构怎么组织，这些步骤不可预知
  • 反馈信号：有丰富的工具反馈（数据API返回结构化数据，可做数值校验）
  • 成本可行性：人工写一份研报约需8小时（$800成本），Agent约$15/份——ROI 53倍

方案：用带护栏的Agent。设置最大迭代次数（15步）、预算限制（$20/份）、事实核查步骤（交叉验证关键数据）。

ROI：53x ROI。这是Agent的甜点区——开放式任务 + 可验证反馈 + 高人工成本替代。

场景5：用户意图分类

决策：单次增强LLM调用（最简Workflow）

分析维度：

  • 路径确定性：4类分类 = 1次LLM调用。路径完全确定
  • 复杂度匹配：用Agent做分类就像用航母运快递——杀鸡用牛刀
  • 成本极致优化：甚至可以先用规则系统处理高频case（关键词匹配），只有规则覆盖不到的才调LLM

方案：单次LLM调用 + 4类输出Schema。或者更简：规则优先 + LLM兜底。

ROI：单次LLM调用约¥0.01/次。Agent系统约¥4.7/次。成本降低470倍。

变体题3：内容审核——Rule + Agent混合系统设计

题目背景

某社交媒体平台需要设计内容审核系统，处理每日100万条UGC（用户生成内容）。审核维度包括：违规违法内容、广告垃圾、人身攻击、不实信息。现有纯规则系统准确率82%，但误杀率高（把正常内容判为违规）。业务方希望用AI提升准确率，但要求：

  • 99.9%的审核决定必须在2秒内完成
  • 每条审核成本不超过¥0.005
  • 所有审核决定必须可审计（能解释为什么这么判）
  • 对争议内容（约2%）需要人工复核

学习目标：训练"混合架构"的设计能力——不是在Rule-Based和Agent之间二选一，而是设计一个两层系统：Rule-Based处理高吞吐确定性场景，Agent处理需要灵活判断的边缘case。这是大型互联网系统中最常见的Agent应用模式——不是全量Agent化，而是在规则的基底上精准注入Agent能力。

与原题的差异：原题关注"该不该用Agent"，本题要求设计一个"Rule + Agent混合"的生产系统。难度在于如何在严格的性能/成本/合规约束下找到两者的最佳分工边界——这需要你对两种技术的优劣有精确的认知。

考察的核心能力：约束条件下的架构设计、性能-准确率-成本的三角权衡、合规性工程、流量分配策略。

输入输出示例

输入：100万条/日UGC样本、4类审核标准、SLA约束条件

输出：

  1. 系统架构图（标注Rule层和Agent层的边界）
  2. 流量分配方案：多少%走纯Rule？多少%走Rule+LLM？多少%走Agent？
  3. 每条路径的延迟和成本计算
  4. 审计日志设计：如何记录每条审核决定的完整决策链？
  5. A/B测试方案：如何安全上线新系统？

本章核心要点回顾

🔑 核心要点
  1. 最简原则：用最简单的方案解决问题，只有不够时才增加复杂度
  2. 路径判断：步骤可预知→Workflow；不可预知+有反馈信号→Agent
  3. 可靠性悬崖：单步95%准确率×20步=36%成功率，多步Agent不可靠
  4. 成本对比：Agent月成本$5,000+，等效Workflow通常$200-400
  5. 88%失败率：头号原因是范围蔓延(34%)，不是模型不够强
  6. 渐进复杂度：从API调用→Workflow→Agent→Multi-Agent，每步只在前一步不够时升级
  7. Agent-Washing：能画出完整流程图的"Agent"本质是Workflow
  8. 混合策略最优：规则处理确定性流程，LLM处理灵活性需求，规则监控Agent行为
  9. Anthropic建议：能直接用LLM API就别用框架
  10. 三问法则：路径确定吗？有反馈信号吗？有护栏吗？三问皆"是"才考虑Agent
