一、题目描述

前文已讨论"什么时候不该用 Agent"。假设你已经通过了三问法则的检验——路径不确定、有反馈信号、有护栏——你确信你的场景确实需要 Agent。那接下来面临的就是一个最基础的工程问题：Agent 怎么"动手"？

大语言模型（LLM）本质上是一个文本生成引擎。你给它一段文字，它续写一段文字。就这么简单。它本身不能查数据库、不能调用 API、不能发送邮件、不能执行计算——它只能输出文本。如果说前八章我们构建的 Agent 架构是给这位"军师"配备了完整的指挥体系，那 Function Calling（函数调用，简称 FC）就是给这位军师递上了第一部电话机，让她终于能够向前线下达命令。

Function Calling 是 2023 年 6 月由 OpenAI 首先在 deepseek-v4.1-flash API 中标准化的能力，随后迅速被各大模型厂商跟进。它允许开发者向 LLM 声明一组"工具函数"的名称、参数格式和使用说明，LLM 在对话过程中可以根据用户意图，自主决定调用哪个函数、组装什么参数，并以结构化的 JSON 格式输出调用请求。宿主程序（你的 Python 代码）解析这个 JSON，执行真正的函数，然后把结果返回给 LLM 继续对话。这个机制看似简单，但它几乎是所有现代 AI Agent 框架的基石——ReAct 循环、LangGraph 的工具调用、CrewAI 的任务执行、MCP 协议的底层通信，全都建立在 Function Calling 的基本范式之上。

本题是你进入 G2"工具调用与 MCP"模块的第一道关卡。掌握 FC，你才能真正理解 Agent 是如何与外部世界交互的。无论你后面学 LangGraph 还是 CrewAI，底层都是这套机制。

题目背景

你是某电商平台的后端工程师。产品经理老王给了你一个需求：做一个智能客服 Agent，能够处理三类用户请求——

  • 商品搜索：用户说"有没有蓝色条纹衬衫"，Agent 需要调用商品搜索接口
  • 订单查询：用户说"我的订单到哪了"，Agent 需要根据订单号查物流信息
  • 退款申请：用户说"这个衬衫质量不行，要退款"，Agent 需要发起退款流程

这三个场景有一个共同特征：LLM 自己无法完成（它不能直接访问你的数据库），但 LLM 能够理解用户意图并决定"该调用什么函数、传什么参数"。这就是 Function Calling 的典型应用场景。你作为工程师的职责是：定义好工具函数、正确配置 FC 参数、处理好执行与结果回传的循环。

题目要求

请实现一个基于 Function Calling 的多工具智能客服 Agent，满足以下条件：

  1. 定义至少 3 个工具函数（商品搜索、订单查询、退款计算），每个函数需要完整的 JSON Schema 参数定义
  2. 使用 deepseek-v4.1-flash（智谱 AI）或 deepseek-v4.1-flash的 Function Calling API 作为主要实现（不要使用 OpenAI API，我们在本章会详细讲解国内可用方案）
  3. 支持多轮对话（用户可以在一次工具调用后继续追问）
  4. 具备基本的错误处理能力（参数缺失、函数执行失败时给出友好提示，而不是崩溃）
  5. 对退款等敏感操作实现简单的二次确认机制

输入输出示例

输入：

Agent: [调用 search_products(query="衬衫", color="蓝色", pattern="条纹")]

2. 休闲棉麻蓝条纹衬衫 - ¥159

二、思路分析

这是 G2 模块的第一道题，也是整本书中信息密度最高的核心章节之一。Function Calling 看似只是一个 API 参数的用法差异，但它背后的设计哲学、工程实践和常见陷阱值得花整整一章来讲透。我们按照"是什么 → 怎么运作 → 怎么用好 → 有什么坑"的逻辑逐步展开，确保你在做完这道题之后，不仅会写 FC 代码，更理解每一行代码背后的"为什么"。

在开始深入之前，先给一个全局视图：Function Calling 涉及的技术栈可以分为三层。最底层是模型能力层——不同模型（deepseek-v4.1-flash、deepseek-v4.1-flash、deepseek-v4.1-flash 等）对 FC 的支持程度和格式差异。中间是工程封装层——JSON Schema 定义、参数校验、错误处理、工具注册表等代码基础设施。最上层是框架抽象层——LangGraph、CrewAI、Dify 等框架对 FC 的封装和增强。本章主要聚焦于前两层，让你理解 FC 的底层原理和工程实践。框架层我们在 G5 模块（第 31-40 题）会专门讨论。理解了本章的内容，你在学习任何 Agent 框架时都能迅速看穿它们的抽象外壳，直击底层本质。

2.1 FC 的本质——从"嘴"到"手"的进化

在没有 Function Calling 之前，开发者是怎么让 LLM"调用工具"的？答案是通过 Prompt Engineering。你会在 system prompt 里写："你可以使用以下工具：1. 搜索商品 2. 查询订单……当你需要使用某个工具时，请输出 TOOL: search_products，然后在下一行输出 JSON 参数。"然后你的代码用正则表达式去解析 LLM 的输出，提取函数名和参数。

这个方案能用吗？能用。好用吗？极其不好用。问题在于：LLM 的输出格式不稳定。你可能让它输出 TOOL: search_products，它偏偏输出 工具调用: search_products 或者 我将使用 search_products 函数。你写的正则只能覆盖有限的变化，总有遗漏。更糟糕的是，LLM 可能在不该调用工具的时候输出了"工具调用"格式，或者参数格式混乱——JSON 的 key 加了引号但 value 忘了加引号，数组写成了逗号分隔的字符串，嵌套对象少了一层大括号……

Function Calling 的突破在于：它把"工具调用"从非结构化的自然语言输出变成了结构化的 API 级别能力。你不再需要用正则去解析 LLM 的输出来"猜"它想调用什么函数。模型在训练阶段就已经学会了：当它"决定"要调用某个函数时，在 API 响应中生成一个专门的 tool_calls 字段，里面包含函数名和严格符合 JSON Schema 的参数。这个字段是模型原生支持的，不是靠 prompt "哄"出来的。

这个变化可以用一个类比来理解：以前你让一个实习生帮你发快递，你得口头告诉他地址、收件人、物品信息，然后他写下来去发——问题是每个人的写法不一样，快递员经常看不懂。现在你给了他一张标准化的快递单，他只需要填空就行。Function Calling 就是那张标准化的快递单。

但要注意的是，Function Calling 并非万能魔法。它解决的是"输出格式"问题，而非"输出质量"问题。LLM 仍然可能选错函数（比如该查订单时却调了搜索）、传错参数（比如把订单号当成商品 ID）、或者在不该调用工具时强行调用。这些问题的根源是模型能力本身，而非格式规范。我们在后面讨论 Tool Hallucination 和 Schema Drift 时会深入展开。

从发展历程来看，Function Calling 的标准化经历了几个阶段。2023 年 6 月 OpenAI 首先在 deepseek-v4.1-flash 和 deepseek-v4.1-flash-turbo 中推出了 Function Calling 功能，最初的格式是 functions 参数和 function_call 响应字段。2023 年 11 月，OpenAI 将这个能力升级为更通用的 tools 和 tool_calls 格式（也就是我们现在使用的标准格式），同时支持了并行工具调用。这个新格式很快成为行业标准——Anthropic 的 deepseek-v4.1-flash、Google 的 deepseek-v4.1-flash、智谱的 deepseek-v4.1-flash、deepseek-v4.1-flash 等模型都采纳了这个格式或做了兼容设计。可以说，tools/tool_calls 已经成为 Function Calling 的事实标准，就像 REST 之于 Web API 一样。

虽然 API 格式趋于统一，但不同模型在 Function Calling 的底层实现上有本质差异。有些模型（如 deepseek-v4.1-flash 系列）是在预训练阶段就融入了工具调用的训练数据，使模型真正"理解"了工具的概念；而另一些模型可能只是在推理时通过特殊的 prompt 模板来实现类似效果，模型本身并没有深度理解工具调用的语义。这种差异在简单场景中不明显，但在复杂的多轮工具调用、工具组合推理等场景中会导致显著的性能差距。这也是 BFCL 评测存在的意义——它能够揭示不同模型在 FC 能力上的真实差距。

如上图所示，Prompt Engineering 时代的链路有四个环节，每个环节都可能出错。而 Function Calling 时代把最脆弱的两个环节——"格式不稳定输出"和"正则解析"——替换成了 API 原生支持的结构化字段。这不是量变，是质变。整个 AI Agent 工程领域能在 2023 年之后爆发式发展，Function Calling 的标准化功不可没。

2.2 核心设计理念——决策与执行分离

这是 Function Calling 最重要的架构原则，没有之一。Martin Fowler 在他的技术博客中专门阐述了这一点：

"当使用 Function Calling 时，LLM 本身并不执行函数。它识别适当的函数，收集所有必需的参数，并以结构化 JSON 格式提供信息。这个 JSON 输出然后可以被反序列化为 Python 的函数调用。"

—— Martin Fowler

用一句话概括：LLM 是策略师，不是执行者。它负责"想"——分析用户意图、选择正确的函数、组装参数；它不负责"做"——真正的 API 调用、数据库查询、文件操作全部由你的确定性代码完成。

为什么要做这样的分离？因为 LLM 的输出本质上是概率性的。即使准确率高达 99%，那 1% 的错误如果发生在执行环节（比如误删了数据库记录、发送了错误的邮件、向支付接口传了错误的金额），后果可能是灾难性的。把执行交给确定性代码，你就可以在执行前做校验、做权限检查、做审计日志——这些安全保障在 LLM 内部是无法实现的。

理解了这个原则，你就能理解为什么所有成熟的 Agent 框架都采用"LLM 决策 + 宿主执行"的架构。LangGraph 的 create_agent（1.x 新 API，替代了已废弃的 create_react_agent）内部实现就是：LLM 返回 tool call → 框架自动执行绑定的 Python 函数 → 结果送回 LLM。CrewAI 的 Agent 执行 Task 时也是同样的流程。这些框架做的事情本质上就是帮你把"决策与执行分离"的管道代码封装好了。

2.3 FC 完整工作流程——六步走完全程

让我们把 Function Calling 的完整工作流程拆解成六个步骤。这是你理解后续所有代码和框架的基础——无论你用的是 LangGraph、CrewAI 还是 Dify，底层都在走这个流程。

上图清晰地展示了职责边界：步骤①②⑤⑥由开发者（也就是你）负责，步骤③④是 LLM 原生完成。步骤⑥的虚线箭头是关键——它代表了一个"回环"，函数执行结果需要送回 LLM，LLM 看到结果后可能继续调用下一个工具，也可能生成最终的自然语言回复。这个回环就是 Agent 的核心循环。

让我们用一个具体例子走一遍这六步。假设用户说"有没有蓝色条纹衬衫"：

步骤①：你定义了一个 search_products 函数，并用 JSON Schema 声明它接受三个参数——query（搜索关键词，必填）、color（颜色，可选）、pattern（图案，可选）。

步骤②：你把 search_products 的 Schema 定义连同用户消息一起发给 LLM 的 API。此时 API 请求中会多一个 tools 参数，里面是所有可用工具的 JSON Schema 列表。

步骤③：LLM 分析用户消息"有没有蓝色条纹衬衫"，识别出这是一个商品搜索请求，理解"蓝色"对应 color 参数、"条纹"对应 pattern 参数、"衬衫"对应 query 参数。这个"理解"过程是模型在训练阶段就学会的能力，不需要你在 prompt 中特别指示。

步骤④：LLM 在响应中返回一个 tool_calls 字段，内容类似：{"name": "search_products", "arguments": {"query": "衬衫", "color": "蓝色", "pattern": "条纹"}}。注意这个 JSON 是模型在 API 响应中原生返回的结构化字段，不是你需要从自然语言中解析的。

步骤⑤：你的代码解析这个 JSON，找到对应的 Python 函数 search_products，用解析出的参数调用它。函数内部可能调用了你公司的商品搜索 API，查到了三条结果。

步骤⑥：你把函数执行结果（三条商品信息）以 role: "tool" 的消息格式送回 LLM。LLM 看到结果后，用自然语言组织回复："找到 3 款蓝色条纹衬衫：1. 经典商务蓝条纹衬衫……"。

这六步看起来很机械，但每一步都有工程细节需要注意。比如步骤①中 JSON Schema 描述写得不够清晰，LLM 就可能在步骤③中选错参数；步骤⑤中如果函数没有做参数校验，就可能因为 LLM 传入了非法参数而崩溃。这些都是我们在后面小节中要深入讨论的。

2.4 JSON Schema——工具描述的"语言"

JSON Schema 是 Function Calling 的核心基础设施。你可以把它理解为"工具的说明书"——它告诉 LLM 这个工具叫什么名字、做什么用、接受哪些参数、每个参数是什么类型、哪些参数是必填的。LLM 就是靠阅读这份"说明书"来决定该不该调用这个工具以及怎么调用的。因此，Schema 写得好不好，直接决定了 FC 的准确率。

这份 Schema 里有几个关键字段需要特别注意。第一个是 name：函数名必须与你的 Python 函数名完全一致。建议用 snake_case 命名，语义清晰。避免使用 func1、do_something 这种无意义的名称——LLM 在选择工具时严重依赖名称的字面含义来匹配用户意图。

第二个是 description：这是影响 LLM 工具选择准确率的最重要字段。好的描述应该包含三要素：做什么（功能）、什么时候用（触发条件）、返回什么（输出格式概要）。对比两种写法："搜索商品" 和 "在商品库中搜索商品。支持按关键词、颜色、图案等条件筛选。返回匹配的商品列表，包含名称、价格、库存信息。"——后者的信息量让 LLM 能够更准确地判断"这个用户请求是否应该调用这个函数"。研究表明，在 BFCL（Berkeley Function Calling Leaderboard）评测中，仅通过优化 description 就能提升工具选择准确率 10-20%。

第三个是 parameters.properties：每个参数需要声明 type（类型）、description（描述）和可选的约束（如 enum 枚举值、minimum/maximum 范围、pattern 正则）。参数描述同样重要——"搜索关键词，如'衬衫'、'鞋子'" 远比 "query" 有用，因为它告诉 LLM 这个参数期望什么样的值。

第四个是 required：必填参数列表。不在 required 中的参数是可选的，LLM 只在用户明确提及时才会填充它们。比如用户只说"有没有衬衫"，LLM 只会传 query="衬衫"，不会猜测 color 和 pattern。但如果你把 color 也设为 required，LLM 就会尝试从用户输入中推断一个颜色，或者索性随机编一个——这就导致了参数幻觉。

这里有一个容易被忽略的技巧：additionalProperties: false。这个字段告诉 LLM"除了 properties 中列出的参数外，不允许传其他参数"。不加这个限制时，LLM 有时会"自作主张"地添加 Schema 中没有定义的参数（比如把用户的原话作为一个新参数传进去）。设为 false 可以有效减少这类参数幻觉。

另一个实用技巧是善用 enum 约束。如果你的函数只接受固定的几个值（比如颜色只有"红、蓝、黑、白"），一定要用 enum 列出来。这比让 LLM 自由发挥要可靠得多——你不想看到 LLM 返回 "color": "天蓝色带点紫" 这种你的数据库里根本没有的值。Enum 约束把开放性的生成问题变成了封闭性的选择问题，准确率天然更高。

除了基本类型和 enum，JSON Schema 还支持更复杂的参数结构。数组类型（type: "array"）用于接受多个同类值，比如 "product_ids": {"type": "array", "items": {"type": "string"}} 可以让 LLM 一次性传入多个商品 ID。嵌套对象用于表达层级关系，比如地址参数可以嵌套 province/city/district 三层。但要注意：嵌套层级不宜超过两层，否则 LLM 组装参数的准确率会明显下降。如果参数结构过于复杂，更好的做法是把它拆成多个扁平的简单参数，或者拆成多个工具函数。

还有一个值得讨论的话题是参数的粒度设计。以订单查询为例，你是让 LLM 传一个 order_id 就够了，还是同时传 order_id + user_id 做权限校验？答案是后者——即使 LLM 从用户消息中提取 user_id 的准确率不如 order_id，你也应该声明这个参数并在函数内部做交叉验证。参数冗余设计的本质是用更多的上下文信息来降低误操作风险。在安全敏感场景（支付、退款、数据删除）中，这种做法尤其重要。

最后提一下 description 中写示例的技巧。在参数描述中给出一个具体示例，能显著提升 LLM 的参数组装质量。比如 "description": "订单号，格式如 ORD-YYYYMMDD-XXX，例如 ORD-20260628-001" 比 "description": "订单号" 有效得多——LLM 看到示例后就能按图索骥地生成格式正确的值。这种 few-shot 式的提示虽然简单，但在实际工程中效果显著，BFCL 评测中优化 description 添加示例后准确率平均提升 8-12%。

2.6 Schema Drift——参数漂移的幽灵

Schema Drift（Schema 漂移）是 Function Calling 中最隐蔽也最让人头疼的问题之一。它指的是：LLM 返回的参数虽然格式上是合法的 JSON，但参数值的语义偏离了你期望的范围。这种现象不是模型 bug，而是 LLM 作为概率模型固有的不确定性。

举几个实际场景中常见的 Schema Drift 例子：

类型漂移：你定义 order_id 为 string 类型，但 LLM 返回了 "order_id": 12345（数字而不是字符串）。虽然 JSON 中数字和字符串是不同类型，但有些模型的 FC 实现并不严格遵守 Schema 中的类型声明。如果你的代码直接用 json.loads() 解析，就会得到一个 int 而不是 string，后续以字符串方式处理时就会出错。

格式漂移：你的函数期望 order_id 格式是 "ORD-YYYYMMDD-XXX"，但 LLM 从用户消息中提取时可能把日期格式弄错（"ORD-20262806-001"），或者少了一个横线（"ORD-20260628-001" 少了中间的横线）。用户甚至可能只说了"28号那个订单"，LLM 就自己编了一个订单号。

枚举值漂移：你在 enum 中定义了 ["红色", "蓝色", "黑色"]，但 LLM 返回了 "蓝色条纹"——它把用户说的原话直接塞了进去，而不是映射到枚举值。这种情况在模型能力较弱或 description 不够清晰时特别常见。

幻觉参数：你没在 Schema 中定义 sort_by 参数，但 LLM 自行添加了 "sort_by": "price"。如果你的代码没有设置 additionalProperties: false，这个多余参数就会被传给你的函数，可能导致意外行为。

如何应对 Schema Drift？核心原则是：永远不要信任 LLM 返回的参数，在执行前做完整校验。具体做法包括：用 Pydantic 或类似的验证库在函数入口处做参数校验；对关键参数做范围检查和格式检查（比如用正则验证订单号格式）；对枚举值做 fuzzy matching（比如"蓝色条纹"可以匹配到"蓝色"）；对所有参数做 fallback 处理（如果参数缺失或非法，给 LLM 返回一个错误提示，让它重新生成）。

这里有一个重要的工程实践：当参数校验失败时，不要直接抛异常或返回错误信息给用户。你应该把错误信息以 role: "tool" 的消息格式送回 LLM，告诉它"参数 X 的值不合法，期望格式是 Y，请重新生成"。LLM 看到这个错误反馈后，通常能够自动修正参数并重新调用。这就是所谓的"错误反馈循环"（Error Feedback Loop），它是让 Agent 具备自适应能力的关键机制。

错误反馈循环的实现非常直观。当你的 Pydantic 校验抛出 ValidationError 时，你把这个异常信息格式化为一条 tool 消息：{"role": "tool", "content": "参数校验失败：order_id 格式不正确，期望 ORD-YYYYMMDD-XXX，收到的是 '12345'。请使用正确格式重新调用。"}。LLM 看到这条消息后，会在下一轮推理中尝试修正参数。你需要设置一个最大重试次数（通常 3 次），超过后直接返回兜底错误信息给用户，防止死循环。这种"校验→反馈→重试"的模式和人类发现错误后自我纠正是同一个道理，是 Agent 智能性的重要体现。我们在第 13 题会专门讨论工具调用错误处理的完整方案，包括指数退避、Fallback 策略和断路器模式。

2.7 Tool Hallucination——工具幻觉的成因与对策

Tool Hallucination（工具幻觉）指的是 LLM 在不该调用工具的时候调用了工具，或者调用了根本不存在的工具。这比 Schema Drift 更严重——Schema Drift 至少是调对了函数但参数有问题，而 Tool Hallucination 是连函数都选错了。

工具幻觉主要有三种表现形式：

第一种：虚构函数名。LLM 返回了一个 tool_calls 字段，但里面的函数名根本不在你声明的 tools 列表中。比如你只定义了 search_products 和 get_order_status，LLM 却返回了一个 send_email 调用。这种情况通常发生在模型能力较弱、或用户请求与可用工具不匹配时——LLM"很想帮忙"，但它手头没有合适的工具，就自己"发明"了一个。

第二种：在不该调用时调用。用户只是闲聊说"今天天气真好"，LLM 却非要调用 search_products。这种情况通常是因为 system prompt 过于"鼓励"工具调用（比如写了"你应该尽可能使用工具来帮助用户"），导致模型对工具调用的阈值过低。

第三种：过度调用。用户问一个简单问题（"衬衫多少钱"），LLM 本可以一次性调用 get_product_details 就回答，但它连续调用了搜索、详情查询、库存查询三个函数，浪费了 token 和时间。这种情况在复杂工具集特别常见，LLM 不能精确判断"最少需要几个工具调用"。

应对 Tool Hallucination 的策略包括以下几个层面：

第一，严格限制工具列表。不要一次把所有工具都传给 LLM。研究表明，当工具数量超过 15-20 个时，LLM 的工具选择准确率会显著下降（这一现象被称为"工具超载"）。在第 12 题中我们会专门讨论工具选择策略，包括工具分组、动态加载、Reranking 等高级技巧。

第二，在代码层做白名单校验。这是最基本也是最重要的防线。当 LLM 返回 tool_calls 时，第一步就检查 func_name 是否在你的 FUNCTION_REGISTRY 中。如果不在，不要尝试执行，而是返回一条提示消息："该功能暂不可用。请使用以下可用功能：..."。这个白名单校验的成本几乎为零，但能有效阻止虚拟函数调用。在 Python 中可以用一个简单的 if func_name not in FUNCTION_REGISTRY 来实现。

第三，优化 system prompt。在 prompt 中明确告诉 LLM 何时该调用工具、何时不该。一个有效的 prompt 模式是："你只能使用以下工具：[列表]。如果用户的请求不在这些工具的能力范围内，请直接用文字告知用户你无法处理该请求，不要编造不存在的功能。" 这种显式的约束比泛泛地说"尽可能帮助用户"要有效得多。同时，tool_choice 参数应设为 "auto" 而非 "required"——后者会强制 LLM 每次都调用工具，即使完全不需要。

第四，日志和监控。在生产环境中，你应该记录每一次工具调用的日志，包括 LLM 想调用什么函数、传了什么参数、执行是否成功。通过分析这些日志，你可以发现 Tool Hallucination 的模式和频率，进而有针对性地优化 Schema 描述或调整工具列表。如果某个工具频繁被误选，可能说明它的 description 与其他工具混淆了，需要重新措辞。

2.8 工具数量管理——太多了选不准

这是一个经常被忽略但在生产系统中极其关键的问题：当你给 Agent 配备的工具越来越多时，整体准确率反而会下降。这并非模型 bug，而是一个认知信息过载问题——LLM 的注意力机制在面对过多选项时，和人类一样会"选择困难"。

上图为示意性的工具数量-准确率关系。不同模型的下降曲线有所差异，但整体趋势一致：5 个工具以内准确率最高（通常 95%+），10 个左右开始轻微下降，15 个是一个关键临界点——超过这个数量后准确率下降加速。这也是为什么在第 5 题中我们提到"单 Agent 的工具天花板大约在 15 个"的原因。

当你确实需要超过 15 个工具时，常见的解决策略包括：工具分组——按功能领域将工具分组（如"商品工具组"、"订单工具组"、"支付工具组"），LLM 先选择组再选择具体工具；动态加载——根据对话上下文只传递相关工具子集；工具 Reranking——先用轻量模型对工具做初步筛选排序，再将 Top-K 工具传给主模型。这些策略我们在第 12 题会详细展开。

这里展开讲一下工具分组的具体实现思路。假设你的客服系统有 30 个工具，涵盖商品、订单、支付、物流、售后、用户管理六个领域。你可以把它们分成六组，每组 5 个工具。然后在 system prompt 中声明六个领域的简要描述，让 LLM 先判断用户请求属于哪个领域。根据判断结果，你只在 tools 参数中传递该领域的 5 个工具（加上一个通用的 transfer_to_human 转人工工具）。这种两阶段的方法将有效工具数量控制在 6 个以内，准确率可以维持在 95% 以上。代价是多了一次轻量的 LLM 调用用于领域判断，但这次调用可以用更小更快的模型（如 deepseek-v4.1-flash），成本很低。

动态加载是比分组更精细的策略。你可以维护一个用户上下文向量，包括用户最近浏览的商品类别、当前会话的主题等，然后根据这个上下文向量从工具库中检索出最相关的 Top-5 工具。这种方法的准确率比分组更高，因为它考虑了用户的实时上下文而不只是粗粒度的领域划分。但实现复杂度也更高，你需要一个工具描述的向量索引和实时检索管道。在大型企业应用中，这种投入是值得的。

2.9 BFCL——Function Calling 的基准测试

BFCL（Berkeley Function Calling Leaderboard）是 UC Berkeley 推出的 Function Calling 基准测试平台，也是目前评估模型 FC 能力最权威的公开评测。了解 BFCL 的评测维度，可以帮助你在选模型时做出更明智的判断。

BFCL 的评测维度设计得非常贴近真实场景。其中"非函数调用"这一维度特别值得关注——它考察的是模型在不需要工具时能否正确地不调用工具。很多模型在这一项上表现糟糕，因为它们在训练时见过太多"调用工具"的样本，形成了一种"只要有工具就想用"的倾向。在选模型时，不要只看总分数，要特别关注 Non-FC 维度的得分——这个维度得分低的模型会导致严重的 Tool Hallucination 问题。

目前 BFCL 排行榜上表现最好的模型通常能取得 90% 以上的综合准确率，包括 deepseek-v4.1-flash、deepseek-v4.1-flash 3.5 Sonnet 等。国产模型中，deepseek-v4.1-flash 系列和 deepseek-v4.1-flash 也在 FC 能力上取得了不错的成绩，完全可以胜任生产环境的工具调用需求。建议你在选模型时去 BFCL 官网查看最新排名，关注你计划使用的模型在各个维度上的表现。

BFCL 的评测用例来自真实场景，覆盖了多种复杂边界情况。比如"参数中包含特殊字符"（Unicode 表情、多语言混合）、"用户消息中同时包含多个工具调用意图"（比如"帮我查下订单顺便搜下类似的商品"）、"工具的 description 刻意写得模糊"（测试 LLM 是否能在描述不充分的情况下做出正确判断）。这些边界情况在日常开发中经常遇到，但很多模型在它们上面的表现远不如理想。这就是为什么不能只看模型官方宣传的"支持 Function Calling"就放心使用——你需要在自己的业务场景中做实际测试。

对于想要深入研究 FC 的工程师，建议你做一件事：自己写几组测试用例，覆盖你的业务场景中最常见的工具调用模式（单工具、多工具并行、多轮链式），然后在 deepseek-v4.1-flash、deepseek-v4.1-flash 等模型上跑一遍，记录准确率和延迟。这种场景化的基准测试比通用排行榜更有参考价值。在开源社区中，Promptfoo 和 LangSmith 等工具都提供了 FC 评测的脚手架，可以帮助你快速搭建评测管道。

2.10 错误处理最佳实践

在生产环境中，Function Calling 的失败率通常在 5-15% 之间。这个数字看似不高，但如果你每天处理 10000 条用户请求，就意味着每天有 500-1500 次工具调用失败。如果没有完善的错误处理机制，这些失败会直接导致用户体验崩溃。

另一个重要的实践是敏感操作的二次确认。退款、删除、支付等操作一旦执行就难以撤销，在调用这类函数之前，你应该让 LLM 先输出一个确认请求（"确认为订单 XXX 发起退款吗？"），等用户明确回复"确认"后才真正执行。这个机制虽然简单，但能有效防止 LLM 误判导致的不可逆操作。这也是我们这道题目的要求之一。

2.11 tool_choice 参数——控制 LLM 的工具使用策略

在结束思路分析之前，我们还需要讨论一个容易被忽略的 API 参数：tool_choice。这个参数控制 LLM 在面对工具时的行为策略，它有三个可选值，理解它们的差异对于精细控制 Agent 行为至关重要。

tool_choice: "auto"（默认值）：LLM 自主决定是否调用工具以及调用哪个。这是最灵活也最常用的设置，适用于绝大多数 Agent 场景。LLM 会根据用户意图和可用工具列表做出判断——如果用户的问题需要工具来回答（如"查下我的订单"），就调用相应工具；如果可以直接回答（如"你们的客服电话是多少"），就不调用。

tool_choice: "none"：禁止 LLM 调用任何工具，即使声明了 tools 参数。这看起来矛盾——既然声明了工具为什么又不让用？但这个模式有实际用途：当你想用同一套 prompt 做纯对话回复时（比如用户切换到了闲聊模式），你可以动态切换 tool_choice 而不必重新构造 messages。这比移除 tools 参数再重新发送请求要高效得多。

tool_choice: {"type": "function", "function": {"name": "specific_func"}}：强制 LLM 调用指定的函数。这种模式用于你已经知道用户意图是什么、需要调用哪个工具的场景。比如在多 Agent 系统中，Supervisor Agent 已经判定用户的请求应该由"订单查询 Agent"处理，就可以在传递给子 Agent 的请求中设置 tool_choice 强制调用 get_order_status，跳过 LLM 的工具选择步骤，减少延迟和 token 消耗。但要注意：强制调用意味着 LLM 仍然需要组装参数，如果用户消息中缺少必要信息（比如没说订单号），LLM 可能会编造一个参数值——这直接导致了 Schema Drift。因此，使用强制调用前要确保用户消息中包含足够的参数信息。

在多轮对话中动态切换 tool_choice 是一种高级优化技巧。比如在对话初期用 auto 让 LLM 自由探索用户意图，一旦确定了具体任务后切换为强制调用，减少不必要的推理时间。这种"先自由后强制"的策略在复杂任务中能有效提升响应速度和准确率。

在阅读代码时，建议你特别关注以下几个设计决策的"为什么"：为什么用字典做函数注册表而不是 if-else？为什么每个工具都要有独立的 Pydantic 校验模型？为什么退款函数不直接执行退款而是返回确认信息？为什么对话历史用列表而不是数据库？这些设计决策背后都有明确的工程权衡，理解它们比记住代码本身更重要。

上面这份代码包含了我们在思路分析中讨论过的所有关键设计：三层脚手架（安全检查在 system prompt 中体现、LLM 决策通过 FC 完成、执行层有 Pydantic 校验）、JSON Schema 定义（含 enum 约束和 additionalProperties: false）、错误处理（Pydantic 校验失败时返回结构化错误给 LLM）、以及多轮对话支持（通过 history 列表维护上下文）。

代码的核心运行流程如下：用户输入首先和对话历史一起组装成 messages 列表，连同 SYSTEM_PROMPT 和 TOOLS 定义一起发送给 deepseek-v4.1-flash API。如果 LLM 返回了 tool_calls，代码遍历每个工具调用：先用 json.loads() 解析参数字符串，再从 FUNCTION_REGISTRY 中取出对应的函数和 Pydantic 校验模型，校验通过后执行真实函数，执行结果以 role: "tool" 格式追加到 messages 中。所有工具执行完毕后，发起第二次 API 调用，让 LLM 看到工具结果并生成最终的自然语言回复。这就是我们在 2.3 节讨论的六步工作流程的代码实现。

有几个值得注意的实现细节：

  • FUNCTION_REGISTRY：用字典做函数注册表，避免 if-else 链。当工具数量增加时，只需在注册表中添加一行即可。这种设计遵循了开闭原则——对扩展开放，对修改关闭。
  • Pydantic 校验：每个工具有独立的参数校验模型。validate_order_id 用正则验证订单号格式，防止 Schema Drift。如果校验失败，异常信息会被格式化为友好的提示返回给 LLM，触发自纠错循环。
  • 两轮 API 调用：第一轮 LLM 返回 tool_calls，执行后需要第二轮调用让 LLM 看到结果并生成自然语言回复。这是 FC 多轮对话的标准模式，理解这一点对于实现任何 Agent 都至关重要。
  • 退款不直接执行：calculate_refund 只计算金额并返回确认提示，真正的退款执行需要另一个函数（如 execute_refund）。这种"先计算再确认"的模式是处理敏感操作的最佳实践，有效防止了误操作。
  • 对话历史管理：history 列表在多轮对话中持续追加，让 LLM 能够引用之前的对话内容（如"上次提到的那个订单"）。但要注意，当对话轮次过多时需要做摘要压缩或滑动窗口截断，否则会超出上下文窗口限制。

四、举一反三

掌握了 Function Calling 的基本实现之后，以下变体题可以帮助你拓展能力边界。

变体 1：多工具并行调用

学习目标：训练多工具协调和并行执行能力。在真实场景中，用户的一个请求往往需要同时调用多个工具——比如"查下我最近三笔订单的状态"需要连续调用三次查询。原题的代码是串行遍历 tool_calls 的，但如果三个查询互不依赖，串行执行就浪费了时间。

与原题差异：原题中每轮对话最多调用一个工具，且代码是串行执行的。本变体要求支持并行调用：当 LLM 一次返回多个 tool_calls 时（即开启 parallel_tool_calls），你的代码应该并行执行这些函数（使用 asyncio.gather() 或 concurrent.futures.ThreadPoolExecutor），而不是串行逐个执行。这要求你把工具函数改成 async，并处理并行执行中的异常隔离（一个函数失败不应影响其他函数的结果）。

考察核心能力：异步编程（asyncio）、并行工具执行的编排、多结果聚合、异常隔离。这个变体看似简单，但在生产环境中处理并行工具调用的错误边界是一个有挑战性的工程问题。

text 
用户: 帮我查下 ORD-001、ORD-002、ORD-003 这三个订单的状态
Agent: [并行调用 get_order_status x3]


订单汇总：


ORD-001: 已发货，预计明天到达


ORD-002: 仓库处理中


ORD-003: 已签收

变体 2：动态工具加载

学习目标：训练工具管理策略能力。当工具数量超过 15 个时，全量传递会导致准确率下降，需要实现动态加载机制。这是大型企业级 Agent 系统的核心架构问题之一——当你的客服 Agent 需要对接商品、订单、支付、物流、售后、会员等十几个子系统时，工具总数轻松超过 50 个。怎么让 LLM 在这么多工具中准确选择？这就是本变体要解决的挑战。

与原题差异：原题只有 3 个工具，全部传递即可。本变体假设你有 30 个工具（覆盖商品、订单、支付、物流、售后等多个领域），需要实现一个工具路由器：先用一轮轻量 LLM 调用判断用户意图属于哪个领域，然后只传递该领域的工具子集给主 LLM。这道题考察的不只是 FC 的使用，更是 Agent 架构设计能力——你需要设计领域分类体系、工具归属规则、以及跨领域场景的处理策略。

考察核心能力：意图分类、工具分组策略、两阶段 LLM 调用编排、token 成本优化、跨领域工具调用。这个变体的难点在于如何设计一个既准确又高效的路由器——太粗会导致一个领域内工具过多，太细又增加了路由错误的概率。

text 
用户: 帮我退货
[阶段1: 工具路由器] → 判定领域: 售后 → 加载售后工具组（4个工具）
[阶段2: 主LLM] → 调用 calculate_refund(order_id="ORD-001", reason="退货")
Agent: 已为您发起退货申请...

变体 3：工具调用链的自纠错

学习目标：训练错误恢复和自适应能力。当工具调用失败时，Agent 不应该直接报错给用户，而应该尝试自我修正。这道题模拟的是真实生产环境中最常见的场景——用户提供的信息不完整或格式不对，Agent 需要通过对话逐步引导用户提供正确信息。

与原题差异：原题中错误处理只是简单地返回错误信息给 LLM。本变体要求实现一个完整的重试与自纠错循环：当 Pydantic 校验失败或函数执行出错时，把结构化的错误信息反馈给 LLM（包括期望的参数格式和实际收到的值），让 LLM 重新选择函数或修正参数。最多重试 3 次，超过后转人工处理。你需要特别注意防止死循环——如果连续两次 LLM 都犯了同样的错误，说明这个错误超出了模型的自我修正能力，应该优雅地降级。

考察核心能力：错误分类与分级处理、LLM 自纠错循环设计、终止条件判断、优雅降级策略。这道变体题的难点不在于代码实现，而在于错误处理的策略设计——什么错误可以重试，什么错误应该直接失败，重试间隔如何设置，这些都需要你在实践中摸索。

text 
用户: 查下我的订单 28号那个
Agent: [第1次调用] get_order_status(order_id="28号那个")


→ 校验失败: 订单号格式应为 ORD-YYYYMMDD-XXX
Agent: [第2次调用] get_order_status(order_id="ORD-20260628-???")


→ 校验失败: 订单号不完整
Agent: [回复用户] 抱歉，我无法确定完整的订单号。


请提供完整的订单号（格式：ORD-YYYYMMDD-XXX）
要点回顾

FC 本质：把工具调用从非结构化文本输出变成结构化 API 能力，是 Agent 与外部世界交互的基础。

核心原则：LLM 是策略师不是执行者——决策与执行分离，是所有 Agent 框架的底层架构。

六步流程：定义工具 → 传递给 LLM → LLM 推理 → 返回 JSON → 执行函数 → 返回结果，形成循环。

JSON Schema：description 是影响准确率的最重要字段；善用 enum 和 additionalProperties:false 减少幻觉。

格式兼容：deepseek-v4.1-flash 和 deepseek-v4.1-flash 均兼容 OpenAI FC 格式，代码只需替换 api_key 和 base_url。

Schema Drift：LLM 返回参数的类型、格式、枚举值可能漂移，必须用 Pydantic 在函数入口做防御性校验。

Tool Hallucination：虚构函数名、不该调用时调用、过度调用——通过工具数量控制、白名单校验、prompt 优化来缓解。

工具数量：超过 15 个工具时准确率显著下降，需采用分组、动态加载、Reranking 等策略。

BFCL 评测：关注 Non-FC 维度得分，选模型时不要只看总分。

错误处理：5-15% 的工具调用会失败，必须有完整的校验→重试→fallback→审计日志链条。
