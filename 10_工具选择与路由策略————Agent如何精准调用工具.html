10. 工具选择与路由策略——Agent如何精准调用工具

⭐⭐ 中级 工具描述质量 数量上限 Reranking 命名规范 工具发现

一、题目描述

背景

你的团队正在构建一个企业级智能助理 Agent。起初一切顺利——3 个工具（查询天气、发送邮件、搜索文档）时，Agent 表现完美，每次都能精准调用正确的工具。但随着业务需求不断叠加，工具列表开始膨胀：日程管理、数据库查询、报表生成、文件操作、代码执行、知识库检索、消息推送、用户管理……三个月后，你的 Agent 挂载了 28 个工具。

然后问题来了。用户说"帮我查一下上周的销售数据"，Agent 却调用了搜索文档工具；用户说"给张三发个消息"，Agent 犹豫了一下，先调用了邮件工具，失败后又跳到了日历工具。团队开始怀疑是不是模型不够聪明，于是换了个更大的模型——但情况只是略有改善，错误率依然在 20% 左右徘徊。

这不是模型能力问题，而是工具选择策略问题。就像一个走进巨型超市的顾客，面对 28 排货架，如果没有清晰的指示牌和合理的商品分区，即便他再聪明，也会在找一瓶酱油上浪费十分钟。LLM 面对工具时的困惑，与之如出一辙。

题目要求

请你作为 Agent 架构师，为上述场景设计一套完整的工具选择优化方案，需要覆盖以下方面：

  1. 工具描述优化：给出工具描述的编写规范，包括名称、描述、参数的最佳实践，并指出常见反模式。
  2. 工具数量管理：设计一套工具分组与按需加载策略，解决工具数量过多导致的准确率下降问题。
  3. 工具选择增强：实现一个基于语义相似度的工具 Reranking 机制，在 LLM 做最终决策前先缩小候选范围。
  4. 工具发现机制：基于 MCP 协议的 tools/list 机制，设计一个支持动态工具注册与发现的方案。

输入输出示例

输入：一个包含 25 个工具定义的 JSON 列表（工具名称、描述、参数 Schema），以及一个用户查询字符串。

输出：经过优化后的工具选择流程——先通过语义检索筛选出 Top-5 候选工具，再让 LLM 从候选列表中做最终选择，输出被选中的工具名及调用参数。

本题难度为 ⭐⭐（中级），但涉及的知识面相当广。工具选择是 Agent 工程化中"看似简单实则深不见底"的典型问题——入门容易（不就是写个 description 吗），精通极难（涉及 LLM 认知机制、信息检索、协议设计等多个领域）。如果你之前认为"工具越多越强大"，这道题会彻底改变你的看法。

二、思路分析

在动手写代码之前，我们需要先搞清楚一个根本问题：LLM 到底是怎么选工具的？只有理解了底层机制，才能在正确的层面做优化。否则，所有的改进都像是闭着眼睛修水管——拍一拍，哪里漏水补哪里，永远修不完。

2.1 LLM 工具选择的认知原理

当你在 API 调用中传入 tools 参数时，LLM 并不是"理解"了每个工具的功能然后理性地做选择。实际发生的事情要机械得多：LLM 把所有工具的 name、description、parameters 三个字段拼接成一段文本，附加在用户消息之前作为上下文，然后基于这个扩展后的上下文做 next-token prediction。换句话说，对 LLM 来说，选工具本质上是一次阅读理解加文本续写任务。

这意味着什么？意味着 LLM 选工具的过程，和一个学生在开卷考试中翻参考书找公式的过程惊人地相似：

  • 如果参考书的目录写得清晰准确（工具描述质量高），找到正确公式只需几秒钟
  • 如果参考书有 200 页且没有目录（工具数量过多且缺乏组织），找一个小公式可能要翻十分钟
  • 如果两个章节标题几乎一样（工具名称冲突），学生会困惑到底该看哪一章
  • 如果公式说明写得含糊不清（描述反模式），学生可能会用错公式还不自知

理解了这个认知原理，就能明白为什么后续的所有优化策略——描述质量、数量控制、分组分类、Reranking——本质上都在做同一件事：帮 LLM 更高效地分配注意力。所有的方法都只是为了一个目标服务：让正确的工具在 LLM 的注意力分布中获得最高权重。

2.2 工具描述质量对选择准确率的影响

如果说工具选择是一场考试，那么工具描述就是参考书里的说明文字。大量的工程实践和研究表明，工具描述的质量是影响 LLM 工具选择准确率的第一因素——比模型能力、提示词工程、甚至工具数量都更为关键。一个粗糙的描述配上最强大的模型，选择准确率可能还不如一个精确的描述配上中等模型。

一个高质量的工具描述需要回答三个问题：这个工具做什么？什么时候该用它？什么时候不该用它？大多数开发者只回答了第一个问题，而忽略了后两个——这正是工具误选的根源所在。

让我们看一个典型的反面案例和正面案例对比：

❌ 差描述（常见写法） name: search
description: "搜索数据"
parameters: {"query": {"type": "string"}}
✅ 好描述（工程级写法） name: search_product_database
description: "在产品数据库中按关键词、SKU编号或品类搜索商品信息，返回商品名称、价格、库存状态。适用于用户询问商品详情、库存查询、比价等场景。不适用于订单查询（请使用 get_order_status）或用户账户操作（请使用 get_user_info）。"
parameters: {"query": {"type": "string", "description": "搜索关键词，支持中文和英文"}, "category": {"type": "string", "enum": ["electronics", "clothing", "food"], "description": "可选：限定搜索品类"}}

看出差异了吗？好描述比差描述长了五倍，但每一个字都在帮 LLM 做更精准的判断。具体来说，高质量描述包含五个关键要素：

动作定义（What） 用一句话精确描述工具的功能，使用动词开头。"搜索产品数据库中的商品信息"远好于"搜索数据"——前者告诉 LLM 搜索的对象和范围，后者什么都没说。动作定义要避免歧义词汇，比如"处理"可以理解为任何操作，几乎没有信息量。
返回值说明（Returns） 告诉 LLM 工具会返回什么样的数据。这非常关键——因为 LLM 需要判断工具的输出能否满足用户的需求。如果返回值不明确，LLM 可能会选错工具然后用幻觉来弥补信息差。例如"返回商品名称、价格、库存状态"就比"返回数据"好一百倍。
适用场景（When to use） 明确列出"在什么情况下应该使用此工具"。这相当于给 LLM 一个正面信号——当用户请求匹配这些场景描述时，注意力权重会显著提高。适用场景的描述应该尽量覆盖该工具的主要使用 case，用自然语言列举 2-3 个典型场景。
不适用场景（When NOT to use） 这是最常被遗漏的要素。明确告诉 LLM "什么情况不要选我"，可以有效减少与相似工具的混淆。这种负面指引的效果往往比正面指引更好——因为排除法比选择法更快。推荐写法："不适用于 XXX 场景（请使用 YYY 工具）"。
参数语义（Parameter semantics） 每个参数都应该有清晰的 description，不仅说明数据类型，还要说明语义含义。例如 "query: 搜索关键词，支持中文和英文" 远好于仅仅标注 "query: string"。参数描述还应包含格式要求、取值范围、是否必填等约束信息。

在我见过的实际案例中，仅仅把工具描述从"差描述"升级到"好描述"，不改变任何代码逻辑，LLM 的工具选择准确率就能从 65% 提升到 90% 以上。这不是夸张——描述质量就是有这么大的影响。如果整个团队只能做一项工具选择优化，我会毫不犹豫地推荐：先把描述写好。

2.3 工具描述反模式

了解了"好描述长什么样"之后，我们还需要系统性地认识"坏描述"——因为有些反模式非常隐蔽，即使是有经验的开发者也容易踩坑。以下是五类最常见的工具描述反模式，你在实际工程中几乎一定会遇到其中至少三种：

反模式1：名称过于泛化 get_data、process、search、handle——这些名称完全没有信息量。LLM 看到名为 get_data 的工具时，根本不知道要 get 什么 data。正确做法是在名称中嵌入领域语义：get_customer_orders、search_knowledge_base。泛化名称是工具混淆的头号原因。
反模式2：描述过于简短 "发送消息"——发给谁？通过什么渠道？消息格式是什么？这些信息全部缺失。LLM 在看到这个描述时，无法判断它和另一个名为 send_notification 的工具有什么区别。描述至少应包含动作、对象、返回值和适用场景四个维度。
反模式3：多个工具描述高度相似 当你有三个工具分别叫 send_email、send_message、send_notification，且描述都写着"发送消息给用户"时，LLM 基本是在抛硬币做选择。解决方案是在描述中明确每个工具的独占场景和差异化能力——渠道不同、格式不同、触发条件不同。
反模式4：参数无描述 只写了参数名和类型：{"x": "number", "y": "number"}。LLM 不知道 x 是经度还是横坐标，不知道 y 是纬度还是纵坐标。结果是 LLM 瞎猜参数含义，调用时张冠李戴。每个参数必须有清晰的语义说明。
反模式5：隐藏副作用 描述里写"更新用户信息"，但实际上这个工具会发送邮件通知、触发 webhook、写审计日志。这些副作用如果不写明，LLM 无法在需要"静默更新"的场景中做出正确选择。所有副作用都必须在描述中显式声明。
最危险的反模式：描述与实际行为不一致

比"描述差"更可怕的是"描述错误"。如果一个工具的描述写的是"查询用户信息"，但实际代码里还会修改用户的最后登录时间——这种隐式副作用会导致 LLM 在需要纯查询的场景中误触发写入操作。而且这种 bug 极难排查，因为从 LLM 的角度看，它确实"选对了工具"——是工具描述骗了它。原则：描述必须与代码行为严格一致，有变更时同步更新描述。

2.4 工具数量上限——15 个阈值效应

现在我们来聊一个让很多团队措手不及的现象：工具数量阈值效应。具体来说，当 Agent 挂载的工具数量在 10 到 15 个以内时，LLM 的选择准确率通常能维持在 90% 以上。但一旦超过 15 个，准确率就会出现显著的下降——而且这不是线性下降，而是加速下降。到 25 个工具时，准确率可能已经跌破 60%。

这个现象的根本原因在于 Transformer 的注意力机制。当上下文中包含 N 个工具描述时，LLM 需要在 N 个候选之间分配注意力。当 N 较小时，每个工具都能获得足够的注意力预算，LLM 可以仔细"阅读"每个描述并做出准确判断。但当 N 增大时，注意力被稀释——就像一个老师同时监督 30 个学生，根本看不过来。这就是所谓的"注意力稀释效应"（Attention Dilution Effect）。

更糟糕的是，工具数量增加还带来一个间接问题：描述之间的词汇干扰。当有 20 个工具时，很多工具的描述不可避免地会出现词汇重叠。比如 search_product 和 search_order 都包含 "search"，LLM 的注意力会被这些相似词汇分散，导致误选。研究表明，干扰程度与工具描述之间的语义相似度正相关——功能越相近的工具，互相干扰越严重。

上图的数据是基于多个 LLM 厂商的测试基准和社区工程经验总结的趋势曲线。具体的阈值数字会因模型能力、工具描述质量和工具间的相似度而有所浮动——能力强的大模型可能到 18 到 20 个工具才开始退化，能力弱的小模型可能 10 个就开始出问题。但15 作为一个安全的工程经验值，适用于当前主流模型。在实际项目中，建议把这个数字当作硬性约束来对待——就像函数圈复杂度上限一样，超过了就需要重构。

那么问题来了：当业务需求确实需要超过 15 个工具时该怎么办？答案就是下面要讲的工具分组与按需加载策略，以及Reranking 机制。这两种方法可以从不同层面缓解工具数量过多带来的注意力稀释问题。

2.5 工具分组与分类

工具分组的核心思想很简单：不要把所有工具一次性全部暴露给 LLM，而是根据当前对话的上下文，只提供相关的工具子集。这就像一个瑞士军刀——你不会同时展开所有刀片，而是按需弹出需要的那一个。也像一个百货商场——顾客进来后先看楼层指引牌（意图分类），然后直奔目标楼层（工具分组），而不是在一楼就面对所有三万件商品。

分组策略通常有两种维度，可以组合使用：

按功能域分组是最直觉的维度。把工具按照业务领域归类：数据查询类（搜索数据库、查询订单、获取用户信息）、通信类（发邮件、发消息、推送通知）、文件操作类（读取文件、上传文件、生成报表）、系统管理类（创建用户、修改权限、查看日志）等。在对话开始时，先用一轮轻量级的意图分类判断用户请求属于哪个功能域，然后只加载该域的工具。意图分类可以用一个小模型完成，成本很低——只需要一次简单的分类判断，而不是完整的工具选择。

按使用频率分组是另一种实用维度。将工具分为三层：常用工具层（日常对话中高频使用的核心工具，如搜索、查询、发送消息，通常 5-8 个，常驻加载）、专业工具层（特定场景下才需要的工具，如生成年度报表、导出数据、批量处理，按需加载）、管理工具层（管理员才能使用的工具，如用户管理、系统配置，需要权限验证后才加载）。这种分层方式参考了操作系统的内存管理——热数据在内存，冷数据在磁盘，各取所需。

数据查询组（6个工具） search_db, get_order, get_user_info, query_sales_data, search_knowledge_base, get_inventory
通信组（4个工具） send_email, send_message, push_notification, create_meeting
文件操作组（5个工具） read_file, write_file, upload_file, generate_report, export_data
管理组（3个工具） create_user, update_permission, view_logs

通过分组，原本 18 个工具的 Agent 在任何一次对话中只需要暴露 4 到 6 个工具——完全在安全区内。这种做法的代价是多了一次意图分类的 LLM 调用（可以用小模型完成，成本极低），换来的是工具选择准确率从 65% 到 95% 的大幅提升。这是一笔非常划算的交易。实际工程中，意图分类的准确率通常在 95% 以上——因为它只需要做单选题（选一个分组），而不是多选题（从一堆工具中选一个）。

2.6 工具名称冲突与命名规范

工具名称冲突是多工具环境中的另一个隐形杀手。当两个工具的名称或功能描述高度相似时，LLM 的注意力会被均分到两个工具上，导致选择置信度大幅下降——即使选对了，confidence 也不高；更多的情况是选到了那个"看起来也行"的错误工具。这种问题在 MCP 多 Server 环境下尤其严重——不同的团队、不同的 MCP Server，很容易注册名字相似的工具。

名称冲突通常有三种表现形式：

  1. 完全同名：两个不同 MCP Server 注册了同名工具（如两个 Server 都提供 search 工具）。这在 MCP 生态中非常常见，因为不同团队开发的 Server 很容易用到通用词汇。MCP 协议规范本身没有强制名称唯一性，这需要 Agent 层面来解决。
  2. 功能重叠：名称不同但功能高度相似。比如 send_email 和 send_message 在很多场景下可以互换——但一个走 SMTP 协议、一个走 IM 协议，选择错误会导致用户收不到信息。这种冲突最难发现，因为表面上看起来"两个都能用"。
  3. 前缀冲突：db_query 和 db_search——前缀相同，区别仅在最后一个词。LLM 很容易混淆这类工具，特别是在快速推理时。读者可能觉得这个例子很极端，但在实际项目中，同一团队的命名风格高度一致，前缀冲突是非常常见的。

解决方案是建立一套命名规范。推荐使用"域名_动作_对象"三段式命名法，这种方法借鉴了 RESTful API 的命名哲学——每个工具名本身就是自解释的：

采用三段式命名的好处是双重的：对 LLM 来说，每个工具名本身就是一段高密度的语义信息，不需要读 description 就能大致判断功能——相当于在每个工具前面挂了一个高亮标签；对开发者来说，按域名前缀排序后，功能相近的工具会自然聚集，便于管理和维护。在团队协作中，命名规范还可以作为 Code Review 的一项检查标准——不遵循命名规范的工具 PR 直接打回。

对于 MCP 多 Server 环境下的名称冲突，MCP 协议本身提供了 server_name.tool_name 的命名空间隔离机制。在实际工程中，建议在工具注册时自动加上 Server 名称作为前缀，确保全局唯一性。例如来自 Weather Server 的 search 工具会被注册为 weather_search，来自 Knowledge Base Server 的 search 会被注册为 kb_search——冲突自动消解。

2.7 工具描述 Reranking 策略

当工具数量无法减少到 15 个以内时（有些复杂业务场景确实需要 20 到 30 个工具），Reranking 策略是目前工程实践中最有效的解决方案。它的核心思想借鉴了 RAG（检索增强生成）领域的成熟经验：先用检索缩小范围，再用 LLM 精选。这个思路在搜索引擎、推荐系统中已经验证了几十年——先召回后排序，两步走永远比一步到位更高效。

具体流程分两个阶段：

Reranking 的技术实现并不复杂。第一步，离线阶段：把所有工具的 name + description 拼接成文本，用 Embedding 模型（如 OpenAI text-embedding-3-small 或国内的 bge-large-zh）生成向量，存入向量索引。第二步，运行时：把用户的 query 同样向量化，在工具向量库中做 Top-K 检索（K 通常取 5），取相似度最高的 5 个工具作为候选。第三步，把候选工具的完整 Schema（包括参数定义）传给 LLM，让它做最终选择。整个过程只在第一步和第二步之间多了一次向量检索（通常 < 5ms），对用户体验几乎无影响。

这里有一个关键的工程细节：Embedding 模型的选择很重要。通用的英文 Embedding 模型在中文工具描述上表现很差，因为中英文的语义空间差异巨大。如果你的工具描述是中文的，务必使用中文优化的 Embedding 模型。国内可选方案包括智谱的 embedding-3、百度的 embedding-v1 以及开源的 bge-large-zh。这些模型在中文语义匹配上的准确率比英文模型高出 20-30%。

🔑 Reranking 的核心价值

把 28 选 1 的问题降维成 5 选 1。在 5 个候选中，LLM 的选择准确率可以恢复到 95% 以上——几乎等于只有 5 个工具时的表现。而代价仅是一次 < 5ms 的向量检索。

2.8 工具发现机制——tools/list 与动态注册

到目前为止，我们讨论的工具选择策略都建立在一个前提上：Agent 提前知道有哪些工具可用。但在 MCP 生态中，工具列表不是静态的——新的 MCP Server 可能在运行时被加载，已有的 Server 可能动态注册新工具。这就是 MCP 协议中 tools/list 机制要解决的问题。

MCP 协议定义了一个标准的发现流程。当 Client 连接到 Server 后，第一步就是发送 tools/list 请求，Server 返回所有已注册工具的完整描述（name、description、inputSchema、annotations）。Client 缓存这个列表，后续的 tools/call 调用就基于这个缓存。如果 Server 的工具列表发生变更（新工具上线、旧工具废弃），Client 可以通过 notifications/tools/list_changed 通知触发重新拉取。

这套机制看起来简单，但在多 Server 环境下有几个工程挑战需要注意。第一个挑战是发现延迟：如果你有 5 个 MCP Server，每个 Server 有 10 个工具，启动时需要发送 5 次 tools/list，每次可能需要 100-300ms（包括连接建立和工具描述序列化）。这意味着 Agent 冷启动时会有 0.5-1.5s 的延迟。解决方案是并行发送所有 Server 的 tools/list 请求，并用异步方式加载——用户不需要等所有工具都加载完才能开始对话。

第二个挑战是工具聚合与去重。多个 Server 可能提供功能重叠的工具——比如三个不同的 Server 都提供了某种形式的搜索功能。Client 需要维护一个全局工具注册表，处理命名冲突（通过加 Server 前缀），并决定是否对功能重叠的工具做去重。推荐策略是：不去重，而是在工具描述中明确标注来源和差异，让 LLM 自己判断选哪个。因为"看起来功能一样"的工具，实际上可能在参数格式、返回值结构、副作用等方面存在差异——自动去重很容易误删。

第三个挑战是动态注册。在某些高级场景中，Server 可以在运行时动态注册新工具——比如一个数据库 MCP Server 在检测到新表创建后，自动注册一个查询该表的工具。这种动态能力让 Agent 的工具集可以随环境变化而自适应扩展。但要注意安全：动态注册的工具必须经过相同的 Schema 校验和安全审计，不能因为是"运行时添加的"就跳过安全检查。

2.9 工具版本管理与兼容性

工具和 API 一样会演进——参数会变、返回值会改、功能会迭代。没有版本管理，一次工具升级就可能导致 Agent 行为异常。这在 MCP 生态中尤其重要，因为 Server 和 Client 可能由不同团队维护，一个不兼容的变更就可能让整个系统瘫痪。

版本管理的核心原则是向后兼容优先。每次工具变更都应遵循"加法不做减法"的原则：新增参数时给默认值（旧 Client 不传该参数也能正常工作），修改返回值时只增字段不删字段，废弃功能时先标记 deprecated 而不是直接删除。这种渐进式演进策略可以确保旧版本 Client 不会因为 Server 升级而崩溃。

对于必须做的不兼容变更（比如参数名修改、返回值结构重组），推荐使用版本化工具名：query_order_v1、query_order_v2。虽然这种命名不那么优雅，但它有一个巨大的优势——新旧版本可以共存，Client 可以按自己的节奏迁移。比"优雅"更重要的是"不裂"。

在 MCP 协议层面，工具的 annotations 字段可以携带版本信息。推荐在工具注解中加入 version 字段，Client 可以据此做兼容性判断。同时建议维护一个工具变更日志（CHANGELOG），记录每个版本的变更内容，方便团队协作和问题排查。

变体一：多 Server 工具聚合与去重

学习目标：训练多源工具管理能力。当 Agent 同时连接 3-5 个 MCP Server，每个 Server 提供 5-10 个工具时，如何设计全局工具注册表、处理命名冲突、管理版本兼容性。

与原题的差异点：从单 Server 变为多 Server 环境。新增了命名空间隔离（server_name.tool_name）、跨 Server 功能去重策略、Server 健康检查与故障转移等挑战。

考察的核心能力：分布式系统设计思维、命名空间管理、容错策略。

输入输出示例：输入为 3 个 MCP Server 的工具列表（共 35 个工具，其中 4 对存在功能重叠），输出为一个去重后的全局工具注册表和聚合选择流程。

变体二：工具使用反馈学习

学习目标：训练自适应优化能力。设计一个反馈收集机制，记录每次工具选择的命中/ miss 情况，用历史数据持续优化 Reranking 模型和分组策略。

与原题的差异点：从静态规则变为动态学习。新增了用户隐式反馈（是否接受工具调用结果）和显式反馈（用户纠正）的收集管道、在线/离线 Reranking 模型更新机制。

考察的核心能力：数据驱动优化、反馈闭环设计、在线学习策略。

输入输出示例：输入为 1000 条历史工具选择记录（含命中/miss 标签），输出为优化后的 Reranking 模型参数和准确率对比报告。

变体三：工具安全审计与权限控制

学习目标：训练工具安全治理能力。在 25 个工具中，有 8 个涉及写操作或敏感数据访问，需要设计基于 RBAC 的工具访问控制和操作审计体系。

与原题的差异点：从选择准确率变为安全治理。新增了工具风险等级分类（基于 annotations 的 readOnlyHint/destructiveHint）、用户角色权限矩阵、敏感操作审计日志。

考察的核心能力：安全架构设计、RBAC 模型、审计合规。

输入输出示例：输入为用户角色（admin/staff/viewer）和工具列表，输出为过滤后的可用工具列表和审计日志格式定义。

  • 描述为王：工具描述质量是选择准确率的第一影响因素，胜过模型能力和工具数量
